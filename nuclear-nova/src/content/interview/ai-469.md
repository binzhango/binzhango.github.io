## Question

Implement the core of an editor text buffer: efficient insert/delete at arbitrary positions and fast line lookup. What structure do you pick?

## Brief answer

Use a balanced rope or piece tree augmented with subtree character counts and newline counts. Splitting and joining at an offset supports local edits, while newline aggregates support logarithmic line lookup. A plain string copies the entire suffix; a simple piece-table list eventually pays linear costs in the number of pieces.

## Detailed answer

This compact randomized treap stores one character per node for clarity. Production editors use larger leaves to reduce memory overhead and separately define UTF-16, Unicode-code-point, and grapheme offsets.

```python
import random

class R:
    def __init__(self, ch):
        self.ch, self.priority = ch, random.random()
        self.left = self.right = None
        self.size, self.lines = 1, int(ch == '\n')

def size(t): return t.size if t else 0
def lines(t): return t.lines if t else 0

def fix(t):
    if t:
        t.size = 1 + size(t.left) + size(t.right)
        t.lines = (t.ch == '\n') + lines(t.left) + lines(t.right)
    return t

def merge(a, b):
    if not a or not b: return a or b
    if a.priority < b.priority:
        a.right = merge(a.right, b)
        return fix(a)
    b.left = merge(a, b.left)
    return fix(b)

def split(t, n):
    if not t: return None, None
    if n <= size(t.left):
        a, t.left = split(t.left, n)
        return a, fix(t)
    t.right, b = split(t.right, n - size(t.left) - 1)
    return fix(t), b

def insert(t, at, text):
    if not 0 <= at <= size(t): raise IndexError(at)
    middle = None
    for ch in text: middle = merge(middle, R(ch))
    a, b = split(t, at)
    return merge(merge(a, middle), b)

def delete(t, start, end):
    if not 0 <= start <= end <= size(t): raise IndexError((start, end))
    a, rest = split(t, start)
    _, b = split(rest, end - start)
    return merge(a, b)

def line_start(t, line):
    if not 0 <= line <= lines(t): raise IndexError(line)
    if line == 0: return 0
    offset = 0
    while t:
        count = lines(t.left)
        if line <= count:
            t = t.left
        else:
            line -= count
            offset += size(t.left)
            if t.ch == '\n':
                line -= 1
                if line == 0: return offset + 1
            offset += 1
            t = t.right
    raise AssertionError('invalid aggregate')

def flatten(t):
    return flatten(t.left) + t.ch + flatten(t.right) if t else ''

t = insert(None, 0, 'ab\ncd')
t = insert(t, 2, 'X')
assert flatten(t) == 'abX\ncd' and line_start(t, 1) == 4
t = delete(t, 1, 4)
assert flatten(t) == 'acd'
```

Expected split/join and line lookup are O(log n); inserting m characters here builds nodes in O(m log m). The randomized tree has a worst-case linear depth, so use a deterministic balanced tree for strict latency bounds.

### The augmented-tree invariant

Every node's `size` equals the number of characters in its subtree, and `lines` equals its newline count. Splitting at offset n returns exactly the first n characters and the remainder while repairing those aggregates along the affected path. Insertion is split, construct the inserted subtree, then join three pieces. Deletion is two splits followed by a join that omits the removed middle. Neither operation needs to copy the unchanged suffix into a new flat string.

For `ab\ncd`, the second line starts after three code points. Inserting `X` before the newline changes that offset to four, which `line_start` derives from subtree counts rather than rescanning the text. Deleting across the newline updates both character and line aggregates, so later lookups remain consistent.

The demonstration's `flatten` function is a debugging convenience: recursive string concatenation can be much more expensive than an O(n) iterator that appends chunks and joins once. A production buffer also needs undo snapshots, newline conventions, and explicit offset units. A user-perceived character may contain multiple Unicode code points; correct tree indexing does not by itself implement grapheme-aware cursor movement.
