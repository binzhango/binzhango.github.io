## Question

Do the roofline maths: how many tokens/sec can one H100 produce for a 70B model at batch size 1?

## Brief answer

There is no valid single-H100 BF16 batch-one estimate for a 70B model without first checking memory: its roughly 140 GB of raw weights exceed an 80 GB device. With sufficiently compressed weights, a bandwidth bound gives only an optimistic ceiling.

## Detailed answer

For an illustrative 80 GB SXM H100 with about 3.35 TB/s peak memory bandwidth and idealized 35 GB four-bit weights, reading weights once per token gives roughly $3350/35\approx96$ tokens/s. Metadata, dequantization, KV traffic, kernels and imperfect bandwidth utilization lower this; long contexts lower it further. This is calculated, not measured. Other H100 variants differ. A compute roofline and actual quantized kernel benchmark are required before quoting deployment performance. The bandwidth and capacity assumptions use NVIDIA’s H100 SXM specifications, checked on 2026-09-20.

The roofline estimate is the minimum of a compute ceiling and a memory ceiling. For dense inference, a rough projection cost is $2N$ FLOPs per generated token, so 70B parameters imply about 140 GFLOPs before attention and other overhead. Divide effective compute throughput by that quantity to estimate the compute ceiling. Separately divide effective memory bandwidth by bytes read per token. The smaller limit controls only under the stated simplifications.

For the four-bit weight example, ideal arithmetic intensity from the weight matrices is approximately $140\text{ GFLOPs}/35\text{ GB}=4$ FLOPs per byte. This is low for a modern accelerator, explaining why peak tensor-core FLOPs are not the useful first estimate at batch size one. If effective bandwidth were 60% of the quoted peak and other traffic were ignored, the ceiling would fall from about 96 to about 57 tokens/s. That is an illustrative sensitivity calculation, not a benchmark.

A long KV history adds reads each decode step; quantization scales and unpacking add work; sampling and synchronization add latency. CPU offload changes the relevant bandwidth to the slower transfer path. First verify the complete model and cache fit, then profile the actual kernel path and compare measured tokens/s against the bound to identify how much performance is lost to each cause.
