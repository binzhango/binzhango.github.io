## Question

What’s the core idea behind adapter-tuning?

## Brief answer

A classic adapter projects hidden states down to a small bottleneck, applies a nonlinearity, projects back up, and adds a residual connection.

## Detailed answer

A schematic form is:

$$
h'=h+W_{\mathrm{up}}\phi(W_{\mathrm{down}}h+b_{\mathrm{down}})+b_{\mathrm{up}},
$$

where the bottleneck width $r$ is much smaller than model width $d$. The projection weights contribute about $2dr$ parameters. Placement and normalization vary by method. This nonlinear bottleneck module differs from LoRA's low-rank linear weight update, even though both are often loosely called “adapters.”

The down projection maps a $d$-dimensional hidden state to $r$ features; the nonlinearity creates a task-specific transformation in that smaller space; the up projection restores width $d$. The residual addition lets the module start close to the original function and learn a correction rather than replacing the whole representation. Initializing the added branch near zero is one way to preserve behavior at the start of adaptation.

For $d=768$ and $r=64$, the two projection matrices contain $2\times768\times64=98,304$ weights. Including the two biases adds $64+768=832$ parameters. This is the count for one module; inserting modules after multiple sublayers multiplies the total. Frozen backbone weights still occupy memory and take part in forward computation.

The nonlinearity makes the module different from a fixed low-rank linear update. In general, $W_{up}\phi(W_{down}h)$ cannot be folded into one existing linear matrix for all inputs. Placement affects which representations it transforms, and some methods also train normalization parameters. Document those choices and evaluate both task gains and runtime overhead rather than using “adapter” as if it named one universally identical architecture.
