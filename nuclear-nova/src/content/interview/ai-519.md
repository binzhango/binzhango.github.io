## Question

Design agent orchestration across dozens of connected SaaS systems. Where is authorization enforced, and why can it not live in the model?

## Brief answer

Enforce authorization at every connector's execution boundary using the actual user, resource, and requested operation. The orchestrator coordinates workflows, but neither its prompt nor the model's claimed role grants access. Recheck permissions immediately before writes because identity, resource state, and policy can change during a long plan.

## Detailed answer

**Suggested approach.** A central broker issues short-lived, audience-bound delegated credentials, while each connector validates its own source-system permissions and action constraints. The workflow stores typed steps, dependencies, approvals, and authoritative outcomes. Separate read, draft, send, delete, and administrative capabilities rather than exposing a universal API proxy.

Use durable state and idempotent actions for multi-system workflows; define compensations where atomic transactions are unavailable. Treat connector responses as untrusted input for planning and avoid letting them supply new authority. Audit who requested, approved, and executed each action. Test confused-deputy attacks, cross-tenant identifiers, stale approvals, partial completion, and revoked tokens. A model cannot be the authorization layer because probabilistic text interpretation does not reliably enforce policy invariants.

### Prevent the orchestrator from becoming a confused deputy

Suppose a user can read a sales record but cannot modify payroll. A CRM response containing a payroll employee ID must not cause the orchestrator to invoke a more privileged payroll connector on the user's behalf. Each step needs the original delegated actor, the target resource, and the requested operation. The connector rejects insufficient authority regardless of where the ID came from.

Represent a workflow as a durable graph with prerequisites and recorded outcomes. A completed read may support a later proposal, but it does not grant write permission. Approvals should reference the concrete action and relevant version, and long-running workflows must recheck revoked credentials before resuming.

Cross-system transactions need explicit partial-failure semantics. If creating a ticket succeeds but sending a notification fails, retrying the entire workflow can duplicate the ticket. Persist the completed step and retry only the notification with its own idempotency key. Some actions have compensations; others require human resolution. The model can plan and explain these paths, while trusted code enforces identity, state transitions, and authority at every boundary.
