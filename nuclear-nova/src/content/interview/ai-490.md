## Question

As a Deployed Engineer, you are rolling Devin into a 2,000-engineer organisation. What do the first ninety days look like?

## Brief answer

Start with a narrow, measured pilot and expand only after engineers can reliably review and trust the output. Establish repository access, security boundaries, task suitability, and baseline productivity before onboarding all 2,000 engineers. The ninety-day objective is a repeatable operating model with demonstrated value, not maximum account activation.

## Detailed answer

**Suggested approach.** In days 1–30, map workflows, select a few willing teams, configure isolated execution and scoped credentials, and create a task rubric with baseline completion/review times. Choose bounded maintenance and test tasks before complex ownership-sensitive changes. Train reviewers to inspect diffs and verification evidence.

In days 31–60, analyze failures, improve repository setup and task descriptions, and track accepted changes, review effort, regressions, and cost per useful task. Maintain an incident and escalation path. In days 61–90, expand to similar teams only where quality and support capacity hold; publish documented exclusions and ownership. Compare against a matched baseline or randomized rollout where feasible. Adoption without net time savings or safe behavior is not a successful deployment.

### Make expansion conditional on evidence

Select pilot tasks whose outcomes are reviewable, such as adding a missing regression test or fixing a bounded dependency issue. Record baseline engineer time from task start through accepted review, then include setup, prompting, review, and rework in the agent-assisted comparison. Measuring only the agent's coding interval can hide costs transferred to senior reviewers.

Create an operating owner for repository setup, access approval, incident handling, and failed-task triage. A team with unsupported build dependencies may need environment work before more licenses provide value. Keep exclusions explicit, such as production credential changes or poorly specified architectural migrations, until the pilot supplies evidence for expanding authority.

For the ninety-day decision, distinguish adoption, quality, and net benefit. High activation with low accepted delivery suggests onboarding or task-fit problems; high acceptance with frequent later regressions suggests verification problems. Expand first to teams with similar environments and task types, then rerun the measurement when those assumptions change. An organization-wide rollout is an operational change, not merely installing a tool for 2,000 accounts.
