## Question

Design a personalised feed ranking system with a two-stage candidate generation and ranking architecture.

## Brief answer

Suggested approach: retrieve a broad candidate set cheaply, rank a smaller set with richer features, then apply eligibility, diversity, and policy constraints before display. Separate relevance from engagement incentives and define the intended user value. Every stage needs exposure logging so training data reflects what users could actually see.

## Detailed answer

Candidate sources can include followed creators, collaborative neighbors, semantic retrieval, fresh content, and exploration. Deduplicate and enforce permissions before ranking. The ranker combines user/item embeddings, recency, context, and interaction features, with calibrated outputs for the chosen objectives.

Use a final reranker for diversity, repetition limits, safety, and freshness. Allocate latency budgets by stage and keep a fallback feed when feature services fail. Evaluate candidate recall, ranking quality, harmful recommendations, long-term satisfaction, and creator exposure. Time-based splits and online experiments reduce misleading offline gains. Include new users and content through content features and controlled exploration, and monitor feedback loops that repeatedly amplify already-popular items.

### Allocate work by candidate count

Candidate generation searches millions of items cheaply and returns hundreds or thousands using approximate neighbors, followed creators, and fresh-content pools. The heavier ranker then scores that bounded set with richer user–item interactions. A final reranker applies diversity, safety, availability, and repetition rules. This architecture spends expensive computation only where it can change the displayed list.

Measure recall of useful items at the candidate stage: no ranker can rescue an item never retrieved. Log source contributions so one generator does not silently dominate. For training, account for exposure and delayed outcomes; treating every unseen item as a negative teaches the old policy's limitations. Include exploration for new content and cold-start users, with bounded user cost. Cache stable features and define a fallback feed if real-time signals fail. Online tests should include long-term satisfaction and harmful-content exposure, because improving immediate clicks can worsen the experience or create a popularity feedback loop.
