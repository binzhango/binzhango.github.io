## Question

You inherit an 800-line pipeline script from a previous deployment. It's slow and occasionally produces wrong numbers. The original author is gone. Go.

## Brief answer

Freeze representative inputs and outputs, establish the intended data contracts with stakeholders, and reproduce incorrect cases before restructuring the 800-line script. Add observability around stages and profile realistic workloads. Preserve a working baseline so performance changes cannot quietly alter business meaning.

## Detailed answer

**Suggested approach.** Identify sources, joins, filters, units, time zones, deduplication rules, and output grain. Build small fixtures for known errors and reconcile totals with source systems. Common causes include join fanout, late-arriving data, mutable defaults, and inconsistent date boundaries. Instrument row counts and checksums between stages to localize divergence.

Once correctness is understood, separate pure transformations from I/O and configuration, then optimize the measured bottleneck. Use incremental processing, vectorized operations, or database pushdown only where semantics remain equivalent. Run old and new pipelines in parallel on held-out periods and review discrepancies. Add ownership, runbooks, and restart/idempotency behavior. A broad rewrite without a trusted oracle risks producing faster wrong numbers.

### Establish an oracle before refactoring

Ask the business owner what each output row means and which source totals it should reconcile to. Build a small fixture where an order has two lines and two supplier records; this can expose join fanout more clearly than a million-row production file. Record row counts, distinct keys, sums, and date boundaries after every transformation to locate the first incorrect stage.

Capture dependencies, environment, input versions, and run parameters so the failure is repeatable. Profile only after a correct reference case exists. If repeated per-row network calls dominate, batch or cache under a freshness contract; if a quadratic join dominates, use a proper keyed join without changing multiplicity. Extract pure transformations gradually, running fixtures and heldout-period reconciliation after each change. Define restart behavior so a crash cannot append duplicate output. The final handoff should include an owner, monitored invariants, and recovery instructions. Faster code is valuable only when its numbers retain the agreed business meaning.
