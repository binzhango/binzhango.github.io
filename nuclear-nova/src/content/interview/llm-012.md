## Question

Why is it problematic to adjust hyperparameters based on test set performance?

## Brief answer

Tuning on the test set leaks evaluation information into model selection and makes the reported result optimistically biased.

## Detailed answer

Even without taking gradients on test examples, choosing the best of many candidates using test scores adapts the system to that set. Tune on validation data and use the test set only after choices are settled. If extensive test-driven iteration has already happened, obtain a new independent holdout or explicitly report that the old test set became development data.

Model selection can exploit random noise in a score. Imagine 100 equally capable configurations evaluated on one small test set. Some will score higher by chance. Choosing the highest-scoring configuration and presenting that same number as independent evidence overstates expected performance, even though none of its weights was trained directly on test examples.

Leakage can also happen indirectly: editing prompts after reading failed test questions, selecting a retrieval configuration based on test answers, or retaining whichever checkpoint has the best test score. These choices all make the system depend on information from the test set.

Use a development set for iterative work and decide the metric, candidate selection procedure, and acceptance criteria before opening the final test. If a test uncovers a real bug, fixing it is appropriate, but the resulting system needs fresh independent evaluation for an unbiased final estimate. When new data is unavailable, disclose that the set has become development data and use cross-validation or uncertainty analysis without pretending it restores complete independence.
