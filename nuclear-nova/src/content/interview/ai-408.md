## Question

A compiler statically schedules every instruction and every chip-to-chip transfer. What does that compiler need to know that an NVCC-style compiler does not, and what breaks when its assumptions are wrong?

## Brief answer

A statically scheduled accelerator compiler may need a global model of operation timing, memory residency, communication routes, and resource conflicts across chips. A conventional GPU compiler also schedules instructions, but hardware/runtime mechanisms handle much dynamic warp and memory behavior. The contrast is where scheduling responsibility sits, not that GPU compilation knows nothing about timing.

## Detailed answer

The static system needs tensor shapes, layouts, dependencies, operator latencies, buffer lifetimes, link bandwidth and latency, and synchronization constraints. It assigns operations and transfers so data arrives before consumption and resources are not double-booked. Dynamic shapes or data-dependent routing require padding, multiple compiled schedules, or controlled runtime mechanisms.

If assumptions are wrong, the result can be a missed deadline, buffer overwrite, deadlock, or incorrect data consumption rather than merely lower utilization. Validate schedules in a cycle-aware simulator and test boundary conditions, congestion assumptions, and hardware faults. Groq's tensor-streaming architecture is a concrete example of compiler-managed scheduling; details differ across generations.

### Scheduling includes the network and storage lifetime

An ordinary GPU compiler maps kernels to an execution model in which hardware handles many runtime scheduling and memory-latency details. A fully static spatial schedule must assign where an operation runs, when its operands arrive, which buffer holds them, and when that buffer can be reused. A tensor transfer is therefore part of the dependency graph, not an incidental library call.

For example, if chip B consumes an activation at cycle t, the compiler must schedule chip A's production and transfer early enough under the supported latency contract. Reusing B's buffer one cycle too early can corrupt data. Variable message lengths, dynamic shapes, or expert routing require bounded schedules or explicit runtime support. Validate resource conflicts and timing in addition to functional tensor equations. If external inputs miss their planned slot, the runtime needs a defined stall, reschedule, or failure behavior; silently continuing on stale data is unacceptable. Static predictability is valuable only within its verified assumptions.
