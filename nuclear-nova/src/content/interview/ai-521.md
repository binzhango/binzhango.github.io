## Question

Glean's ranking leans on a knowledge graph of people, content and activity. How would you build that graph, and how does it improve retrieval beyond embedding similarity?

## Brief answer

Build a permission-aware graph linking people, teams, documents, projects, and observed activity with timestamps and provenance. Use it to add organizational context, authority, and relationship features to retrieval. Graph proximity supplements textual relevance; popularity or personal proximity alone should not override the user's actual question.

## Detailed answer

**Suggested approach.** Ingest explicit ownership, membership, links, mentions, and collaboration events as typed edges. Resolve identities carefully across SaaS systems and decay time-sensitive activity signals. At query time, use the authorized subgraph to expand project context or score a document's relationship to the user's task. Keep private edges from leaking through rankings, explanations, or counts.

Evaluate gains on queries with ambiguous project names, expert finding, and authoritative-document selection. Compare against lexical/dense baselines and ablate individual edge types. Watch feedback loops where already popular documents receive more exposure and activity. Audit stale ownership and incorrect entity merges. This is a proposed knowledge-graph ranking design, not a claim about the internals of a named enterprise-search product.

### Turn relationships into bounded ranking features

A graph might contain person-to-team membership, document-to-project association, document ownership, and explicit links between related artifacts. For a query about an ambiguous project name, the user's authorized team and recent task context can help distinguish two similarly named projects. An owned, current design document can rank above an abandoned draft even when their embedding similarity is close.

Treat every edge as a claim with source and time. An employee transfer invalidates some membership edges; a document rename does not necessarily change identity. Avoid merging people based only on names, because one incorrect identity link can spread both ranking errors and access leaks across the graph.

Evaluate a graph feature by removing it and comparing judged relevance on the queries it is supposed to help. Also inspect who loses exposure. Activity-based signals can create a feedback loop in which visible documents accumulate clicks and become even more visible. Use current authority and task relevance as explicit counterweights, and never let an unauthorized relationship reveal itself through a personalized explanation or a supposedly harmless count.
