## Question

Implement “top-k most frequent search queries” over a large query log, then tell me what breaks when the log becomes an unbounded stream across many machines.

## Brief answer

For a finite log, count queries exactly with a hash map and select the largest k counts with a heap. This uses memory proportional to distinct queries, not log length. For an unbounded distributed stream, define a time window and use partitioned counting or bounded-memory heavy-hitter sketches; exact lifetime counts over an unbounded key space cannot have fixed memory.

## Detailed answer

This implementation preserves query strings exactly and breaks ties lexicographically. Normalization, privacy filtering, and bot removal are separate product decisions.

```python
from collections import Counter
from heapq import nsmallest

def top_queries(queries, k):
    if k < 0:
        raise ValueError("k must be nonnegative")
    counts = Counter(queries)
    return nsmallest(k, counts.items(), key=lambda item: (-item[1], item[0]))

assert top_queries(["b", "a", "b", "a", "c"], 2) == [("a", 2), ("b", 2)]
assert top_queries([], 3) == []
assert top_queries(["x"], 0) == []
assert top_queries(["x"], 9) == [("x", 1)]
```

For $N$ events and $U$ distinct strings, counting is expected $O(N)$ and heap selection $O(U\log k)$ for small k. At scale, partition by query and aggregate counts with event IDs or replay-safe offsets. Local top-k lists alone can miss globally frequent keys spread across partitions. Address hot keys, late events, deletion requests, and window expiration explicitly. Approximate sketches require stated error bounds and a candidate-key mechanism.

### Why local top-k can be wrong

Imagine two partitions: the first has A=100 and X=99; the second has B=100 and X=99. Each partition's local top-one omits X, yet X is globally first with 198 occurrences. Exact distributed aggregation must combine counts by key before selecting the final top-k, or retain enough candidates under a proved approximation scheme.

For a large finite log, external aggregation can spill sorted key/count runs to disk, merge counts, then maintain a heap of k winners. This trades I/O for bounded working memory without changing the exact result. For continuous traffic, define whether “most frequent” means lifetime, last hour, or event-time day. Window expiration, late events, duplicated deliveries, and hot keys alter the design. Normalizing case or whitespace merges distinct strings intentionally; apply and version that policy before counting. Test all-equal counts, k larger than unique keys, a dominant hot key, and nearly uniform data where approximate ranks are uncertain.
