## Question

Design an agent that operates a web browser to complete multi-step tasks. How do you make it reliable enough to ship?

## Brief answer

Suggested approach: use an observe–act–verify loop with constrained browser tools, explicit task state, and independent permission checks. Prefer stable semantic elements where available, refresh observations after page changes, and verify the final outcome from the application. Reliability comes from recovery and bounded behavior, not from a longer precomputed click plan.

## Detailed answer

Represent actions as typed operations with target identity, expected state, deadline, and side-effect classification. Track subgoals and detect loops, stale elements, redirects, and navigation failures. Re-read before submitting forms that may have changed. Use domain allowlists and keep credentials outside the model context.

Treat webpage content as untrusted instructions. Require authorization for purchases, messages, or destructive operations and handle confirmation pages carefully to avoid duplicate submissions. Test pop-ups, slow loads, localization, session expiry, and unexpected dialogs. Measure end-to-end completion, unintended actions, recovery rate, intervention rate, and cost over repeated runs. Escalate ambiguous or unsupported tasks with the observed blocker instead of fabricating success.

### Use an observe–act–verify loop

For a form-submission task, first read the current page and identify the actual field labels and available options. Build a typed action plan, fill one logical section, and verify the rendered values before submitting. The postcondition might be a receipt number or a saved record visible through the application, not simply the absence of an error dialog.

Persist the latest observation, subgoal, and confirmed side effects. A stale element after navigation should trigger a fresh observation, not a guessed coordinate. When submission times out, inspect the application's status before retrying to avoid duplicate orders or messages. Keep task-specific credentials and browser sessions isolated, and restrict destinations and tools according to the user's authorization. Recovery should have a budget: after repeated uncertain observations, explain the specific blocker and let a human resolve it. Test with fault injection so reliability includes delayed responses, redirects, and unexpected dialogs rather than only the ideal path.
