## Question

A new frontier model is released and scores better on your benchmarks. What happens before it reaches customers?

## Brief answer

A better benchmark score starts evaluation; it does not authorize an automatic production swap. Pin the new version, verify interface and policy compatibility, replay representative workflows, and compare failure severity, latency, cost, and reviewer effort. Roll out through a reversible canary after the model meets the product's actual acceptance criteria.

## Detailed answer

Run held-out tasks including long documents, contradictory evidence, citations, structured outputs, and required abstention. Inspect paired outputs blindly and test tool-call schemas, context limits, refusal behavior, and document-format preservation. Recalibrate automated judges so a changed writing style is not mistaken for improved quality.

Use shadow traffic where permitted, then a small cohort with monitoring and a rollback switch. Retain versioned prompts and evidence so customer reports can be reproduced. Update routing only after measuring total workflow cost, including retries and human corrections. Communicate material behavior changes to users who depend on stable outputs. A model that improves general reasoning but misses more critical clauses should fail the relevant release gate despite its aggregate benchmark gain.

### Upgrade the workflow contract, not just the model ID

A model change can alter tool arguments, citation syntax, refusal behavior, answer length, and the probability of obeying document-borne instructions. Freeze the surrounding workflow while comparing versions so the observed difference is attributable. Then test any prompt or parser adaptation as a separate change, using a held-out set that was not used to tune the adaptation.

Inspect paired failures, including cases the old model handled correctly. An average improvement can conceal a new error in a rare but critical contract type. Define release gates around those categories, schema validity, unsupported assertions, and reviewer effort, with uncertainty intervals where sample sizes are small.

A shadow deployment exercises realistic inputs without changing customer-visible output. A canary then limits exposure and provides a rollback path with the previous model and prompt still available. Preserve immutable input and artifact versions for reproducibility, subject to the customer's retention policy. Rollback is useful only if downstream formats and stored state remain compatible, so include that compatibility in the release rehearsal.
