## Question

A prospective customer runs their workload on H100s. Talk me through when you would tell them not to move.

## Brief answer

Suggested approach: Recommend staying on H100s when the existing system meets requirements more economically after realistic migration costs, or when the alternative lacks needed models, operators, context support, availability, or operational tooling. A new accelerator's best-case decode speed does not establish value for compute-heavy prefill, training, or highly variable workloads.

## Detailed answer

Profile the customer's traffic and identify the actual bottleneck. If it is retrieval, network, application code, or low utilization, changing accelerators may add complexity without solving it. Compare complete-task cost and latency at equal quality and SLOs, including quantization differences, long contexts, batching, and redundancy.

Include porting, compiler constraints, lock-in, debugging, monitoring, staff expertise, and supply commitments. Run a reproducible proof of value on representative traces and preserve a rollback path. A hybrid deployment may be preferable for a specific low-latency segment. State the cases where the alternative loses as clearly as where it wins; trustworthy technical advice is more useful than forcing a migration.

### A no-migration recommendation can be precise

A customer with large offline batches, mature GPU kernels, acceptable latency, and high utilization may gain little from hardware optimized for small-batch latency. Another may depend on unsupported operators or rapidly changing models, making compiler and porting costs dominant. Long-context memory requirements and existing capacity commitments can also make migration unattractive.

Build a comparison table using the customer's actual request mix, quality target, p99 SLO, availability requirement, and annual operating effort. Include migration engineering and fallback capacity, not just accelerator hourly cost. Run the same tasks with identical output constraints and quantify uncertainty. If only a narrow interactive tier benefits, propose routing that tier separately and retain GPUs for the rest. Establish success and stop criteria before the trial so the outcome is credible either way. The recommendation should explain the mechanism behind a gain or loss and identify what future workload change would justify revisiting it.
