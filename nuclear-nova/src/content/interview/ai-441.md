## Question

Design an RL environment for booking a multi-city trip in a web travel app. Specify the reward and how to prevent reward hacking.

## Brief answer

Build a reproducible travel sandbox with realistic search, inventory, prices, time zones, and booking state. Reward a valid itinerary satisfying the user's constraints and a confirmed sandbox booking, with explicit penalties for unauthorized spending or changes. Derive the reward from trusted backend state rather than screenshots, model claims, or user-editable confirmation text.

## Detailed answer

**Suggested approach.** Randomize cities, travel dates, layover limits, budgets, passenger details, and inventory changes. Use a fake payment instrument and reversible bookings. The terminal validator checks every segment, connection feasibility, traveler identity, currency, total cost, and confirmation requirement. In a task requiring user approval, purchasing before that approval is a hard failure even if the itinerary is otherwise correct.

Give small bounded shaping rewards for verified progress, such as finding a feasible itinerary; ensure repeated searches cannot accumulate more reward than completion. Isolate reward services from browser access and hide evaluation seeds. Adversarially test DOM editing, URL guessing, duplicate bookings, stale fares, and forged receipts. Track valid completion, unauthorized actions, wasted calls, and robustness to site changes. Hold out routes and page layouts so the policy must learn the task rather than a memorized click sequence.

### Define an episode and its invariant

An episode starts with a user itinerary request and a seeded inventory snapshot. The observation includes the page and authorized task state; actions include search, selecting a fare, entering permitted traveler information, requesting approval, and committing a reservation. Inventory can change between selection and commitment, so a successful policy must revalidate price and availability rather than memorize a happy path.

Use a lexicographic success rule: first reject unauthorized purchase, wrong traveler, or invalid connections; only among valid completed bookings reward lower cost and fewer actions. A scalar weighted sum alone can accidentally make a cheap unauthorized booking worth more than an authorized expensive one. If shaping is used, give credit for state changes such as obtaining a valid quote, not repeated clicks on a search button.

For example, an itinerary with two cheap flights fails if the second departs before the first arrives in the correct time zone. A screenshot saying “confirmed” also fails without the corresponding reservation in the sandbox ledger. Hold out both constraint combinations and interface layouts to distinguish learning travel rules from memorizing routes or page coordinates.
