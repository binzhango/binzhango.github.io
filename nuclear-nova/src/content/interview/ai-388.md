## Question

How do you design a feature store, and what causes training/serving skew?

## Brief answer

Suggested approach: define versioned features once, materialize historical values for training and fresh values for low-latency serving, and enforce entity/time semantics. Training-serving skew arises when transformations, freshness, defaults, joins, or available information differ. A feature store helps manage these contracts but does not automatically make every historical join leakage-free.

## Detailed answer

Use a registry containing entity keys, schema, ownership, transformation version, freshness target, and null policy. Maintain offline history and an online store, with validation and lineage connecting them. Construct training rows from feature values that were available at prediction time, not merely events whose timestamps precede it; late-arriving corrections can otherwise leak future knowledge.

Monitor missing rates, staleness, distributions, and sampled online/offline parity. Version breaking changes, backfill safely, and define fallback behavior when a feature is unavailable. Avoid duplicating transformation logic in separate languages without equivalence tests. Feast documents event-time point-in-time joins; actual availability-time requirements need explicit handling.

### Reproduce what the model knew then

Suppose a fraud decision occurred at 10:00 and a transaction from 09:59 arrived in storage at 10:05. A training join based only on event time would include information unavailable during the original decision. Store availability/ingestion timing where needed, and reconstruct the feature values actually accessible at prediction time.

A feature definition includes the entity key, transformation, window, type, default, freshness requirement, and version. Batch jobs maintain historical values for training; stream or online computation updates low-latency serving values. Reuse transformation code where practical and run parity tests on captured inputs. Skew can arise from different time zones, missing-value defaults, rounding, aggregation windows, or stale online materialization even when column names match. When a feature is stale, the service should apply a defined fallback or reject the prediction rather than silently changing semantics. Monitor freshness and missingness by cohort and tie every model version to the feature contract it expects.
