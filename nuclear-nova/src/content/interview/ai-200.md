## Question

Your pretraining loss suddenly diverges at step 300k of a long run. Diagnose and fix it.

## Brief answer

Preserve the failing batch, checkpoint and telemetry before changing anything. Determine whether the spike is a logging artifact, a bad batch, numerical overflow, optimizer instability or hardware/distributed corruption. Reproduce from the last known-good checkpoint with controlled changes; blindly lowering the learning rate can hide the cause and waste a costly run.

## Detailed answer

Inspect loss by data source, token counts, sequence length, gradient norms, activation ranges, optimizer moments and nonfinite values. Check recent changes in the learning-rate schedule, data mixture, checkpoint restore and precision settings. Compare ranks to distinguish a global issue from one device or shard.

Replay the offending batch on a small controlled configuration and, if useful, higher precision. Test whether the problem follows the data, the checkpoint or the hardware. Outlier sequences, malformed labels and accidental all-padding batches can create failures that ordinary average metrics obscure.

Resume only after a bounded experiment demonstrates stability and comparable learning progress. Quarantine bad data with an audit trail, replace suspect hardware or adjust the identified numerical path. Record lost useful steps and checkpoint recovery time so the next incident has a shorter diagnosis path.

Classify the first nonfinite or abnormal tensor in the computation graph. If activations become nonfinite before the loss, inspect input lengths, normalization and precision scales. If activations are finite but gradients explode, inspect the loss mask, learning-rate transition and optimizer state. A single rank diverging while peers remain normal suggests a shard, data or hardware-specific cause rather than a global hyperparameter problem.

Keep the offending batch and RNG/data-loader state so the failure can be replayed. Compare the same checkpoint and batch on known-good hardware or a higher-precision path. Change one factor at a time; a restart that happens to skip the bad batch is not evidence of a fix.

After correction, run enough controlled steps to show stable gradients and comparable loss behavior, then resume from a verified checkpoint. Record whether skipped data or optimizer resets change the training trajectory. Good incident handling preserves evidence and reduces lost useful compute instead of masking the symptom with a broad learning-rate reduction.
