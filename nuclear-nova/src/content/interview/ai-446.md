## Question

An eval pipeline you own suddenly reports a 6-point drop for a customer's model between Tuesday and Wednesday. The model didn't change. Debug it.

## Brief answer

Freeze the evidence and compare Tuesday and Wednesday at every boundary: sampled tasks, data versions, prompts, retrieval results, tool environment, judge, scoring code, and infrastructure. “The model did not change” rules out only one component. Reproduce both runs against an immutable test set before attributing a six-point change to capability.

## Detailed answer

Start with denominators and confidence intervals: did six percentage points come from a small or differently weighted sample? Compare missing results, retries, parsing failures, truncation, and timeout handling. Replay identical requests with fixed decoding settings where possible; hosted aliases, routing, and numerical nondeterminism still need checking. Examine judge prompts and thresholds independently from the model under test.

Diff failing task traces to find a shared signature, then bisect recent harness, dependency, connector, and retrieval-index changes. Run a known baseline model through both environments: a shared drop suggests an evaluation-system regression. Notify the customer with verified scope, not an untested explanation. Restore the last reliable measurement pipeline, rerun affected reports, and add a regression fixture for the discovered failure.

### Use a small cross-over experiment

Run the old and new evaluation harnesses against the same saved model outputs. If the score changes, the regression is in scoring, parsing, weighting, or judging rather than generation. Next generate fresh outputs in both environments from the same frozen inputs. If only fresh outputs regress, inspect prompt construction, retrieval, inference configuration, network failures, and any unpinned provider endpoint. This separates components without changing everything at once.

For example, Tuesday may count 940 successful completions out of 1,000 assessed tasks, while Wednesday retains 1,000 in the denominator but marks 60 newly timed-out requests as wrong. The six-point drop then has an operational cause even though successful model responses have unchanged quality. Conversely, silently excluding those timeouts would inflate the apparent capability score. Report both service completion and conditional answer accuracy.

After locating the cause, rerun the historical baseline through the repaired pipeline and retain the original reports with a correction note. Save one minimal failing input, the expected intermediate representation, and the expected score. That fixture protects the measurement contract rather than merely asserting that the aggregate returns to its old number.
