## Question

What do output parsers validate, and what do they not validate?

## Brief answer

Output parsers convert model responses into application types and report format errors; they do not establish that the content is true.

## Detailed answer

A parser might validate JSON fields, types, or an enum. Prefer a model/provider's supported structured-output mechanism when suitable, then validate the returned object and domain constraints. Decide whether malformed output should trigger a bounded retry, repair, or user-visible failure. A syntactically valid amount or citation can still be wrong.

Validation has layers. JSON parsing establishes syntactic structure. A schema can establish that `amount` is numeric and `currency` is one of the allowed strings. Domain checks can establish that an end date follows a start date or that a cited source ID exists. None of those checks proves that the amount was copied correctly from the invoice or that the source supports the claim.

For an extraction workflow, return both the parsed value and evidence coordinates or source text where feasible. Compare critical fields against that evidence, and use deterministic arithmetic for totals. If the model returns a well-formed but unsupported value, retrying the parser cannot fix the underlying grounding error.

Decide failure behavior before deployment. A malformed response might receive one repair attempt with the validation error; repeated failure should produce a controlled application error rather than an unbounded loop. Do not silently coerce ambiguous values such as “1,200” without a locale policy. Structured-output support can reduce formatting failures, but correctness, permission checks, and action authorization still belong to the application.
