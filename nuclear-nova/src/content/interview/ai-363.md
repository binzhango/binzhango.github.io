## Question

A model runs fine in FP32 but produces garbage after conversion to FP16. Debug it.

## Brief answer

Find the first layer or operation where FP16 diverges from the FP32 reference, rather than inspecting only final output. Common causes include overflow, underflow, unstable reductions, incorrect casts, incompatible kernels, and conversion mistakes. FP16's limited exponent range differs from BF16; a model trained in BF16 may contain values that FP16 cannot represent safely.

## Detailed answer

Fix input tokens, seed, decoding settings, and model revision. Compare intermediate activations and logits layer by layer, checking maxima, minima, non-finite values, and relative error. Verify that weights, normalization epsilon, masks, and attention scaling were converted correctly and that no parameters were dropped or reordered.

Keep sensitive reductions, normalization, and softmax in FP32 where appropriate, use stable algorithms, and test BF16 if supported. For training, loss scaling addresses small gradients but does not fix forward overflow. Inspect custom kernels and fused paths separately from the reference implementation. Validate recovery across representative prompts and long contexts; one repaired example does not establish numerical stability. Record the smallest precision exceptions needed rather than reverting everything blindly.

### FP16 changes range as well as precision

FP16's largest finite value is 65,504, so a finite FP32 activation can overflow on conversion or during a product. BF16 has an exponent range similar to FP32 but fewer significand bits, which can help overflow while introducing different rounding error. Underflow can also erase small values. A model that is “the same weights at lower precision” is not numerically identical.

Find the earliest divergence, not only the final nonsense output. Run one fixed batch through a reference path and the converted path, comparing inputs, projection outputs, attention logits, normalization, and final logits. Disable fused kernels selectively to distinguish a precision issue from an implementation bug. Keep accumulations and sensitive operations at adequate precision, then re-enable optimizations one at a time. For training, dynamic loss scaling protects small gradients but cannot repair forward activations already at infinity. Test long contexts and extreme inputs because ordinary short prompts may never exercise the failing numerical range.
