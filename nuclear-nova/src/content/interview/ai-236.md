## Question

Build an in-memory key-value store with SET/GET/DELETE, then add transactions with BEGIN/COMMIT/ROLLBACK, including nested transactions.

## Brief answer

Represent each open transaction as a write overlay, including tombstones for deletes. Reads search overlays from newest to oldest; committing a nested transaction merges into its parent, while rollback discards only the newest overlay.

## Detailed answer

This Python implementation defines missing-key reads as `KeyError`, deletes as idempotent, and commit/rollback without a transaction as errors. It provides nested savepoint-like behavior for one process, not concurrent database isolation.

```python
class KVStore:
    _deleted = object()

    def __init__(self):
        self.layers = [{}]  # committed base, then open overlays

    def get(self, key):
        for layer in reversed(self.layers):
            if key in layer:
                if layer[key] is self._deleted:
                    raise KeyError(key)
                return layer[key]
        raise KeyError(key)

    def set(self, key, value):
        self.layers[-1][key] = value

    def delete(self, key):
        if len(self.layers) == 1:
            self.layers[0].pop(key, None)
        else:
            self.layers[-1][key] = self._deleted

    def begin(self):
        self.layers.append({})

    def commit(self):
        if len(self.layers) == 1:
            raise RuntimeError('no transaction')
        child = self.layers.pop()
        parent = self.layers[-1]
        for key, value in child.items():
            if len(self.layers) == 1 and value is self._deleted:
                parent.pop(key, None)
            else:
                parent[key] = value

    def rollback(self):
        if len(self.layers) == 1:
            raise RuntimeError('no transaction')
        self.layers.pop()

store = KVStore()
store.set('x', 1)
store.begin()
store.set('x', 2)
store.begin()
store.delete('x')
store.commit()
try:
    store.get('x')
    raise AssertionError('deleted value must be hidden')
except KeyError:
    pass
store.rollback()
assert store.get('x') == 1
```

A read is expected O(d) dictionary lookups at transaction depth d; a write is expected O(1). Commit costs O(w) for the newest overlay's w changed keys. Memory stores the base plus outstanding writes. Copying mutable values or prohibiting external mutation is necessary if rollback must undo in-place changes to stored objects. Test empty transactions, repeated deletes, nested commit followed by outer rollback and error cases. Durable storage and concurrent clients require a separate logging/conflict-control design.

### Nested commits are still provisional

Start with committed x=1. An outer transaction writes x=2, then an inner transaction deletes x. Reads must see the inner tombstone and report absence. Committing the inner transaction merges that tombstone into the outer overlay; it does not change the committed base. Rolling back the outer transaction therefore restores x=1, exactly as the test demonstrates.

A tombstone differs from removing a key from an overlay: removing it would expose an older value and make deletion ineffective. Writes overwrite only the newest layer, so rollback needs no inverse operations. Empty transactions and repeated deletes are safe under the defined contract. Mutable stored objects remain a caveat: changing a list obtained by `get` bypasses the overlay, so copy values or restrict them if isolation from in-place mutation is required. Multiple clients also need conflict/isolation rules and atomic commit; this single-process example does not provide durability or concurrent database semantics.
