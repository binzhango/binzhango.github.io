## Question

Build a rate limiter. Every ten minutes I add a requirement: per-tenant limits, burst allowances, then a sliding window. How do you keep the code from collapsing?

## Brief answer

Keep admission policy behind a small `allow(tenant, timestamp, cost)` interface. Separate tenant configuration, clock, state storage and algorithm. Token buckets model bursts; exact sliding windows model a count over a recent interval. They enforce different promises, so replacing one with another requires a stated contract change and boundary tests.

## Detailed answer

The following exact sliding-window implementation is an illustrative final requirement. Each tenant has a deque of accepted request timestamps; timestamps must be monotonic per tenant.

```python
from collections import defaultdict, deque

class SlidingLimiter:
    def __init__(self, limits, window):
        if window <= 0 or any(n <= 0 for n in limits.values()): raise ValueError('invalid limits')
        self.limits, self.window = limits, window
        self.events, self.last = defaultdict(deque), {}
    def allow(self, tenant, now):
        if tenant not in self.limits: raise KeyError(tenant)
        if now < self.last.get(tenant, now): raise ValueError('clock moved backward')
        self.last[tenant] = now
        q = self.events[tenant]
        while q and q[0] <= now-self.window: q.popleft()
        if len(q) >= self.limits[tenant]: return False
        q.append(now); return True

l = SlidingLimiter({'a':2, 'b':1}, 10)
assert l.allow('a',0) and l.allow('a',1) and not l.allow('a',2)
assert l.allow('b',2) and l.allow('a',10)
```

Operations are amortized O(1), with memory proportional to accepted events in the active windows. Add a lock or atomic datastore transaction around prune/check/append. Keep tests for previous requirements and distinguish burst allowance from a larger long-window quota; many APIs enforce both simultaneously.

Changing requirements should modify a policy component, not force every caller to know the algorithm's storage details. Keep tenant configuration immutable or versioned, inject the clock for tests, and give the store one atomic admission operation. This allows a local deque to be replaced with a distributed transaction without changing the request-facing contract.

The sliding window admits at most the configured count in $(now-window,now]$. At time ten in the example, the event at zero leaves the window, freeing capacity. A token bucket instead allows a burst followed by gradual refill; it can permit a different pattern over the same ten seconds. Treat switching between them as a product-policy decision rather than an internal refactor.

If both burst and long-window constraints apply, check and debit them atomically so a failure in one does not consume the other. Test tenant isolation, boundary timestamps, configuration changes and backward time. Exact windows retain each accepted event, so high-rate tenants may require bucketed approximations with documented error. Keep those approximations separate from the exact reference and quantify the allowed overshoot.
