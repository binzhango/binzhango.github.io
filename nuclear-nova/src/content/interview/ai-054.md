## Question

Design human-in-the-loop approval for an agent that takes consequential actions.

## Brief answer

Separate proposal from execution. Present the exact consequential action, affected resources and meaningful consequences for approval, then bind that approval to the reviewed payload and current authorization state.

## Detailed answer

Store a hash or version of the proposal with the approval; changing the recipient, amount, scope or material content invalidates it. Recheck permissions and relevant state immediately before execution. Use idempotency and an execution ledger so resuming after a crash cannot repeat an approved write. Handle rejection, expiration and cancellation explicitly. The model cannot approve its own proposal or infer approval from silence.

Approval should refer to a reviewable artifact, not a vague plan such as “let the agent handle purchases.” Show the exact recipient, item, quantity, price and source account for a purchase, plus any material side effects. Bind the approval to a canonical payload hash or immutable proposal version and an expiration time.

The execution worker verifies the approval, current permissions and relevant preconditions immediately before acting. If the price or recipient changes, the prior approval no longer covers the new action. A conditional write or fresh status check can prevent a stale proposal from modifying a resource that another user changed after review. Persist the execution result under the same logical action ID so a restart cannot create a second purchase.

Design explicit paths for reject, edit, expire and cancel. An edited proposal returns to review; silence is not approval. Low-risk preparatory work such as calculating totals or producing a draft can happen before the confirmation step, making the user's decision concrete. Measure approval abandonment and correction rates as well as blocked unsafe actions: a system that asks constantly for vague approvals trains users to click through without understanding the consequences.
