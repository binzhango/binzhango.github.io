## Question

Design an LLM agent that files and updates work orders in a customer's ERP: real writes to a production system. How do you make that safe?

## Brief answer

Expose narrow, typed ERP actions behind an authorization and policy service, with previews, approval where required, idempotency, and transaction reconciliation. The agent proposes work-order changes; the trusted service validates business rules and executes them. A fluent success message must follow an authoritative ERP receipt.

## Detailed answer

**Suggested approach.** Resolve asset, location, priority, required parts, and assignee using current master data. Present the exact create/update diff and bind approval to that version. Recheck permissions and record state at commit, using optimistic concurrency to avoid overwriting another operator's update. Keep a ledger of request, approval, execution, and result IDs.

Start in read-only or draft mode, then canary low-risk reversible operations. Test duplicate retries, stale records, unavailable inventory, partial ERP outages, and timeouts after commit. Define compensating or manual recovery procedures where rollback is impossible. Measure wrong-asset writes, duplicates, policy violations, and operator review effort. Never give the model a broad database credential merely to simplify integration.

### Treat a write as a transaction with evidence

For “raise a work order for locomotive 42's compressor,” resolve the actual asset ID, verify the fault evidence, select an allowed priority, and construct a proposed record. Present the concrete diff if approval is required. Bind that approval to the record version and parameters so a later replan cannot silently execute a different write.

The executor checks current role, asset state, and required fields, then sends an idempotency key to the ERP or maintains an equivalent transaction ledger. A timeout leaves the outcome unknown: query by request ID before retrying. Updates use optimistic concurrency so a technician's intervening change is not overwritten. Store authoritative ERP receipts and distinguish submitted from confirmed state. Test partial outages, stale approvals, duplicate requests, wrong asset resolution, and revoked permissions. Roll out a bounded reversible workflow first and measure wrong-target writes and recovery time. Model/prompt rollback cannot undo an external production write; compensation and human repair must be designed separately.
