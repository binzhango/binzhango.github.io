## Question

Serving a custom completion model to millions of DAU: walk me through the inference-cost model and your top three levers.

## Brief answer

Model cost from accelerator-seconds, utilization, input/output lengths, KV memory, and supporting infrastructure, then divide by successful useful completions. Millions of daily users do not determine capacity without request frequency, burstiness, and token distributions. The first levers are reducing unnecessary work, improving serving utilization, and choosing an adequate smaller model.

## Detailed answer

For an illustrative workload of two million users making ten requests daily, there are 20 million requests/day, about 231 requests/second on average before burst headroom. If each generates 100 tokens, output demand averages roughly 23,100 tokens/second. Measure sustainable throughput on the actual hardware and latency target rather than dividing by an advertised peak.

First reduce prompt and output waste with retrieval, cancellation, and safe prefix caching. Second improve batching and model placement while monitoring p95 latency. Third use distillation, quantization, or routing to a smaller completion model, gated by acceptance and edit quality. Include idle capacity, retries, storage, networking, and rejected suggestions in cost. A cheaper token is not cheaper productivity if users reject more completions or spend time correcting them.

### Convert workload into a fleet estimate

Suppose load tests show one replica sustains 1,000 generated tokens per second while meeting the target latency for the actual input lengths. The illustrative average demand of 23,100 tokens per second needs at least 24 replicas on output throughput alone. A three-times traffic peak raises that lower bound to 70 replicas before resilience headroom. Prefill compute, memory pressure, and uneven placement can require more, so this is a sizing component rather than a complete capacity answer.

Compute cost per useful completion as total serving cost divided by completions that actually help users. If half of speculative suggestions are canceled or rejected, their compute still belongs in the numerator. A smaller model that doubles throughput but sharply lowers useful acceptance may produce no economic gain.

Prioritize cancellation and context trimming when work is wasted, scheduling and batching when accelerators are underutilized, and model compression or routing when model compute remains dominant. Measure each change at a fixed user-quality threshold. Prefix caching helps only with repeated compatible prefixes, and larger batches help throughput only while queueing and memory remain within the interactive latency budget.
