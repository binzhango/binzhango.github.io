## Question

Walk me through writing a finished note back into Epic. What goes wrong?

## Brief answer

Use the customer's supported Epic integration and note workflow, bind every write to the verified patient and encounter, and preserve draft versus signed status. Write-back is a stateful integration operation, not a generic “save text” call. Exact APIs and permissions must be confirmed in that customer's configured environment.

## Detailed answer

**Suggested approach.** Validate encounter identity, author attribution, note type, and version, then submit an idempotent draft with provenance. Reconcile the returned record ID and status by reading it back. Handle stale versions and clinician edits with conflict detection rather than overwriting. Do not assume that a standard resource guarantees a particular vendor endpoint supports creating that note.

Failure cases include expired authorization, closed encounters, formatting loss, duplicate retries, wrong chart selection, unavailable fields, and an acknowledgment lost after commit. Queue recoverable failures with clear user-visible state and escalate ambiguous ones. Test in the approved nonproduction environment with representative note structures. Measure correct-chart write rate, duplicates, latency, and clinician review burden; successful HTTP status alone is insufficient.

### Treat write-back as a customer-specific integration contract

Before coding, establish which supported interface the deployment exposes, the permitted resource or document types, the required scopes, and whether a write creates a draft, an inbox item, or an immediately visible record. Do not infer those semantics from the existence of a generic FHIR endpoint. Verify them in the customer's test environment with integration owners.

Bind the draft to an explicitly selected patient and encounter. Include a stable external operation identifier where supported and maintain an application-side ledger of requests and outcomes. If the connection drops after submission, look up the created artifact or reconcile through the agreed integration mechanism before retrying. A transport error does not prove the EHR rejected the write.

Handle concurrent clinician edits with version checks or an equivalent supported workflow. The application should not overwrite a newer signed or edited document with an older generated draft. Present conflicts for review and preserve both versions as appropriate.

Acceptance tests should cover wrong encounter context, expired authorization, duplicate submission, unsupported document status, and a response lost after a successful write. Monitor end-to-end artifact availability, not just HTTP success. The user-facing confirmation should identify what was actually created and whether further clinician action remains required.
