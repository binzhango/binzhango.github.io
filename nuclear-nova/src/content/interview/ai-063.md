## Question

Prompting, RAG or fine-tuning: give me your decision framework with cost and latency attached.

## Brief answer

Use prompting for instructions and output format, RAG for changing or attributable knowledge, and fine-tuning for repeated behavioral or task adaptation that prompting does not solve. Combine them when the error analysis supports it.

## Detailed answer

First build an evaluated baseline and classify errors: missing evidence, poor retrieval, wrong behavior or insufficient capability. RAG adds indexing and retrieval latency but avoids retraining for every document update. Fine-tuning adds dataset, training and maintenance cost and does not ensure freshness. Prompting is inexpensive to develop but large demonstrations raise per-request token cost. Compare total cost per successful task at the required latency and quality, including ongoing updates.

Use the failure mode to choose the intervention. If the model knows the material but ignores the requested format, improve instructions and examples first. If it lacks current or private facts, retrieval or a structured tool provides evidence. If it repeatedly fails a stable task despite good evidence and a carefully evaluated prompt, supervised adaptation may be justified. Fine-tuning should not be used as a substitute for a permission-aware source of truth.

Compare costs over the expected request volume. A longer few-shot prompt has little setup cost but adds tokens on every call. RAG adds ingestion, storage, retrieval and context tokens while allowing document updates without retraining. Fine-tuning adds data preparation, training and release validation; it may shorten prompts or enable a smaller model afterward. Include ongoing maintenance, not just the first experiment.

For example, a policy assistant can retrieve current policy passages while a small adapter teaches citation format and abstention behavior. A fixed classification task with stable labels may benefit more from tuning than from a vector database. Establish a baseline, label a representative error sample, and run the smallest experiment that tests the suspected cause. Select by cost per successful task within latency and quality limits, since cheaper calls that require repeated retries may be more expensive overall.
