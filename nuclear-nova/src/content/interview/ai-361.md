## Question

Here's a CUDA kernel that's 10x slower than expected. Without running it, what are the usual suspects, and how do you confirm each?

## Brief answer

Treat static inspection as hypothesis generation: poor memory coalescing, low occupancy, register spills, divergence, serialization, excessive launches, or the wrong precision/kernel path are common causes. Confirm each with profiling and a correctness baseline. A kernel that looks inefficient may be limited elsewhere, and high occupancy alone does not guarantee high performance.

## Detailed answer

Inspect address patterns across warp lanes and estimate bytes moved per useful operation. Check launch dimensions, synchronization, atomics, shared-memory bank conflicts, and accidental host/device transfers. Large per-thread state can spill to local memory; too little parallel work can leave most multiprocessors idle.

Use CUDA events with warmup and explicit synchronization for timing, then Nsight Systems for gaps and transfers and Nsight Compute for memory throughput, stalls, occupancy, and instruction mix. Compare against a roofline estimate and a library implementation. Change one mechanism at a time and rerun numerical tests.

### Use a bottleneck hypothesis for each symptom

If neighboring warp lanes read far-apart addresses, memory transactions fetch many unused bytes; coalescing should improve effective bandwidth. If registers spill, local-memory traffic rises; reduce live values or change launch geometry and inspect the trade-off. If all threads contend on one atomic counter, serialize less work through it or aggregate locally. If only a few blocks launch, a large GPU may simply have too little parallel work.

For an elementwise operation reading two FP32 arrays and writing one, at least 12 bytes move per element before cache effects. Divide total bytes by sustained bandwidth to obtain a rough memory-bound floor, then compare with measured time. Do not infer a compute problem from low occupancy alone: increasing occupancy can reduce registers and cause more spills. Check correctness after transformations, especially synchronization and boundary handling. Without running the kernel, these remain ranked hypotheses; profiling counters and a minimal reproducible benchmark establish which mechanism causes the tenfold gap.
