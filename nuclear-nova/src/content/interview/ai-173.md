## Question

Design the serving stack for a ChatGPT-scale consumer assistant: hundreds of millions of weekly users, streaming chat, multiple model tiers.

## Brief answer

Separate the consumer chat product from the inference fleet: durable conversations and streaming gateways handle user experience, while model-tier routing and token-aware schedulers manage GPUs. Weekly active users are not a capacity unit; estimate concurrent sessions, turn rate, prompt length and output length by region and peak period before provisioning.

## Detailed answer

Suggested architecture: regional edges authenticate sessions, enforce account budgets and create idempotent generation jobs. Conversation services store message branches and attachments. A context builder selects history and evidence, then a router chooses an explicitly supported model tier according to user choice and product policy.

Inference pools batch compatible requests continuously, reserve KV capacity and prioritize latency-sensitive streams. Keep warm replicas for bursts and use admission control before queues become unbounded. Cancellation must release GPU resources when a user stops a response. Reconnection needs event IDs and durable completion state.

Measure first-token and inter-token latency separately by tier, length and geography. Track cost per successful conversation, not only tokens per second. Test a regional outage, a popular launch spike and long-context traffic. Capacity estimates should expose assumptions; hundreds of millions of weekly users can imply very different peak loads depending on usage patterns.

Create separate service classes for model tiers and workload types so a long-context batch cannot monopolize interactive capacity. The router needs a policy for overload: queue within a bounded delay, reject with a useful retry signal or offer an evaluated lower-cost tier. A silent switch can violate the user's capability or data-handling expectations.

Prefix locality and balanced load compete. Sending related conversations to one replica may save prefill but overload its decode queue. Route using both saved work and current token/KV pressure, and measure the effect on user-level latency rather than cache-hit rate alone. Keep autoscaling signals ahead of model-loading delays with warm capacity and demand forecasts.

The hardest incidents often amplify work: clients reconnect, retries create duplicate generations, and a regional outage pushes traffic into already busy pools. Use idempotent generation IDs, cancellation and admission limits to contain the amplification. Capacity models should include those failure conditions and reserve margins, with costs expressed per completed useful conversation rather than an idealized steady-state token benchmark.
