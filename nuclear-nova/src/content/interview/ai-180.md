## Question

How would you design safeguards for an AI system that can take actions on behalf of a user?

## Brief answer

Require explicit authority for actions, validate arguments outside the model and make consequential operations previewable, reversible or reviewable where possible. Give the agent only the credentials and tools needed for the task. A model's confidence or statement that the user approved something is not an authorization mechanism.

## Detailed answer

Suggested architecture: classify tool capabilities by effect, enforce user and resource permissions in a policy layer, and separate planning from execution. For a payment or message, approval should bind the relevant amount, recipient and content; changing those parameters invalidates the approval. Read-only lookup may proceed under a narrower standing permission.

Use idempotency keys, transaction boundaries, rate/cost limits and an audit trail. Handle uncertain outcomes explicitly: after a timeout, query the external system before repeating a write. Sandboxing and network restrictions limit the blast radius if an injected instruction influences the model.

Test wrong-recipient actions, stale approvals, duplicate requests, privilege escalation and cancellation during execution. Provide a stop control and recovery path. Avoid placing every trivial read behind confirmation; excessive prompts train users to approve blindly and obscure the actions that genuinely require attention.

Create a capability matrix describing each tool's effect, data scope, reversibility and approval requirement. A calendar read may be permitted under standing authorization, while sending an invitation or canceling an appointment has a different consequence. The model can propose an action, but the host should derive permission from the user session and reviewed workflow.

For a consequential write, display the exact target and material payload, persist approval against that version, then recheck resource state before execution. If the payload changes, approval must be reconsidered. Use conditional writes where possible so a stale model observation cannot overwrite a newer user edit.

After a timeout, mark the outcome uncertain and reconcile with the destination; do not infer failure or success from the absence of a response. Keep a stop control that cancels pending work and accurately reports already completed effects. Test this across crashes and retries. The objective is controlled delegation with recoverable evidence, not a sequence of generic confirmations that users learn to ignore.
