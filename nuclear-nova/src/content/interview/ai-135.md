## Question

Design a batched inference system where 100 requests take the same time as 1.

## Brief answer

One hundred requests can approach the latency of one only if the single request underutilizes the hardware and the combined workload still fits compute, memory and latency budgets. Batching improves throughput by amortizing weight reads and kernel overhead; it does not make arbitrary additional work free. Clarify whether the requirement refers to one-token decoding, full responses or a latency percentile.

## Detailed answer

Suggested approach: benchmark a single request's prefill and decode separately, then sweep batch size and sequence lengths. Decode often benefits from shared weight reads across many sequences, while prefill already has substantial matrix-multiplication work. Model weights, KV state and temporary buffers must fit the selected replicas.

Use continuous batching so completed sequences leave immediately and new requests enter at iteration boundaries. Cap batched tokens, split long prefills and enforce admission limits so one long prompt cannot stall every decoder. Record time to first token, inter-token latency and end-to-end p99, not just aggregate tokens/second.

If measured capacity cannot meet the target, add replicas, use a smaller or quantized model, or negotiate the requirement. For example, 100 responses each generating 200 tokens still require 20,000 output tokens. A good design explains where parallelism hides that work and where memory bandwidth or compute stops scaling.

Distinguish throughput latency from batch completion time. If one decode request is bandwidth-bound, processing many token vectors together can reuse loaded weights and approach the same step duration for a range of batch sizes. That range ends when compute, KV reads or memory capacity becomes limiting. Prefill has more arithmetic reuse already, so its scaling curve can look very different.

Queueing is another hidden cost: waiting to accumulate a batch of 100 can make the first arrival much slower even if the GPU batch is efficient. Use a maximum batching delay or continuous admission, and test the arrival pattern rather than only preassembled batches. Output lengths also differ, so the longest response should not hold finished requests hostage.

A credible answer presents a measured batch-size/latency curve and states the regime where near-equal latency holds. If the requested SLO lies outside it, replication or a different model is required. Batching is a way to exploit idle capacity, not an exemption from finite compute and memory budgets.
