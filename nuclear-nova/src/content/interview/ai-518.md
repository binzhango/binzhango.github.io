## Question

Design an agent that takes actions in enterprise tools (file a Jira ticket, draft an email) on a user's behalf. How do you handle permissions and evaluate it?

## Brief answer

Let the agent propose typed actions under the user's delegated identity, but enforce permissions and action policy in the connector service. Drafting an email and sending it are different capabilities. Use previews and explicit confirmation for consequential writes, plus idempotency and authoritative receipts for execution.

## Detailed answer

**Suggested approach.** Resolve the intended resource, validate parameters, show the exact change, then recheck access and current state at commit. A ticket-creation request gets a correlation ID and stable idempotency key; a timeout triggers status reconciliation rather than duplicate creation. Store the user's approval against the concrete action, not a vague earlier instruction.

Evaluate task completion in sandbox tools with realistic permissions, concurrent updates, rate limits, and failures after commit. Score wrong-recipient writes, duplicate actions, unsupported success claims, and unnecessary confirmations separately. Keep credentials outside model context and restrict each tool to the user's scope. In production, start with drafts and low-impact reversible actions, then expand based on measured reliability and the organization's policy.

### Make approval specific and execution idempotent

For a ticket, the proposal should name the project, title, description, assignee, and visibility. For an email, it should name recipients, subject, body, and attachments. Approval binds to this exact proposal and its relevant source versions. If the model later changes the recipient or adds an attachment, the old approval does not automatically authorize the new action.

At execution, the connector derives identity from the authenticated session, rechecks resource access, and submits a stable idempotency key. If the remote system lacks native idempotency, keep a local operation ledger and use reconciliation where the API permits it. Do not claim exactly-once execution merely because the agent makes only one visible tool call.

Test a revoked permission between preview and commit, an ambiguous resource name, a timeout after creation, and a duplicated user message. The correct result includes both the intended remote state and an accurate explanation to the user. An agent that creates the right ticket twice, or says it sent a message when it only saved a draft, has not completed the task correctly.
