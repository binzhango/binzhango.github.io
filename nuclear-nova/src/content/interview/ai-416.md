## Question

How would you serve a large mixture-of-experts model on a statically scheduled fabric when expert selection is data-dependent?

## Brief answer

Suggested approach: bound the dynamic routing choices within a statically planned execution envelope. Place experts ahead of time, reserve dispatch capacity, and use runtime routing metadata to select among compiled paths. Alternatives include padding to fixed capacities, compiling multiple workload shapes, or executing a superset. Each trades predictable timing against wasted compute, memory, or routing flexibility.

## Detailed answer

Characterize expert-load distributions, top-k selection, and worst-case token concentration. Plan communication and buffers for the accepted capacity, with explicit overflow behavior such as rerouting, queuing, or rejecting rather than silently dropping required computation. Group expert work to avoid tiny inefficient operations.

Measure utilization under both balanced and adversarially skewed routes. Overprovisioning every expert for the worst case can erase sparse-compute savings; a too-tight plan creates tail stalls or changes model semantics. Keep the router's numerical behavior consistent with training and validate any routing constraints for quality. The answer depends on the fabric's supported dynamic mechanisms; a fully static, single-path machine cannot magically execute arbitrary data-dependent routing without accommodation.

### Make dynamic choice fit a bounded execution contract

The router's selected experts depend on token data, so a single fixed path cannot know all destinations in advance. One approach reserves slots and buffers for a bounded set of expert assignments, then fills them at runtime; another compiles several routing/shape variants and selects a compatible one. The fabric must explicitly support the required data-dependent dispatch or execute padded work whose cost is known.

Capacity planning needs a per-expert token bound and an overflow policy. Queuing preserves computation but increases latency; dropping or rerouting assignments may change model behavior and requires quality validation. For an adversarial batch sending most tokens to one expert, balanced-average benchmarks hide the critical failure. Test those skewed routes and measure padding waste, communication, and tail latency. A sparse architecture saves arithmetic only if the schedule can exploit unused expert work economically. Preserve router scores and combination semantics when adding system constraints; changing them is a model change, not merely scheduling.
