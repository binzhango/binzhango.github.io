## Question

Write a SQL query that joins and aggregates across tables to answer a business question.

## Brief answer

Define the business question and table grain before joining. Aggregate child rows to the intended parent grain and use `EXISTS` for eligibility checks when multiple matching records should count only once. Many incorrect business queries are syntactically valid but multiply rows through one-to-many joins.

## Detailed answer

For the concrete question “How many open orders per customer have an unresolved supplier issue, and what is their total order value?”, assume `orders(id, customer_id, status)`, `order_lines(order_id, supplier_id, amount)`, and `supplier_issues(supplier_id, resolved_at)`. Amounts share a currency and represent line totals.

```sql
WITH order_totals AS (
  SELECT order_id, SUM(amount) AS total
  FROM order_lines
  GROUP BY order_id
)
SELECT o.customer_id,
       COUNT(*) AS blocked_orders,
       SUM(t.total) AS blocked_value
FROM orders AS o
JOIN order_totals AS t ON t.order_id = o.id
WHERE o.status = 'open'
  AND EXISTS (
    SELECT 1
    FROM order_lines AS l
    JOIN supplier_issues AS i ON i.supplier_id = l.supplier_id
    WHERE l.order_id = o.id AND i.resolved_at IS NULL
  )
GROUP BY o.customer_id;
```

`EXISTS` prevents two unresolved issues from counting an order twice. Test several lines from the same supplier, multiple issues, closed orders, resolved issues, and customers with no blocked orders. If zero-count customers must appear, start from a customers table and left-join the aggregated result. Index the join/filter keys and inspect the query plan on representative data.

### Reason about the row grain

The `orders` table has one row per order, while `order_lines` can have many. Joining lines and supplier issues directly can multiply every line by the number of unresolved issues, inflating both count and value. `order_totals` reduces lines to one row per order first. The correlated `EXISTS` then answers a Boolean eligibility question without adding result rows.

For an open order with two lines worth 10 and 20 and two unresolved issues on one supplier, the correct contribution is one blocked order worth 30. A naive join can produce more rows and a larger sum even though its syntax is valid. The query intentionally sums the entire blocked order value, not only affected line value; confirm that business definition. Orders without lines are excluded by the inner join. Use fixed-precision currency types where available and document null-amount handling. Indexes on order IDs, supplier IDs, and relevant status fields help, but actual complexity depends on the optimizer and data distribution; inspect plans and row counts.
