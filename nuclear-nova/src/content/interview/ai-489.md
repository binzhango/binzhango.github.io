## Question

An autonomous agent has write access to a customer's repository, CI credentials and network access. What is your threat model?

## Brief answer

Assume repository content, dependencies, tool output, and remote pages can be adversarial. The main risks are credential theft, data exfiltration, malicious code execution, unauthorized repository changes, and abuse of CI privileges. A model instruction is not a security boundary; enforce authority in the execution and credential layers.

## Detailed answer

**Suggested approach.** Run each task in an isolated sandbox with read-only base images, scoped filesystem mounts, egress restrictions, resource limits, and short-lived tokens. Separate permission to read code, push a branch, trigger CI, access secrets, and deploy. Do not expose production credentials merely because a test command might need them.

Treat external text as data and require structured authorization for consequential actions. Review outbound requests, secret access, dependency execution, and changed workflow files in an audit trail. Red-team prompt injection in comments, package install hooks, encoded exfiltration, and forged tool-success output. Define incident containment: revoke tokens, stop tasks, preserve logs, and identify affected repositories. The residual risk depends on actual sandbox guarantees and allowed network paths, so validate them with adversarial tests rather than relying on architectural diagrams.

### Follow an attack across boundaries

A malicious dependency can print instructions telling the model that a test requires uploading a configuration file. That is a prompt-injection attempt, but the decisive protection is whether the sandbox can read the file and contact the destination. Restricting secret mounts and outbound connectivity limits harm even if the model follows the text. An instruction hierarchy alone cannot contain a process that already has unrestricted credentials.

Separate credentials by capability and lifetime. A token that can fetch source need not modify workflow files; a branch-push token need not access deployment secrets. Grant consequential capabilities only to the trusted component executing a validated request, and record which identity authorized it.

Also consider availability attacks: fork bombs, enormous artifacts, repeated CI triggers, and expensive provider loops. Enforce resource and spending limits outside the model. Test escape paths through package installation, child processes, artifact uploads, and log collection. The security claim should match the actual execution boundary and allowed capabilities, with a documented containment and credential-revocation path for failures.
