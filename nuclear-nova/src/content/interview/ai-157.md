## Question

Design and implement an in-memory key-value store supporting set, transactional begin, commit and abort.

## Brief answer

Represent a transaction as a private working copy and publish it only at commit. Abort discards the copy. For this single-client in-memory exercise, copying is simple and provides clear isolation from the committed state; concurrent clients require conflict detection or locking, and durability requires logging beyond memory.

## Detailed answer

Assume one active transaction, string keys and immutable values. Reads inside the transaction see its own writes.

```python
class TransactionalStore:
    def __init__(self): self.committed, self.working = {}, None
    def begin(self):
        if self.working is not None: raise RuntimeError('transaction already active')
        self.working = self.committed.copy()
    def current(self): return self.committed if self.working is None else self.working
    def set(self, key, value): self.current()[key] = value
    def get(self, key): return self.current().get(key)
    def commit(self):
        if self.working is None: raise RuntimeError('no transaction')
        self.committed, self.working = self.working, None
    def abort(self):
        if self.working is None: raise RuntimeError('no transaction')
        self.working = None

s = TransactionalStore(); s.set('x',1); s.begin(); s.set('x',2)
assert s.get('x') == 2
s.abort(); assert s.get('x') == 1
s.begin(); s.set('x',3); s.commit(); assert s.get('x') == 3
```

Begin costs $O(n)$ time and memory; get/set remain average O(1), and commit swaps a reference. A write overlay reduces begin cost but makes deletion and lookup semantics more complex. Shallow copies do not isolate mutations inside mutable values, hence the immutable-value assumption. Test empty commits, abort after updates and invalid transaction nesting.

`begin` snapshots the committed dictionary, so writes inside the transaction affect only the working copy. `commit` replaces the committed reference with that copy; `abort` discards it. Reads choose the working copy while a transaction exists, providing read-your-writes behavior for the single client. An empty dictionary is still an active transaction, which is why the code checks `is not None` instead of truthiness.

The shallow-copy assumption is essential. If a stored value is a list and a caller mutates that list, both copies may reference the same object, violating isolation. Immutable values, defensive deep copies or controlled update APIs can address this with different costs.

Two concurrent transactions cannot safely use this design unchanged: each could snapshot the same state and later overwrite the other's changes. Add version-based conflict detection, locking or a richer multi-version model depending on the required isolation. Persistence needs a write-ahead record and recovery semantics as a separate layer. Test that aborted changes are absent, committed changes survive subsequent transactions and invalid nested operations fail without altering state.
