## Question

Design a multi-tenant inference platform that serves many foundation models to thousands of customers (Bedrock-shaped).

## Brief answer

Suggested approach: separate a control plane for tenant policy and model lifecycle from a data plane that routes and serves requests. Use per-tenant quotas and isolation, model-aware scheduling, bounded queues, and a versioned inference contract. Shared GPUs improve utilization only if noisy-neighbor effects and sensitive-data isolation are controlled.

## Detailed answer

The control plane manages model artifacts, approvals, endpoint configuration, quotas, billing, and rollout state. The gateway authenticates, validates payloads, enforces limits, and selects a model/version. Schedulers assign compatible work to warm workers using memory capacity, KV demand, deadlines, and batching opportunities.

Track cache ownership, request cancellation, GPU failures, and partial streams. Encrypt artifacts and data, restrict custom-code loading, and isolate untrusted execution. Admission control and fair scheduling prevent one long-context tenant from monopolizing capacity. Canary model/runtime updates against correctness and latency, with rollback. Measure useful token throughput, p95/p99 latency, error rate, tenant fairness, and actual cost. Explicitly choose which workloads require dedicated capacity rather than promising perfect isolation on every shared pool.

### Separate placement from per-token scheduling

The placement service decides which model versions and replicas occupy each accelerator group, considering weights, expected KV demand, hardware compatibility, and redundancy. Inside a worker, a continuous-batching scheduler decides which requests advance on the next iteration. Conflating these loops can cause model-loading churn when short traffic spikes arrive.

An authenticated request receives a tenant quota and deadline, enters the model queue, and is admitted only when memory and service capacity are available. Workers stream results through a gateway that propagates cancellation and records billable usage. Model artifacts are immutable and verified before loading; custom execution code requires an isolation strategy beyond ordinary tensor loading. Cache keys include tenant and model configuration. Use weighted fair queues to prevent high-volume tenants from dominating, while offering dedicated groups for stricter isolation. Exercise node loss during generation and ensure retries do not double-bill or replay side-effecting tools. Track model loading, queueing, and actual device execution separately.
