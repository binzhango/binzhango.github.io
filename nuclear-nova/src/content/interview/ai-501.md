## Question

You have two hours and access to AI development tools. How do you decide what to build and allocate the time?

## Brief answer

Choose a small end-to-end user problem with a demonstrable outcome, then allocate the two hours around a working vertical slice and verification. Use AI tools to accelerate familiar work and inspect their output; do not let tool experimentation consume the session. State assumptions and cuts explicitly.

## Detailed answer

**Response framework.** Spend the first 10–15 minutes clarifying the user and success criterion, then sketch the smallest flow and data contract. Reserve the final 25–30 minutes for tests, error states, and demonstration. Use the middle period to implement one complete path before adding polish. If external integrations are unavailable, use clearly labeled fixtures with the same interface.

Pick a task with one primary interaction and a visible result, such as turning a structured request into a validated draft artifact. Cut authentication breadth, complex administration, and speculative scale features unless central to the problem. During the demo, show one normal case and one failure case, explain what is real, and identify the next validation step. Judge the work by usefulness and clarity rather than generated code volume.

### Choose a demonstration with a real acceptance test

An illustrative two-hour project could accept a CSV of expenses, validate required columns, and produce a reviewable summary with flagged invalid rows. It has a clear input, visible result, and testable failure path. A broad “AI finance assistant” would hide too many unresolved requirements for the same time budget.

At the first checkpoint, make one fixture travel through the entire flow. Then replace fragile assumptions, such as silently treating a missing amount as zero, with explicit errors. Use AI assistance for implementation and test ideas, but inspect parsing, calculations, and generated output yourself. If the core path is late, reduce optional formatting before cutting validation.

The final demonstration should show the valid case and an invalid input, identify any mocked dependency, and explain how a user recovers. A concise handoff names the supported contract and the next uncertainty to test. In an interview, this is a proposed plan unless it describes your actual work; do not imply that a hypothetical two-hour exercise has already served real users.
