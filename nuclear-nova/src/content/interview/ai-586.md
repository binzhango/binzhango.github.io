## Question

Users ask “how many open orders are blocked on a supplier issue?” Plain RAG gets this wrong. Why, and what's the right architecture?

## Brief answer

The question asks for an exact aggregate over current structured state, not a few semantically relevant passages. Plain RAG cannot guarantee exhaustive retrieval or correct joins and can double-count orders. Use a governed semantic layer or validated database query, then let the model explain the result with its definition and timestamp.

## Detailed answer

**Suggested approach.** Define “open,” “blocked,” and “supplier issue” with business owners, including whether one unresolved issue blocks all orders from that supplier. Query the authoritative order and issue tables using permission filters and `EXISTS` or preaggregation to avoid join fanout. Return count, query version, data freshness, and optionally authorized drill-down rows.

The model maps language to an allowlisted metric or reviewed query plan; it does not invent column semantics. Validate with fixtures containing multiple lines, multiple issues, canceled orders, and late status updates. Use documents to explain policy definitions, while structured data computes the count. If data sources disagree or are stale, surface that limitation instead of providing a precise-looking unsupported number.

### Retrieval cannot certify an exhaustive count

A top-k search might return ten relevant orders while hundreds remain outside the retrieved set. The model cannot infer a complete count from that sample, even if every returned passage is correct. Structured queries operate over the defined relation and can apply the exact status, permission, and blocking predicate to every eligible row.

Use a metric contract such as “count distinct open order IDs with at least one unresolved issue on an associated supplier.” Translate the user request to that approved metric and its parameters, execute with the caller's authorization, and return a structured result with freshness and definition. `EXISTS` is appropriate when multiple issues should make an order blocked only once. Keep policy text retrieval separate: documents explain what blocking means, while a database computes current state. Add fixtures for duplicate lines, resolved issues, canceled orders, and missing relationships. If the data snapshot is stale or the definition ambiguous, return that specific limitation or ask for clarification rather than generating an exact-looking count.
