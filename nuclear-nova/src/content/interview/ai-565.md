## Question

Helix splits into a large slow model and a small fast one. Why not run a single end-to-end network?

## Brief answer

Separate slow semantic understanding from fast reactive control because they have different compute and timing needs. A large model can interpret language and scenes, while a small policy continuously responds to fresh observations and contact. A single large network may have richer integration but miss the control loop's latency and power budget.

## Detailed answer

In the original February 2025 Helix design, Figure describes a semantic model at 7–9 Hz and a visuomotor policy at 200 Hz. Those rates explain the architectural motivation, not a universal robotics prescription. The later Helix 02 description adds a faster System 0 layer, so the two-part description is version-specific.

The hierarchy introduces stale-goal and interface risks: the fast policy must tolerate delayed semantic updates and reject incompatible commands. Train with the expected latency offset and test loss of the slow model. Compare complete task performance, perturbation recovery, power, and worst-case loop timing. The right design is the simplest one that meets both semantic competence and real-time physical control requirements.

### Match computation to the timescale of the decision

Interpreting “put the fragile item in the drawer” requires semantic context that need not be recomputed for every tiny motion correction. Maintaining a stable grasp while the object shifts requires fresh sensor feedback much more frequently. A hierarchy lets the expensive interpretation persist while the faster component adapts movement to current observations.

The original 200 Hz loop has a 5 ms interval. Running a model whose inference takes tens or hundreds of milliseconds directly at that rate would produce stale commands or miss deadlines. Merely interpolating old outputs cannot recover information about unexpected contact that the model has not observed.

The separation creates its own engineering work. Define how a new semantic goal replaces the old one, how long a goal remains valid, and how the fast controller behaves if updates stop. Train and test with realistic delay so the lower layer does not depend on unrealistically fresh guidance. Verify that semantic changes do not create discontinuous or incompatible motion targets.

A single smaller model may be preferable if it meets both task and timing requirements. The hierarchy is justified by measured constraints and competence, not by an assumption that more components are always better. Compare full task outcomes, response to disturbances, compute usage, and timing violations under the actual hardware workload.
