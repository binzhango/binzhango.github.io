## Question

An agent you shipped four months ago runs on a base model being deprecated in 60 days. How do you swap the model without regressing quality, and what had to be in place beforehand?

## Brief answer

Suggested approach: Treat the replacement as a versioned dependency migration with a fixed retirement deadline, not a model-name edit. Inventory the current contract, replay representative tasks, test the new model's tool and formatting behavior, and roll out behind a reversible routing layer. The necessary groundwork is preserved traces, evaluation sets, versioned prompts/tools, and observable outcomes.

## Detailed answer

List model-specific assumptions: tokenizer/context budget, chat template, system instruction behavior, JSON schema support, safety responses, latency, and pricing. Create a baseline before the old endpoint disappears. Compare alternatives on production-representative and severe-error cases, including long trajectories and retries.

Use shadow evaluation where data policy permits, then canary traffic with quality and cost gates. Keep an explicit fallback while the old model remains available and choose a contingency for the final cutoff. Do not blindly reuse prompts optimized for a different model. Communicate user-visible behavior changes and preserve rollback of the full configuration bundle. After migration, monitor delayed outcomes as well as immediate syntax and latency.

### Use the sixty days to retire hidden coupling

In the first phase, freeze a reproducible baseline of the current model, prompt, tools, and source versions. Inventory provider-specific behavior and create an adapter boundary for requests, streaming, errors, tool calls, and usage. In the second phase, evaluate candidate models with checkpoint-specific prompts and templates. Reserve the final phase for canaries, rollback rehearsal, and resolving severe regressions before the cutoff.

Long agent trajectories need end-state evaluation: a replacement that passes single-turn QA may choose tools differently or fail recovery after several steps. Compare latency, token use, refusal behavior, and structured-output validity as well as task success. If no alternative meets every requirement, narrow unsupported workflows or use a temporary fallback with explicit trade-offs. After the old endpoint is removed, rollback cannot mean routing back to it, so prepare a viable contingency in advance. The prerequisite is versioned evaluations and configuration, not merely a generic `model` string in application code.
