## Question

Design a system that enables a large language model to handle multiple questions in a single thread.

## Brief answer

Represent a conversation as ordered messages or a branchable message graph, then build each model request from the current user intent and the relevant prior context. Multiple questions in one turn should become explicit subgoals, while later turns may revise earlier goals. Do not rely on concatenating every historical message indefinitely.

## Detailed answer

Suggested approach: assign message IDs and parent relationships, preserve user corrections, and separate durable user preferences from temporary task state. For a multi-question turn, enumerate the requested outputs internally and verify that the final response addresses each. If a question depends on another tool result, execute the dependency first; independent retrieval can run concurrently.

Use token-aware context selection and summaries with links back to original evidence. Summaries are lossy: retain exact constraints, identifiers and unresolved questions rather than only conversational prose. Retrieved documents and tool results remain untrusted content, even when stored in the thread.

Test pronoun resolution, topic switches, corrections, contradictory requests and long histories. Evaluate unanswered-subquestion rate and whether stale context contaminates a new question. Ask for clarification only when ambiguity materially changes the answer; do not invent a relationship between independent questions simply because they share a thread.

For a turn asking “summarize the incident, identify affected accounts, and draft an update,” represent three outputs with dependencies. The account lookup depends on incident identity, while the draft depends on both the summary and account evidence. The final response should be checked against that set so a fluent summary does not conceal two unanswered requests.

Later corrections need explicit precedence. If the user changes the audience from engineers to customers, the new constraint updates the active task without erasing verified incident facts. A summary should preserve exact identifiers, dates and unresolved decisions, while older irrelevant discussion can be omitted from the next model context.

Test long conversations where pronouns refer to different entities, a new task interrupts an old one, and a user reverses an earlier instruction. Retrieval over history can help find evidence, but similarity alone does not identify which instruction is currently authoritative. Separate conversational memory from an active task ledger and evaluate whether each answer follows the latest accepted intent.
