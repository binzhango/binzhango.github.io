## Question

Design AutoGLM end to end: a cloud service letting users delegate multi-step phone tasks (“order my usual coffee”) to an autonomous agent. Architecture and failure modes.

## Brief answer

Suggested approach: build a permissioned task service with a phone execution session, an agent controller, an action gateway, and an auditable state machine. Separate planning from irreversible actions. “Order my usual coffee” requires resolving store, item, price, payment, and delivery or pickup before the system can reliably complete the purchase.

## Detailed answer

Store user preferences and credentials in appropriate protected services, not in free-form model memory. The controller observes current UI state, proposes one action, and receives the resulting observation. The gateway checks app scope, allowed operations, spend limits, and whether confirmation is required. Persist step IDs and receipts so retries cannot place a second order.

Handle app updates, unavailable items, login expiry, network loss, and ambiguous preferences by replanning or escalating with concrete options. Use bounded retries and compensation where supported; never assume an interrupted payment failed. Tenant isolation covers screenshots, recordings, logs, and sessions. Test complete workflows in sandbox accounts and measure purchase correctness, duplicate actions, intervention rate, cost, and time to completion. A visual agent is only one component of the service.

### Trace the coffee-order workflow

The service first resolves “usual” to a saved, user-approved order and identifies the intended store. It observes menu availability and prices, prepares a cart, and presents the specific purchase when confirmation is required. A privileged gateway submits the purchase using a transaction identifier and returns a receipt. The model receives the receipt and communicates the actual result, rather than inferring success from a button click.

Separate the cloud planner from a device-session service and a credential vault. Screenshots and action results go through a task-scoped channel; credentials are injected by the executor without entering prompts. A durable task journal records planned, submitted, and confirmed actions. If the device disconnects after payment submission, reconcile with the merchant before trying again. If an item is unavailable, request a substitution decision instead of silently changing the purchase. Per-user concurrency limits prevent two overlapping tasks from fighting over the same phone UI.
