## Question

How would you parallelize a processing task while managing concurrency and shared data mutation?

## Brief answer

First identify whether the work is I/O-bound, CPU-bound or accelerator-bound, then partition independent inputs and give each worker private mutable state. Aggregate results through a queue or reduction. Parallelizing a shared read–modify–write loop without changing ownership introduces races even when individual reads and writes look simple.

## Detailed answer

The prompt omits the original task, so assume a CPU-heavy pure transform over independent records. This executable structure uses processes; a function passed to the pool must be importable and picklable.

```python
from concurrent.futures import ProcessPoolExecutor

def transform(x): return x*x

def parallel_map(values, workers=2):
    with ProcessPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(transform, values, chunksize=100))

if __name__ == '__main__':
    assert parallel_map([1,2,3]) == [1,4,9]
```

For HTTP requests use bounded async I/O instead; for vector operations prefer a batched array/kernel operation before adding processes. Measure serialization, startup, skew and downstream rate limits. A speedup is bounded by the serial fraction and can be negative for small work items. If updates must share an account or document, partition by that key or use an explicit transaction, then test determinism against a serial reference.

Start with ownership: each worker receives immutable input and returns a result, while one coordinator assembles outputs. This avoids a shared counter or dictionary becoming the synchronization bottleneck. If records must update the same entity, partition by entity key so one worker owns its sequence, or use a transaction that enforces the required invariant.

A process pool helps CPU-bound Python work but adds serialization and startup overhead. Large arrays may be better shared read-only or processed by vectorized kernels. Async I/O is appropriate when most time is spent waiting on network responses; it does not make CPU computation parallel by itself. Thread behavior also depends on the runtime and whether native operations release its interpreter lock.

Measure against a serial reference and verify deterministic results. Amdahl's law gives speedup at most $1/[s+(1-s)/p]$ for serial fraction $s$ and $p$ workers, before overhead. With 20% serial work and four workers, the ideal bound is 2.5x. Test skewed inputs, worker failure and cancellation, because the slowest partition and recovery policy often determine real completion time.
