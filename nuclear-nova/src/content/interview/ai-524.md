## Question

Implement prompt construction for the next conversation turn under a fixed token budget while preserving a shared prefix cache.

## Brief answer

Keep the reusable instruction/tool prefix byte-for-byte stable, reserve output tokens, and append the newest complete conversation units that fit. Count tokens with the actual model's chat serialization. Never split a tool call from its result or drop mandatory policy to improve cache hits; cache eligibility is an optimization after prompt correctness.

## Detailed answer

The core below treats history items as already-grouped atomic units. `count` must include role delimiters and serialization overhead; it is deliberately injected rather than approximated with character counts.

```python
def build_prompt(prefix, history_units, current, context_limit, output_reserve, count):
    budget = context_limit - output_reserve
    if output_reserve < 0 or budget < 0:
        raise ValueError('invalid budget')
    suffix = [current]
    if count(prefix + suffix) > budget:
        raise ValueError('mandatory content exceeds budget')
    kept = []
    for unit in reversed(history_units):
        candidate = unit + kept
        if count(prefix + candidate + suffix) > budget:
            break
        kept = candidate
    return prefix + kept + suffix

count = lambda messages: sum(len(m.split()) for m in messages)
assert build_prompt(['fixed policy'], [['old turn'], ['recent turn']], 'now', 6, 1, count) == [
    'fixed policy', 'recent turn', 'now']
```

Preserve a contiguous recent suffix and put any separately validated summary after the stable prefix. Count the fully assembled prompt because tokenization is not always additive across concatenated text. Test an oversized current turn, exact budget boundaries, multi-message tool units, and prefix stability across turns. Provider-specific cache block sizes and retention should be measured against the selected deployment's documentation.

### Walk through a budget decision

Assume a 100-token context limit and a 20-token output reserve, leaving 80 input tokens. If the mandatory prefix and current turn require 35, only 45 remain for history. The loop adds newest complete units while the fully serialized prompt stays within 80. When the next older unit no longer fits, it stops, preserving a contiguous suffix rather than skipping an important tool-result relationship to fit an even older short message.

Prefix caching requires exact compatibility, not merely equivalent meaning. Changing a timestamp, tool order, tokenizer, or model revision can invalidate reuse. Keep genuinely stable instructions first and variable summary or retrieved material afterward, but never retain an obsolete policy just to preserve a cache hit.

With H history units, repeated full counting can be expensive: the simple implementation may retokenize growing candidates many times. Cache stable serialized units or use a bounded search strategy where the provider's tokenization contract permits it, then validate the final assembled prompt exactly. An oversized mandatory turn raises an error because silently truncating the user's current request or policy would change the task's meaning.
