## Question

What is an ontology in the Palantir sense, and why put LLM agents on top of one instead of on raw tables and documents?

## Brief answer

An operational ontology maps data to business objects, relationships, properties, and permitted actions, giving applications a consistent domain model. Agents can reason over concepts such as assets, orders, and suppliers while using governed operations. This reduces repeated schema interpretation, but does not remove the need for authorization, data quality, and policy enforcement.

## Detailed answer

Palantir's Ontology overview describes connecting data and models to semantic and operational elements, including objects, links, and actions. In a proposed maintenance workflow, a locomotive links to inspections, faults, parts, and work orders; an action creates a reviewed repair request with validated fields.

Compared with raw tables and documents, this layer can make identity, relationships, and action contracts explicit and reusable. Its costs are modeling effort, governance, synchronization, and the risk of encoding an incorrect business definition centrally. Evaluate whether it improves task correctness and auditability. The agent still needs evidence and scoped tool access; an ontology is not proof that every underlying fact is current or every suggested action is authorized.

### Give the agent business-level operations

Without a semantic layer, an agent must infer that `asset_id` in one system and `equipment_key` in another refer to the same locomotive, and guess which status codes mean a work order is open. An ontology makes those object identities, properties, links, and definitions explicit. Applications and agents can then query “open work orders for this asset” through a stable domain interface.

An action can also carry a typed contract: create a maintenance request for an existing asset, require a valid priority, check the caller's role, and record an audit trail. The model proposes parameters; the operational service validates and executes them. This reduces repeated ad hoc SQL and tool construction, but central mistakes have broad effects. Assign owners for definitions, version changes, and monitor synchronization with underlying systems. Compare the benefit against modeling overhead for the use case; a small read-only report may not need a large ontology. Semantic consistency helps reasoning, while access control and source freshness still require enforcement.
