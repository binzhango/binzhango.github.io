## Question

Build the evaluation harness for a new frontier model release. What does it need to do?

## Brief answer

Build a reproducible harness that evaluates capability, safety, reliability and cost under the intended deployment conditions. Pin datasets, prompts, model versions, tools and inference budgets; retain raw outputs and scoring evidence. Separate benchmark execution from scoring so judges can be audited and changed without rerunning expensive generations.

## Detailed answer

Suggested architecture: a versioned task registry describes inputs, permissions, resource limits and scoring; isolated runners execute model/tool interactions; an artifact store records traces; scorers produce per-case results and uncertainty; reports compare candidates with a pinned baseline. Sandbox executable code and prevent evaluation data from becoming tool instructions.

Include contamination checks, adversarial tests, multilingual and long-context slices, tool-use tasks and regression suites from prior incidents. Use deterministic checks where possible and blinded human adjudication for ambiguous outcomes. Calibrate model judges against humans and report disagreement rather than hiding it in one score.

Release gates should reflect severity and intended access. Evaluate multiple inference budgets because a model may become more capable with tools or retries. Track latency, tokens and cost per successful task, and ensure failures and timeouts remain in the denominator. Post-release monitoring must connect back to new test cases.

Separate execution from scoring so an expensive generation can be rescored when a rubric or judge is corrected. Store inputs, outputs, tool observations, versions, seeds where applicable, resource usage and terminal status in immutable artifacts. Every failed or timed-out case remains a result; dropping it biases the release score upward.

Task runners need isolation for generated code and restricted access to evaluation secrets. A model should not be able to inspect hidden answers through its tools. For agents, evaluate environment state and side effects, not only the final response. Run at multiple inference budgets to distinguish base capability from capability unlocked by repeated attempts or tool access.

Reports should show paired differences, important slices, uncertainty and critical failures, with links to inspectable cases. Calibrate model judges and retain human adjudication for consequential ambiguity. Include a reproducibility check that reruns a small sample and explains expected stochastic variation. The harness is a measurement system with its own failure modes, so validate it with known-good, known-bad and deliberately malformed outputs before using it as a release authority.
