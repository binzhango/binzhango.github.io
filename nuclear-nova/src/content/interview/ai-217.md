## Question

Two-part warm-up: given a stream of user actions, return the k most engaged-with items. Then: why might your heap solution be the wrong choice in production?

## Brief answer

Count engagement by item and select the top k, but define the event and time window first. A heap is useful when k is small; it is not automatically the right production design when updates are distributed, counts expire, events duplicate or rankings must be fresh. Exact unbounded counts also require memory proportional to unique items.

## Detailed answer

This bounded-input reference treats each action as one engagement and gives deterministic ties. Event deduplication and windowing are outside its stated contract.

```python
from collections import Counter
import heapq

def top_engaged(actions, k):
    if k < 0: raise ValueError('negative k')
    counts = Counter(actions)
    return [(item, counts[item]) for item in heapq.nsmallest(k, counts, key=lambda x:(-counts[x],x))]

assert top_engaged(['x','y','x','z','y','x'],2) == [('x',3),('y',2)]
```

For production, distinguish clicks, dwell time, likes and purchases; blindly adding them can reward spam. Use event IDs, event-time windows and late-event policies. Partition counters by item and aggregate candidates, or use a stream processor with durable state. Approximate heavy-hitter sketches can bound memory if error is acceptable.

A heap of mutable counts becomes stale unless updates repair priorities; pushing every update adds unbounded stale entries. For periodic dashboards, a batch aggregation may be simpler. Evaluate freshness, correction behavior and abuse resistance, not only asymptotic selection cost.

The batch reference first builds exact counts for every distinct item, then selects k results. Its memory is therefore $O(u)$ for u unique items, not $O(k)$ simply because a heap is used for selection. This distinction matters for an unbounded stream whose item universe continues growing.

Production engagement also needs a definition. Counting every click equally can reward bots or repeated accidental interactions. A windowed metric needs event timestamps, deduplication IDs, late-arrival policy and corrections for deleted or invalid events. A heap alone stores none of those semantics.

If queries are periodic, durable stream aggregation into time buckets followed by a top-k query may be simpler than continuously maintaining a global heap. If bounded-memory approximation is acceptable, use a heavy-hitter sketch with stated error and merge behavior. For exact rankings, retain authoritative counts in external state and handle distributed updates atomically. Evaluate freshness and correction behavior against a small exact oracle, plus abuse resistance, rather than optimizing selection complexity while ignoring the meaning of the count.
