## Question

A community contributor opens a PR adding a new model architecture to `transformers`. You're the reviewing maintainer: what do you check, and how do you handle the interaction?

## Brief answer

Review architectural correctness, library compatibility, test coverage, checkpoint provenance, and maintenance cost. Reproduce a small forward pass and verify output parity with the reference implementation. Make the review collaborative: explain blocking issues, separate optional improvements, and help the contributor reduce the change into reviewable pieces.

## Detailed answer

Start with the paper, model configuration, tensor shapes, attention masks, positional encoding, and generation cache behavior. Compare deterministic outputs against a reference checkpoint at a stated precision; random-weight smoke tests cannot establish fidelity. Check save/load round trips, tokenizer integration, batching, padding, device/dtype movement, and supported generation paths. Include malformed configurations and tiny-model tests so CI does not need the full checkpoint.

Inspect unsafe deserialization, executable remote code, dependency additions, and licensing. Document unsupported features explicitly instead of silently falling back. Ask for performance evidence only for claimed improvements, using reproducible inputs and hardware. In the interaction, acknowledge useful work, explain why each requested change matters, and offer concrete examples. Merge only with an owner for follow-up fixes; a popular architecture does not justify unmaintainable special cases.

### A concrete review sequence

Start with a tiny configuration that exercises the same attention layout and positional encoding as the real model. Trace an input through embedding, attention, feed-forward block, and output projection, checking shapes and parameter names. Then test a fixed prompt both in one forward pass and token by token with the generation cache. Matching the two catches cache-position and mask bugs that a plausible generated sentence can conceal. Test a padded batch against the corresponding unpadded examples as a separate invariant.

If the checkpoint loader reports unexpected keys, classify each one: an intentionally omitted task head differs from a missing normalization scale. Save and reload the converted model and compare outputs again. Numerical tolerances should reflect precision and backend differences, not be relaxed until any implementation passes.

For review communication, write a blocking comment such as: “The cached path assigns every new token position zero; please add a two-step parity test and advance the position from cache length.” This explains the failure and the acceptance condition. Keep naming preferences separate so the contributor can prioritize correctness and finish a maintainable patch.
