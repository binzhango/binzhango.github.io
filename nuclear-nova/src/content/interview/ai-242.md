## Question

Loss spikes mid-run on a large pretraining job. Walk me through your debugging process.

## Brief answer

First determine whether the spike is a real model update problem, a bad batch or a reporting artifact. Correlate loss with data IDs, gradient norms, learning rate, precision/scaler state and hardware errors before choosing a recovery action.

## Detailed answer

Replay the suspect batch against a known-good checkpoint in a controlled environment. Inspect corrupted tokens, masking errors, unusually long examples, optimizer-state discontinuities and changes in global batch size. Compare per-rank loss and gradients to identify one faulty shard or collective. If nonfinite values occur, locate the earliest operation and compare higher precision; silently skipping every difficult batch can bias training. Preserve the failing state and restore the last verified checkpoint when needed. Add a regression test or data validation rule for the confirmed cause, and evaluate whether the recovered run reproduces expected loss on a fixed probe set.

### Find the first divergence rather than treating the loss

Freeze the failing batch identifiers, checkpoint, optimizer state, numerical configuration, and rank logs. Compare the same batch on the prior checkpoint and the suspect checkpoint. If only one rank has extreme loss, inspect its shard, token masks, and hardware; if all ranks diverge after a schedule change, investigate optimizer and learning-rate state.

A high loss on a genuinely difficult batch is different from NaNs or a corrupted target mask. For nonfinite values, instrument activations and gradients by layer and locate the first invalid operation. Compare selected operations in higher precision, verify scaling conventions, and check whether gradient clipping or accumulation changed. Restoring model weights without compatible optimizer moments can cause another spike, so recovery must restore the full state. After fixing the cause, replay a fixed probe set and several subsequent steps to verify sustained behavior. Avoid suppressing the symptom by excluding every high-loss example, which can bias the training distribution and conceal the actual fault.
