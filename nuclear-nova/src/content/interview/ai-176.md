## Question

Design an in-memory database. / Design Slack.

## Brief answer

The prompt contains two separate design exercises: an in-memory database and a Slack-like messaging service. Clarify which is intended rather than blending them into one vague architecture. An in-memory store centers on data structures, transaction semantics and persistence; a messaging service centers on ordered conversations, fan-out, permissions and durable history.

## Detailed answer

For the database, define key/value types, point operations, scans, TTL and transaction isolation. Use a hash index for point access, an ordered index when range scans matter, and a write-ahead log plus snapshots if restart durability is required. Concurrent updates need a locking or versioning strategy; RAM residency does not imply atomic multi-key operations.

For messaging, model workspaces, channels, memberships, messages and edits. Persist messages with idempotent client IDs and per-channel ordering, distribute live events over WebSockets, and let reconnecting clients fetch missed history. Search and notification delivery can be asynchronous, while permission checks must remain authoritative.

Shared concerns include authentication, observability and failure recovery, but the consistency contracts differ. A useful interview answer explicitly states assumptions and follows one branch deeply. If asked to cover both, present two bounded designs and explain their different bottlenecks rather than claiming that an in-memory database is sufficient for a complete chat product.

A concrete database branch might support point reads/writes plus atomic transactions on a small set of keys. A write-ahead log records committed changes before acknowledgment; snapshots bound replay time. A hash map makes point operations fast, while range queries require another index. The central tradeoff is isolation and durability cost versus latency, with recovery tests validating the promised contract.

A concrete messaging branch stores each message durably before broadcasting a channel event. Client-generated idempotency IDs handle retries, per-channel sequence numbers support ordering, and reconnecting clients fetch gaps from history. Online fan-out and offline notifications are separate consumers; neither should become the sole copy of the message. Membership changes must govern history and live events consistently.

For both, define failure behavior before adding scale. An in-memory node loss may require log replay or replica promotion; a messaging outage may delay delivery while preserving accepted messages. These are different SLOs and data models. Presenting the two branches separately preserves the original follow-up without implying that one generic box labeled “database” answers both design problems.
