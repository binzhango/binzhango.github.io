## Question

How do you build a simulator you would trust to gate a release?

## Brief answer

Validate the simulator against real measurements for the behaviors it will be used to gate, quantify its limits, and prevent the policy from exploiting simulator artifacts. A useful simulator reproduces relevant sensor, dynamics, interaction, and failure distributions, not merely visually convincing scenes. Its credibility is task-specific.

## Detailed answer

**Suggested approach.** Compare simulated and real trajectories, contacts, detection errors, latencies, and outcome distributions on matched scenarios. Include interactive agents and realistic response to ego actions; replaying fixed other-agent tracks can miss closed-loop effects. Calibrate parameters on one dataset and validate on another.

Create scenario families with controlled perturbations and fault injection, and trace each release gate to a validated simulation capability. Check ranking agreement between policies in simulation and controlled real tests. Record domain gaps and avoid using unsupported scenarios as strong evidence. Periodically test for reward or model exploitation of rendering and physics quirks. Simulator pass rates complement hardware and field evidence; they should not silently substitute for phenomena the simulator cannot reproduce.

### Validate the simulator's decisions, not its appearance

A simulator can render realistic rain while modeling tire friction or another driver's response incorrectly. Define what each release test relies on: sensor noise for perception, dynamics for braking, or interaction behavior for negotiation. Compare those quantities with independent real measurements and quantify error over the operating range.

For a braking scenario, initialize matched speed, road friction, reaction delay, and obstacle motion. Compare stopping distance and timing between simulation and controlled physical tests, then perturb conditions around the boundary. Calibrate on one set and validate on another so agreement is not simply parameter fitting. Check whether two software versions rank similarly in simulation and reality; absolute visual realism does not guarantee useful comparative validity. Version simulator assets, physics, agents, and seeds with each result. Investigate unexpected gains for exploitation of quirks such as unrealistic other-agent braking. Use simulation as strong evidence only for validated phenomena, and retain hardware/field tests for important gaps.
