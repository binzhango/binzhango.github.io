## Question

You're ingesting millions of web pages a day. Detect near-duplicates (same article, different boilerplate) efficiently.

## Brief answer

Strip navigation and repeated site boilerplate, normalize article text, and generate word shingles. Use MinHash with locality-sensitive hashing to propose near-duplicate candidates, then verify actual shingle Jaccard similarity. Retain provenance and canonicalization rules so a syndicated copy does not erase a newer correction or materially different article.

## Detailed answer

The following small core uses 32 MinHash values, eight bands, and exact verification. Production ingestion needs persistent buckets, candidate caps for common content, and streaming document IDs. Python's randomized `hash()` is deliberately avoided so signatures survive process restarts.

```python
import hashlib

def shingles(text, width=5):
    words = text.casefold().split()
    if len(words) < width:
        return {tuple(words)} if words else set()
    return {tuple(words[i:i + width]) for i in range(len(words) - width + 1)}

def signature(parts, size=32):
    if not parts:
        return None
    return tuple(min(int.from_bytes(hashlib.blake2b(
        repr(p).encode(), digest_size=8, key=i.to_bytes(4, 'big')
    ).digest(), 'big') for p in parts) for i in range(size))

def band_keys(sig):
    return [] if sig is None else [(i, sig[i:i + 4]) for i in range(0, 32, 4)]

def duplicate(a, b, threshold=0.85):
    union = a | b
    return bool(union) and len(a & b) / len(union) >= threshold

assert duplicate(shingles('a b c d e f'), shingles('a b c d e f'))
assert not duplicate(set(), set())
```

For each new document, union IDs from matching band buckets, verify candidates, then insert its keys. Signature construction is O(32s) for s shingles; verification costs depend on candidate count. Tune banding on labeled examples because locality-sensitive hashing can miss near-duplicates. Do not interpret high textual overlap as permission to merge different access-controlled records.

### Why candidate generation and verification differ

For ideal independent MinHash components, two sets with Jaccard similarity s agree on a component with probability s. With eight bands of four components, the approximate probability of sharing at least one band is `1 - (1 - s^4)^8`. At s = 0.85 this is about 99.7%; at s = 0.5 it is about 40.3%. The latter is acceptable only because a matching band proposes a candidate rather than declaring a duplicate. The keyed hash family in this small implementation approximates, rather than proves, the ideal independence assumption.

After verification, retain a cluster with separate source URLs and versions. If one publisher corrects a number, preserving only the previously chosen canonical text would lose the correction. For a short document, five-word shingles provide little evidence, so use a separate length-aware rule and exclude empty boilerplate-only pages.

Common navigation text can create enormous buckets. Remove it before fingerprinting, cap candidate work with observable overflow handling, and measure missed duplicates on a labeled sample. Exact verification prevents false merges among examined candidates; it cannot recover a true duplicate that candidate generation never proposed.
