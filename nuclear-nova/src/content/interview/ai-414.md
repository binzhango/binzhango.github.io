## Question

On a GPU, batching amortizes weight reads. What is the batching trade-off on an SRAM-only machine, and how should pricing account for it?

## Brief answer

Batching still amortizes scheduling and computation on SRAM-only systems, but the classic benefit of avoiding repeated HBM weight reads is reduced when weights already reside on-chip. The optimal batch depends on matrix utilization, fabric traffic, cache capacity, and latency targets. Pricing should reflect delivered useful throughput and reserved latency capacity, not assume GPU-style batching economics transfer unchanged.

## Detailed answer

Measure batch-one latency and the throughput curve as concurrency increases. A larger batch may improve arithmetic utilization while increasing queue delay, KV memory, and head-of-line blocking. Static schedules can also have shape or padding costs, so “no need to batch” is too strong.

For pricing, model cost per completed request across input/output lengths and SLO classes. Low-latency reserved service may leave capacity idle and needs a different rate from elastic batch work. Include model placement across many chips, power, failures, and software overhead. Test whether demand can fill the available schedule without violating p99. Use measurements and customer value to choose a price; memory architecture alone cannot determine one.

### Batching still trades latency for utilization

When weights already reside in SRAM, batching is less about avoiding repeated HBM reads. It can still fill matrix units more efficiently, amortize scheduling overhead, and improve aggregate use of a pipeline. Conversely, batching increases live KV state and can require waiting for requests to accumulate. Static shape variants may also pad small batches, wasting scheduled work.

Measure both tokens per second per user and total tokens per second across users. A configuration that doubles total throughput while tripling p99 response time serves a different product. Price a reserved low-latency endpoint using the capacity that must remain available for its SLO, while pricing flexible batch work against more fully utilized capacity. Include cancellation and variable output lengths because they change occupancy. The relevant economic comparison is delivered useful work under a latency commitment, not a claim that one memory hierarchy removes the need for scheduling or allows a universal token price.
