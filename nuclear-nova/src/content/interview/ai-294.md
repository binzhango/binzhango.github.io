## Question

How would you evaluate an agentic coding model on SWE-bench and τ-bench style benchmarks without fooling yourself?

## Brief answer

Fix the environment, harness, tool access, and compute budget, then score final outcomes with hidden checks. SWE-bench-style tests measure whether repository changes resolve an issue; τ-bench-style tasks also require correct state changes and policy adherence through tool interactions. Neither should be reduced to whether the agent sounds confident or reports success.

## Detailed answer

Pin repository commits, dependency images, benchmark revisions, and model versions. Keep test solutions unavailable to the agent and audit leakage from repository history, internet search, and training contamination. Re-run flaky failures and report infrastructure errors separately without selectively dropping difficult examples.

For coding, inspect unintended edits and whether patches hard-code test artifacts. For transactional tasks, verify final database state, required confirmations, and prohibited actions. Run repeated trials with fixed budgets, report confidence intervals and cost, and separate best-of-many from single-attempt results. Keep a private time-separated suite for launch decisions.

### Judge outcomes independently of the agent

For a repository task, provision a clean environment, expose the issue and allowed files, and run the agent under a recorded budget. After it finishes, apply an independent test harness to its patch. Preserve regressions as well as the new task's expected behavior. For a customer-service simulation, compare the final database state and policy-compliant actions against the intended outcome; polite prose cannot compensate for an unauthorized refund.

Calculate success per task, not per tool call, and report the denominator including valid failed attempts. Run multiple seeds to distinguish a reliably solved task from a lucky result. If a tool outage invalidates an attempt, state the rule and rerun every affected case consistently. Keep model and scaffold comparisons separate: a stronger scaffold may add retrieval, extra attempts, or specialized tools that change the problem. Record both quality and consumed tokens, runtime, and interventions so users can reproduce the operational trade-off.
