## Question

Refactor bad code: here are ~120 lines of working but messy code with passing tests. Improve the architecture without breaking them. What do you change first?

## Brief answer

Start by identifying observable behavior and adding characterization tests around untested boundaries. Then make small structural changes that separate decisions from side effects, remove duplication and clarify names. Existing passing tests are necessary evidence but may not cover hidden contracts; avoid a full rewrite before understanding callers and error behavior.

## Detailed answer

The 120-line input is not supplied, so no exact patch can be justified. A concrete refactoring pattern is to extract a pure calculation while preserving the public function and its effects:

```python
def total_cents(lines):
    total = 0
    for price, quantity in lines:
        if type(price) is not int or type(quantity) is not int or price < 0 or quantity < 0:
            raise ValueError('nonnegative integer amounts required')
        total += price * quantity
    return total

def checkout(lines, charge):
    amount = total_cents(lines)
    charge(amount)
    return amount

calls = []
assert checkout([(125,2),(50,1)], calls.append) == 300
assert calls == [300]
```

In the actual code, first preserve existing validation and rounding semantics rather than introducing the illustrative policy above. Move one seam at a time, rerun tests and inspect the diff. Prefer dependency injection for clocks, network calls and storage. Only introduce classes or abstractions when they represent real variation; fewer lines or more patterns are not evidence of improved architecture.

Characterization tests capture the behavior that callers currently observe, including awkward error messages, ordering and rounding. Before extracting a function, identify whether it reads time, mutates shared state, performs network calls or depends on implicit globals. A pure calculation can then be separated from those effects without changing the public contract.

The example's `total_cents` is easy to test because its result depends only on input, while `checkout` owns the charge effect. The injected `charge` function makes it possible to verify exactly one call with the expected amount. This is a demonstration of a seam, not a prescription to add new validation to unknown existing code.

Refactor in small commits or reviewable steps, keeping tests green and inspecting diffs for accidental behavior changes. Test boundaries that existing examples miss before removing a branch that looks redundant. Only after structure is clearer should behavior changes be proposed separately. Improved architecture should reduce coupling and make future changes safer; a larger abstraction layer or fewer lines is not an adequate success metric.
