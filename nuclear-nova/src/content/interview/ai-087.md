## Question

Design a red-teaming programme for a model you are about to release.

## Brief answer

Build a red-team program around concrete assets, misuse paths and deployment boundaries, with reproducible tests and a process for fixing findings. Include both model-only behavior and the full tool-enabled application.

## Detailed answer

Recruit varied expertise, define safe test environments and prioritize high-impact scenarios. Exercise indirect injection, data leakage, unauthorized actions, evasion and resource exhaustion across languages and long sessions. Record severity, reproducibility and affected versions; turn confirmed findings into regression tests. Retest mitigations against adaptive variants. Red teaming complements routine evaluation and incident response; absence of discovered failures is not evidence that none exist.

Start with an asset and capability inventory: sensitive data the model can read, tools it can execute, destinations it can contact and decisions users may rely on. Turn that inventory into scenarios with a legitimate task and an adversarial objective. This makes a finding actionable: “an injected document caused an unauthorized export” is more useful than “the model produced a strange answer.”

Run tests in controlled environments with realistic tools, permissions and data fixtures. Include domain experts, security engineers and speakers of supported languages. Explore single-turn attacks, indirect content, long conversations, repeated attempts and combinations of otherwise harmless steps. Record the full reproducible input, environment version, observed effect and severity without exposing real user data.

Triage findings by impact and reachability, assign an owner, implement a mitigation and retest adaptive variants. A defense that blocks one string may leave the same attack path open with different wording. Convert confirmed failures into regression cases while preserving fresh adversarial exploration. Release decisions should consider residual risk, monitoring and incident response, not only the count of discovered issues. Red teaming can demonstrate that a failure exists; failing to find one does not establish that the system is safe under every future input.
