## Question

Design the serving stack for a Claude-scale LLM API. Maximise GPU utilisation without wrecking p99 latency.

## Brief answer

Use a regional gateway, token-aware admission, model-specific routing and GPU replicas running continuous batching with paged KV storage. Separate prefill-heavy and decode-heavy work when measurements justify the added coordination. Optimize useful tokens per GPU-second subject to time-to-first-token and inter-token p99 targets; utilization alone rewards queues that users experience as slowness.

## Detailed answer

Suggested architecture: authenticate and meter at ingress, estimate prompt/output budgets, then route to a healthy replica with available KV capacity. Keep streaming connections at a gateway decoupled from model workers. The scheduler uses token budgets and fairness across tenants, chunks long prefills and cancels abandoned requests promptly.

Replicas combine tensor parallelism within a fast interconnect and replication across failure domains. Prefix caching helps repeated prompts but needs tenant isolation and versioned cache keys. Quantization and speculative decoding require quality and workload-specific speed measurements. If prefill and decode are disaggregated, include KV transfer latency and bandwidth in the capacity model.

Measure queue wait, prefill time, decode step time, KV fragmentation and error rates by length and model tier. Autoscaling must account for model-load delays; reserve warm capacity and shed excess load explicitly. This is a proposed stack for the stated scale, not a claim about a provider's internal implementation.

Set latency classes before maximizing occupancy. A batch job can wait longer and tolerate large output batches, while interactive streaming needs bounded gaps. Separate queues or weighted admission prevents background work from consuming all KV space and causing interactive timeouts. Prompt length and expected output tokens are better scheduling signals than request count alone.

A cache-aware router should balance prefix reuse against queue depth: sending every request with a common prefix to one hot worker can worsen latency despite an excellent hit rate. Likewise, maximizing GPU utilization can be harmful when it leaves no headroom for bursts or long-prefill work. Track accepted load and rejected requests so overload is visible.

Failure tests should include a worker dying mid-stream, a slow tensor-parallel rank, an exhausted KV pool and a reconnect storm. Keep generation state distinct from confirmed tool effects. The capacity target is sustained completed work within SLOs under normal failure assumptions, with a cost model that includes warm replicas and spare capacity rather than only steady-state kernel efficiency.
