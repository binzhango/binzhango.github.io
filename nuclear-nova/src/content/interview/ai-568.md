## Question

Modular perception, prediction and planning, or end-to-end learned driving? Make the case, then tell me what you would actually build.

## Brief answer

A modular stack offers inspectable interfaces, targeted testing, and explicit constraints; an end-to-end learned stack can optimize representations jointly and reduce hand-engineered bottlenecks. I would choose a hybrid with learned perception/prediction or planning where justified, plus independent constraint checking, fallback behavior, and a clear safety case for the intended operating domain.

## Detailed answer

**Suggested approach.** Define the driving domain, sensors, compute, failure response, and evidence requirements before selecting architecture. Use structured intermediate outputs where they improve diagnosis and verification, but avoid forcing every useful learned feature into a brittle hand-designed schema. Compare closed-loop behavior, not just offline perception or imitation metrics.

Evaluate rare interactions, uncertainty, sensor faults, and out-of-domain conditions. Maintain traceability from a bad maneuver to evidence about perception, prediction, planning, and execution even if some components are jointly trained. The tradeoff is integration complexity versus interpretability and controllability. A fashionable architecture is not a release argument; the chosen system must demonstrate safe behavior within its actual deployment envelope.

### Choose interfaces that make failures observable

A modular pipeline can expose object tracks, predicted futures, candidate plans, and control commands. That helps determine whether a poor maneuver came from missing an actor, predicting the wrong intent, or choosing an unsafe plan despite correct inputs. Its weakness is that hand-designed interfaces may discard uncertainty or useful sensor information before downstream components can use it.

An end-to-end model can optimize internal representations for driving behavior directly, potentially avoiding those bottlenecks. However, diagnosing an error or validating behavior under a particular fault becomes harder if the only observable output is an action sequence. Auxiliary outputs and targeted probes can improve observability without proving that a verbal explanation faithfully describes the model's computation.

I would begin with the intended operating domain and evidence requirements, then use learned components where they demonstrate closed-loop benefit. Preserve explicit action constraints, a tested fallback path, and instrumentation sufficient to investigate failures. These components also need validation; calling a checker independent does not guarantee that it detects every hazard.

Compare architectures on the same scenario set, hardware budget, and failure conditions. Include sensor degradation, unusual interactions, and out-of-domain detection. A lower imitation loss or better object-detection score can coexist with worse driving, so require end-to-end behavioral evidence before changing the production architecture.
