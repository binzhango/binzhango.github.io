## Question

Kimi's headline feature is very long context. When you push from 8K to hundreds of thousands of tokens, what actually breaks first, and why?

## Brief answer

The first bottleneck depends on hardware and attention implementation: prefill latency, KV-cache capacity, attention bandwidth during decode, or positional generalization can fail first. Dense attention's arithmetic grows quadratically with sequence length, while the KV cache grows linearly. A model accepting a large input does not prove it can reliably use information throughout it.

## Detailed answer

Measure three independent curves as input length increases: memory occupancy, time to first token, and task quality. Flash-style attention avoids materializing the full attention matrix, but does not remove the quadratic arithmetic of dense prefill. Decode reads an expanding cache; longer histories reduce the number of concurrent requests that fit and increase token latency.

On the modeling side, positions and relative distances may be outside the training distribution. Distractors, conflicting documents, and middle-of-context evidence expose failures that a single needle lookup misses. Test retrieval, multi-hop synthesis, ordering, and contradiction handling at different evidence positions. Use efficient attention, context parallelism, cache compression, or retrieval according to the measured constraint.

### Scaling from 8K to 128K

Multiplying sequence length by sixteen multiplies full attention's pair count by approximately 256, and cache storage by sixteen at fixed model and batch. For an illustrative GQA model with 32 layers, eight KV heads, head dimension 128, and two-byte cache elements, each cached token needs 131,072 bytes. An 8,192-token request uses 1 GiB; 131,072 tokens use 16 GiB before allocator and runtime overhead. This alone can drastically reduce concurrency.

Identify the first failure experimentally. Out-of-memory at low concurrency suggests capacity; rising first-token latency with acceptable memory suggests prefill work; slow inter-token output suggests cache reads or communication. Stable performance but wrong answers near particular positions suggests modeling rather than systems failure. Optimizations address different axes: paged caches reduce fragmentation, flash attention reduces intermediate storage, positional adaptation improves usable distances, and retrieval reduces input length. None is a substitute for measuring all three curves.
