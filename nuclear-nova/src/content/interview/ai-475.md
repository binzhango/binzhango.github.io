## Question

How would you index a 100k-file monorepo so an AI editor can retrieve relevant context, and keep the index fresh as the user edits?

## Brief answer

Build an incremental hybrid index combining filenames, symbols, references, lexical text, and semantic chunks. Keep a persistent committed-base index plus a fast overlay for unsaved edits. Query both and let the overlay shadow older versions, so the editor never retrieves stale content for the file the user is actively changing.

## Detailed answer

**Suggested approach.** Exclude generated/vendor artifacts according to repository rules, parse source into functions and classes, and attach path, language, symbol, commit, and content hash. File watchers enqueue debounced updates; periodic reconciliation catches missed events, renames, and branch changes. Reuse unchanged hashes to avoid re-embedding a 100,000-file tree.

Route exact identifiers through lexical/symbol search and semantic intent through embeddings; expand promising results along imports and call references. Bound each query's context assembly budget. Measure indexing lag, coverage, relevant-symbol recall, and downstream edit success. Test symlink loops, large generated files, unsupported syntax, partial saves, and checkout changes. Store repository and permission boundaries in index identity so content cannot leak between workspaces.

### Keep the index consistent with editor state

Represent each indexed unit with workspace ID, branch or base commit, path, content hash, symbol range, and parser version. The committed index handles most of the repository, while an overlay maps modified paths to their newest parsed contents. Query merging suppresses base-index results for every path present in the overlay, including deleted files. Otherwise a user deleting a function can still receive that function as retrieved context.

A save emits an event, but event delivery is not authoritative: watchers can miss bursts or branch checkouts. Periodic hash reconciliation discovers discrepancies and creates replacement index entries. Publish replacements atomically by file revision, so a query does not combine a new function body with old symbol offsets from the same file.

For a renamed API, exact symbol search locates the declaration, reference edges find callers, and semantic search contributes tests or documentation that use descriptive language. Keep these retrieval reasons in the trace. The main tradeoff is between rapid, partial parsing of active files and more expensive whole-repository analysis; favor current local evidence while backfilling deeper relationships asynchronously.
