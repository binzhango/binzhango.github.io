## Question

Implement beam search for an autoregressive model. When would an answer engine actually use it?

## Brief answer

Beam search keeps the best partial sequences under a defined score, expands them, and prunes to a fixed beam width. It is useful for constrained, relatively deterministic outputs or candidate generation, but maximizing sequence likelihood does not guarantee factuality or citation quality. An answer engine often prefers sampling or greedy decoding with verification.

## Detailed answer

This reference implementation expects `next_log_probs(prefix)` to return `(token, log_probability)` pairs. It uses raw summed log probabilities, includes completed hypotheses in beam competition, and stops at EOS or a token limit. The score convention is explicit because length normalization changes rankings.

```python
def beam_search(next_log_probs, start=(), eos='<eos>', width=3, max_new=20):
    if width < 1 or max_new < 0:
        raise ValueError('invalid search limits')
    beam = [(tuple(start), 0.0, False)]
    for _ in range(max_new):
        candidates = []
        for tokens, score, done in beam:
            if done:
                candidates.append((tokens, score, True))
            else:
                for token, logp in next_log_probs(tokens):
                    candidates.append((tokens + (token,), score + logp, token == eos))
        if not candidates:
            raise ValueError('model returned no candidates')
        beam = sorted(candidates, key=lambda x: x[1], reverse=True)[:width]
        if all(done for _, _, done in beam):
            break
    return max(beam, key=lambda x: x[1])[0]

assert beam_search(lambda p: [('<eos>', -0.1), ('x', -2.0)]) == ('<eos>',)
```

With T steps, beam width B, and vocabulary V, naive expansion stores O(BV) candidates per step; production systems use top-k kernels and shared KV prefixes. Test EOS on the first step, width one, tied scores, and a model that never emits EOS. Finished and truncated outputs should be distinguished by callers.

### A small search trace

Suppose the first step offers A with probability 0.6 and B with 0.4. Greedy decoding keeps A. A width-two beam keeps both. If A's best completion has conditional probability 0.5, its joint probability is 0.30. If B's best completion has probability 0.9, its joint probability is 0.36, so the beam can return the B path that greedy search discarded. Adding log probabilities implements multiplication without numerical underflow.

This does not make beam search globally exact: a promising prefix removed by pruning can never return. Raw sequence probability also tends to favor short outputs because every added token contributes a nonpositive log probability. Length normalization changes that preference but is a different objective, with additional decisions about comparing completed and active hypotheses.

Ignoring model-forward cost, this implementation sorts up to B times V candidates for each of T steps, costing O(TBV log(BV)); copying token tuples adds sequence-length overhead. A production decoder avoids full candidate materialization and reuses KV prefixes. For an answer engine, a high-likelihood false statement still ranks highly unless groundedness is checked separately. Use beams where structured alternatives and a downstream verifier justify the extra work.
