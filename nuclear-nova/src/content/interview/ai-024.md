## Question

Estimate the GPU memory needed to serve a 70B model: weights, KV cache, activations, fragmentation.

## Brief answer

For 70 billion parameters, raw weights require about 140 GB at two bytes per parameter or 35 GB at four bits, before quantization metadata. Add KV cache, activations, temporary workspaces, allocator slack and replication effects.

## Detailed answer

As an illustrative configuration, 80 layers, eight KV heads and head dimension 128 require $2\times80\times8\times128\times2=327{,}680$ cache bytes per token at BF16. An 8,192-token sequence uses 2.5 GiB, so 16 such sequences need 40 GiB of KV alone. Quantized weight size does not imply quantized KV. Confirm the actual architecture and whether the runtime shards or replicates KV before dividing memory across devices. Capacity planning also needs a safety margin for the longest admitted requests.

Build the estimate as a ledger. Raw BF16 weights are 140 billion bytes, approximately 130.4 GiB. Sixteen 8,192-token sequences add 40 GiB of KV for the stated architecture, bringing weights plus cache to about 170.4 GiB before any workspace. Two 80-GiB devices therefore cannot hold that illustrative combination even if tensor sharding is ideal. Quantizing the weights to a raw 35 GB changes the weight term, not the 40-GiB cache term.

Next measure peak temporary memory during the longest permitted prefill. Activations, attention workspaces, CUDA graph pools, communication buffers and runtime metadata vary with engine and kernel choices, so a universal percentage is unreliable. Reserve additional room for partial cache blocks and transient allocations; running at the theoretical limit risks out-of-memory failures on perfectly valid requests.

Admission control should account for prompt tokens, reserved generation growth and per-tenant limits. If a request asks for an additional 8,192 output tokens, its eventual KV footprint doubles under full attention. Shared prefixes reduce incremental storage only when the engine genuinely shares compatible blocks. Validate the spreadsheet against measured peak allocation for cold starts, maximum concurrency and long generations, then choose a headroom policy from the observed peaks rather than advertised accelerator capacity alone.
