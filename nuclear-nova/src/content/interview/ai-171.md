## Question

You are building a production agent that calls tools (function calling). What makes the loop reliable enough to ship?

## Brief answer

Reliability comes from a constrained execution protocol around the model: typed tool requests, authorization, bounded retries, idempotent writes, timeouts and explicit terminal states. Validate the result of an action instead of assuming a well-formed tool call succeeded. Persist state so interruption cannot cause the same side effect to be repeated blindly.

## Detailed answer

Suggested loop: build context, request a model action, validate its schema, check policy, execute with a deadline, append a structured observation and decide whether to continue. Separate read-only tools from consequential writes. Use operation IDs and external reconciliation when a timeout leaves the result unknown.

Prevent loops with step, token and wall-clock budgets. Tool errors should identify retryable versus permanent failures without leaking credentials. Treat retrieved content as data and restrict network, filesystem and account authority outside the model. Human approval must cover the actual action and parameters where the workflow requires it.

Evaluate full tasks with injected failures: stale records, malformed arguments, duplicate responses, unavailable services and malicious tool output. Track completed user goals, unauthorized attempts and recovery success. A high function-call JSON validity score is useful but far short of evidence that the agent safely completes work.

Persist the loop as a state machine rather than only an in-memory message list. Before a consequential tool call, record the intended action, validated arguments and operation ID. After execution, record a confirmed result or an uncertain state requiring reconciliation. This closes the crash window in which a remote action succeeds but the agent forgets it and tries again.

Separate syntax, semantics and authority checks. Valid JSON can request an impossible date; valid business arguments can still target an account the user does not own. Tool observations should say what actually happened and whether retry is safe, without allowing returned text to change the host's permission policy.

Test the full workflow under dropped responses, duplicate calls, stale versions, cancellation and malicious evidence. Verify environment state as well as final language. Track false success claims and duplicate effects as first-class failures. Reliability is demonstrated when the system reaches the intended outcome or accurately reports why it cannot, within bounded time and cost—not when every model response merely fits a tool schema.
