## Question

Design the tool surface for a coding agent: which tools exist, what their schemas look like, and how results come back.

## Brief answer

Expose a small, explicit tool surface for reading, searching, editing, executing tests and inspecting diffs. Each tool needs typed arguments, a permission boundary and structured results. Prefer operations with narrow intent—such as applying a patch—over a universal shell when a narrower tool can express the action and report failures clearly.

## Detailed answer

Suggested interfaces include `read_file(path, start_line, limit)`, `search(query, paths)`, `apply_patch(patch)`, `run(command, cwd, timeout)` and `diff(paths)`. Results should carry status, bounded output, truncation information and stable handles for long-running jobs. File operations resolve paths inside the authorized workspace and reject traversal outside it unless explicitly permitted.

Edits should fail on stale context rather than silently overwrite a changed file. Execution needs cancellation, time limits and output limits; a zero exit code is one observation, not proof that the requested behavior works. Tool schemas should distinguish absent values from empty strings and provide concrete validation errors.

For writes outside the workspace or external publication, make authorization explicit in the host policy. Treat repository text and process output as data, including instructions embedded in README files or test failures. Log arguments and outcomes while redacting secrets. More tools are useful only if their distinctions improve reliability or reduce authority.

Tool design should make safe behavior easy to express. A patch tool can require expected surrounding text or a file hash, making concurrent changes an explicit conflict. A process tool can return a job handle, exit status and bounded output, allowing cancellation and later polling without rerunning the command. A search tool can return path and line metadata so evidence remains locatable.

Keep user-visible intent separate from raw execution. The host determines whether an operation is allowed in the workspace or requires additional authorization; a model-provided boolean such as `approved: true` is not authority. Restrict environment variables and credentials available to child processes, and avoid logging secrets in command arguments or output.

Test schema misuse, path traversal, stale patches, huge results and canceled commands. A tool should return enough information to recover without hiding whether a mutation occurred. For example, a timeout after writing a file differs from a failure before opening it. These contracts reduce ambiguity in the agent loop and make both automated evaluation and human review more reliable.
