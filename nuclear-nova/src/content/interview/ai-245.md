## Question

You have four hours to build and demo a working AI-powered product. How do you spend them?

## Brief answer

Choose one narrow user problem and build a complete, demonstrable path with a clear acceptance test. Allocate time to integration and failure handling early; a collection of unfinished features is difficult to evaluate in a four-hour demo.

## Detailed answer

One reasonable allocation is 30 minutes for requirements and a baseline, 90 minutes for the core flow, 60 minutes for integration/error cases, and 60 minutes for evaluation, polish and rehearsal. Adjust it when a risky dependency needs an earlier spike. Use existing authentication and managed components where appropriate, and keep credentials out of the client. Prepare a few representative and adversarial inputs, plus an honest fallback for unavailable services. The demo should show a real input reaching a useful output, with latency and limitations visible. Label mocked components clearly and explain the next engineering risk rather than implying production readiness.

### Choose the smallest complete value loop

A document-question assistant might accept one file, retrieve a relevant passage, answer one question, and show the evidence used. That is a more useful four-hour scope than accounts, dashboards, uploads, agents, and analytics all partly implemented. Define two or three acceptance examples before coding, including an unsupported question that should produce an honest limitation.

Validate the riskiest dependency first: credentials, file parsing, or model connectivity can consume the whole demo window if deferred. Build a vertical slice, then add input validation, bounded timeouts, clear errors, and a stable sample dataset. Reserve time to run the exact demo path from a clean state and rehearse one failure case. Keep secrets server-side and label any fixtures or mocked services explicitly. Explain what works today and the next engineering constraint, such as permissions or evaluation coverage. A demo proves one path can produce value; it does not establish reliability across users, data, and production load.
