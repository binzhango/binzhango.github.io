## Question

A Structured Streaming job reads Kafka and writes to a Delta table. The cluster is killed mid-batch and restarts. Does the customer get duplicate rows? Explain at the level of the checkpoint and the transaction log.

## Brief answer

With a replayable Kafka source, durable checkpoint, and native Delta streaming sink, a restarted microbatch can be replayed without committing its output twice. Spark tracks batch/source progress, while Delta's transaction log records sink commits. This is not a blanket guarantee against duplicate business events, and arbitrary `foreachBatch` writes require explicit idempotency.

## Detailed answer

If failure occurs before the Delta commit, replay writes the batch normally. If the Delta commit succeeded but Spark did not record completion, recovery may attempt the same batch; the sink's transaction identity lets it recognize the committed write. Uncommitted data files are not visible as table rows merely because they exist in storage.

Preserve the checkpoint identity and compatible query configuration, and retain Kafka data long enough for recovery. Deleting the checkpoint or starting a new query can reprocess data. Producer duplicates need event-level deduplication independent of processing guarantees. In `foreachBatch`, use appropriate transaction IDs or an idempotent merge; writes to multiple tables are not automatically one atomic transaction.

### Exactly once has a defined boundary

Spark records source offsets and progress in the checkpoint. A microbatch computes output for a known input range, and the Delta sink commits a transaction with a query/batch identity. The table's transaction log determines which files are visible. On restart, the query may redo computation, but the sink can recognize an already committed batch and avoid appending the same batch twice.

This is different from every business event being unique. If Kafka contains two records for the same purchase, processing each exactly once still yields two records unless the application deduplicates by event identity. Nor does a transactional table commit make an external email or second database write atomic. A `foreachBatch` callback needs its own idempotency design, especially across multiple destinations. Test crashes before file creation, before commit, after commit but before checkpoint completion, and during recovery. Preserve checkpoint storage and source retention; deleting recovery state changes the guarantee and can force replay from a different boundary.
