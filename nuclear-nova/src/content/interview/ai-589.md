## Question

Your platform must support multiple LLM providers, including deployments in restricted environments where only some models are available. How do you architect model selection?

## Brief answer

Create a capability-aware model gateway with explicit deployment eligibility, typed adapters, and task-based routing. Separate hard constraints such as data location, allowed providers, tools, and context size from optimization goals such as quality, latency, and cost. A fallback is valid only if it satisfies the same hard constraints.

## Detailed answer

**Suggested approach.** Maintain a versioned registry of model endpoints, supported features, evaluated task performance, limits, and permitted environments. Normalize requests and responses at the boundary while preserving provider-specific semantics that matter, such as tool behavior or token accounting. Pin versions for reproducibility and log the routing decision without exposing sensitive prompts.

Run contract tests and task evaluations for each eligible route. In restricted environments, support local adapters and clearly report when a required capability has no approved implementation. Use circuit breakers and bounded retries, but never fail over confidential data to an unapproved public endpoint. Measure task success, latency, cost, and route-specific regressions. The abstraction should make differences manageable, not pretend all models are equivalent.

### Select from an eligible set first

For each request, derive hard requirements such as data location, permitted providers, context capacity, modality, tool support, and deadline. Filter the endpoint registry by those constraints before comparing cost or evaluated quality. A fast unavailable or unapproved model is not a fallback candidate. If the eligible set is empty, return a clear unsupported-capability result or a narrower approved workflow.

Provider adapters should normalize common fields while exposing meaningful differences: schema support, streaming events, token limits, error semantics, and reasoning modes. Keep prompt/template bundles tied to each model version. A circuit breaker can remove an unhealthy route, but must not widen the data-disclosure policy. Use task-specific evaluations to choose routes and log the decision with minimal metadata. In restricted installations, ship local artifacts and dependencies through the approved update path and test without external network assumptions. Monitor quality and latency by route so aggregate metrics cannot hide one provider's regression.
