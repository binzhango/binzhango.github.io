## Question

Why evaluate RAG?

## Brief answer

Evaluate RAG to determine whether failures come from missing sources, retrieval, context assembly, generation, or the overall application.

## Detailed answer

A good answer metric alone cannot explain why a system failed. Measure evidence coverage and rank before generation, then answer correctness, support, citation quality, and abstention. Include latency, cost, permission enforcement, and freshness. Use realistic questions and source snapshots so results are reproducible and changes to ingestion or indexing can be regression-tested.

Decompose an answer failure into observable questions. Did an authorized source contain the answer? Did parsing preserve it? Did retrieval return it at a useful rank? Did context assembly retain the necessary qualification? Did the generator use it correctly and cite it? This sequence identifies a repairable stage instead of treating every failure as “the LLM hallucinated.”

For example, a wrong warranty answer may result from an omitted exception in the parsed PDF. Switching embedding models cannot recover text that never entered the index. Conversely, if the exact exception is in the prompt but ignored, retrieval may already be adequate. An oracle-context test helps distinguish those cases.

Maintain a versioned set of realistic questions with source snapshots, support judgments, and expected behavior for absent evidence. Include permissions, freshness, conflicting sources, multi-hop questions, and numerical tables. Measure latency and cost alongside quality so a gain from many extra retrieval calls is visible. Evaluation supports engineering decisions only when stage outputs are retained and comparable across versions, rather than relying on an opaque overall score.
