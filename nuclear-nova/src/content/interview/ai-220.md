## Question

What breaks when you scale LLM training from 8 GPUs to thousands, and how do modern stacks deal with it?

## Brief answer

At thousands of GPUs, communication, failures, load imbalance and orchestration become first-order costs. Small per-rank inefficiencies accumulate, and the slowest participant can stall a collective. Modern stacks combine topology-aware parallelism, communication overlap, sharded state, reliable checkpointing and detailed per-rank telemetry to maximize useful training progress rather than nominal device utilization.

## Detailed answer

Start from a single-node profile and identify which tensors cross which links. Tensor parallelism communicates frequently and benefits from fast local interconnects; pipeline parallelism introduces bubbles and stage imbalance; data parallelism synchronizes gradients; expert parallelism adds all-to-all traffic and routing skew. Their composition must match the network topology.

Scale the input pipeline and checkpoint system too. A GPU fleet waiting on storage or restoring incompatible shards has poor goodput even if its kernels are fast. Use validated distributed checkpoints, deterministic data-position recovery, health checks and a policy for replacing failed ranks or restarting groups.

Check convergence as global batch size grows: learning-rate schedules and optimization noise can change, so linear throughput scaling is not the same as equal time to quality. Run staged scale tests and inject failures before the largest run. Track tokens contributing to accepted optimizer steps, lost work, recovery time and straggler distributions alongside FLOP utilization.

At large scale, step time is often determined by the slowest participating rank. A small per-device probability of transient failure or slowdown becomes a frequent fleet event, and synchronous collectives propagate the delay. Instrument rank-level compute, communication and input stalls so averages do not hide the culprit.

Design checkpoints around useful progress and recovery cost. More frequent checkpoints reduce lost steps but consume storage bandwidth; asynchronous staging helps only if it does not exhaust memory or contend with training. Verify that all shards represent one consistent step and that data-loader position and RNG state resume correctly.

Scale in stages while checking convergence at the new global batch and parallelism layout. Communication overlap can improve throughput, but a bug in synchronization can silently change training semantics. Failure injection should include rank loss, slow storage and checkpoint corruption before a long expensive run. Report goodput as accepted training progress over wall time, including downtime and replayed work, so an impressive steady-state utilization number does not conceal poor end-to-end efficiency.
