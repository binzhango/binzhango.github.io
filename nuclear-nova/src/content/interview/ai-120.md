## Question

Build core business logic for a toy banking application: a spec that grows in four progressive levels against a black-box evaluator.

## Brief answer

Treat the progressive banking task as an evolving state machine with explicit invariants: nonnegative balances, atomic transfers, stable account identity and deterministic ranking. Keep parsing separate from operations so new levels add behavior without rewriting earlier contracts. The original black-box specification is missing, so the implementation below states a concrete core rather than guessing its exact evaluator.

## Detailed answer

Assume integer minor currency units, unique account IDs, deposits and same-currency transfers. Invalid operations fail without changing state.

```python
class Bank:
    def __init__(self): self.balance, self.outgoing = {}, {}
    def create(self, account):
        if account in self.balance: return False
        self.balance[account] = self.outgoing[account] = 0
        return True
    def deposit(self, account, amount):
        if account not in self.balance or type(amount) is not int or amount <= 0: return False
        self.balance[account] += amount; return True
    def transfer(self, source, target, amount):
        if source == target or source not in self.balance or target not in self.balance: return False
        if type(amount) is not int or amount <= 0 or self.balance[source] < amount: return False
        self.balance[source] -= amount; self.balance[target] += amount
        self.outgoing[source] += amount; return True
    def top_spenders(self, n):
        return sorted(self.outgoing, key=lambda a:(-self.outgoing[a], a))[:n]

b = Bank(); assert b.create('a') and b.create('b')
assert b.deposit('a', 10) and b.transfer('a', 'b', 4)
assert not b.transfer('a', 'b', 20)
assert b.balance == {'a':6, 'b':4}
```

For later levels, model scheduled payments as timestamped events with unique IDs and a defined ordering relative to commands at the same timestamp. Account merging needs historical identity rules and cancellation semantics. Add characterization tests for each level before extending the model; conservation across transfers and failure atomicity are stronger checks than example outputs alone.

The transfer operation validates both identities, amount type and available funds before changing either balance. This ordering preserves failure atomicity: a rejected operation leaves the state untouched. For a successful transfer, the sum of balances is unchanged, while the sender's cumulative outgoing amount increases. Deposits deliberately change total funds because they represent money entering the toy system.

Keep later requirements as explicit transitions on the same invariants. A scheduled payment needs due time, status and a stable ID; cancellation must specify whether it can occur at the exact execution timestamp. Account merging must define how balances, outgoing rankings and pending events follow identity changes. Do not infer these semantics from a few black-box examples when the prompt is incomplete.

Dictionary operations are expected $O(1)$, while `top_spenders` sorts all accounts in $O(n\log n)$. Test equal spending with deterministic ID ties, insufficient funds, self-transfer and duplicate creation. This is single-process interview logic; concurrency, durable ledgers and reconciliation are additional requirements for any real financial system.
