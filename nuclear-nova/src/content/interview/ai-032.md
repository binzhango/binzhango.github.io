## Question

What chunking strategy would you use for a large technical documentation corpus, and why?

## Brief answer

Chunk technical documents along semantic boundaries such as headings, procedures and code examples, retaining hierarchy and stable source offsets. Tune size and overlap against retrieval and answer quality rather than choosing one universal token count.

## Detailed answer

Preserve a complete function or table when feasible, and attach parent headings to ambiguous fragments. Index compact child passages while retrieving surrounding parent context after a hit. For example, a configuration option needs both its name and the caveat in the next paragraph. Evaluate retrieval recall, duplicate context and citation precision across manuals and release versions. Handle oversized units explicitly; claiming both a hard size limit and never splitting an arbitrarily large unit is impossible.

Start from the document structure rather than fixed character counts. Preserve titles, heading paths, numbered steps and code-block language. A passage explaining `timeout_ms` should carry its product/version heading and the unit, otherwise retrieval may match an identically named option in a different component. Keep chunk provenance as document revision plus exact source offsets.

A useful design indexes compact child chunks and stores their parent sections. Retrieval finds the precise child, then context assembly includes nearby prerequisites or warnings from the parent within a token budget. For a procedure, splitting between “disable the service” and “restore it after migration” can make a retrieved fragment dangerous even if the fragment is semantically relevant. Tables need repeated headers when divided by rows; code should be split at syntax boundaries where possible.

Choose candidate sizes and overlap through an experiment on answerable queries. Compare evidence recall, duplicate tokens, answer support and latency, with separate results for API reference pages, tutorials and release notes. Overlap can repair boundary losses but also crowds the context with repeated passages. For an oversized semantic unit, explicitly choose structured subdivision or an oversized exception; do not promise both an absolute size cap and an unsplittable unit of arbitrary length.
