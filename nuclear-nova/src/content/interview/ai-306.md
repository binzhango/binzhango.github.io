## Question

Why is tokenization the first bottleneck for Indian-language LLMs, and how does a low-fertility tokenizer change the economics?

## Brief answer

Tokenization can be an important bottleneck when a tokenizer fragments Indic text into many pieces, but it is not necessarily the first bottleneck for every language or task. Lower fertility can reduce tokens, prefill work, KV memory, and effective context consumption. Data quality, coverage, and multilingual training still determine whether those cheaper tokens yield useful answers.

## Detailed answer

Compare the same meaning across languages using native translations, then measure tokens per word and per character with appropriate segmentation. Inspect combining marks, mixed scripts, transliteration, proper names, and numeral handling. Avoid normalization that changes spelling or meaning merely to improve the metric.

Suppose a passage requires 1,500 tokens with one tokenizer and 900 with another. Input-token volume falls 40%, but latency does not necessarily fall 40% because attention, batching, and model architecture also change. A larger vocabulary increases embedding and output cost. Replacing a tokenizer in an existing model requires adaptation and can disrupt learned representations. Select the tokenizer using end-to-end native-language quality per cost, including decoding and context truncation, rather than fertility alone.

### From fragmentation to user-visible cost

Suppose an English-oriented tokenizer breaks a Hindi word into several subword or byte tokens while a better-covered tokenizer represents it with fewer pieces. The longer sequence consumes more context, more decoding steps for generated text, and more attention work. A fixed 4,096-token window may then hold less useful semantic content in Hindi than English, creating an access and quality gap beyond billed token count.

Tokenization is not always the first bottleneck: poor native training data, weak reasoning, ASR errors, or unavailable product evidence can dominate. Diagnose with matched-content experiments and an oracle translation baseline rather than assuming every language error is fragmentation. If adapting a tokenizer, preserve compatibility where possible, initialize added embeddings deliberately, and continue training on both new-language and existing-language data. Test code-switching and exact entity copying after adaptation; a lower fertility score is not worth introducing corruption in names, amounts, or source identifiers.
