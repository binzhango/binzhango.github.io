## Question

An enterprise customer wants to deploy your RAG system but has no labelled data. How do you evaluate it before and after launch?

## Brief answer

Start with a small, representative human-reviewed task set and an explicit rubric for evidence sufficiency, answer support and acceptable abstention. No existing labels means evaluation data must be created, not that launch quality can be inferred from a polished demo.

## Detailed answer

Ask domain owners for common questions and costly failure cases, then sample actual documents to include stale, contradictory and inaccessible evidence. Double-review a subset to identify ambiguous judgments. Use synthetic queries to broaden development coverage, but retain expert-reviewed examples and real user tasks for acceptance. Evaluate retrieval with relevance judgments and generation with known-good context before scoring the whole pipeline. After launch, sample representative traffic plus incidents, respecting privacy and retention constraints. Track uncertainty and reviewer effort; weak automated labels or an uncalibrated LLM judge should not be described as ground truth.

### Create a small trustworthy benchmark first

Ask domain owners for common tasks and expensive mistakes, then collect questions with expected supporting passages and required answer facts. Include answerable, ambiguous, unsupported, outdated, and unauthorized cases. A useful initial set can be modest if carefully reviewed; label quality and coverage matter more than a large automatically generated score.

Evaluate retrieval separately by whether sufficient evidence appears at the chosen depth. Evaluate generation with known-good evidence to identify hallucination or instruction failures. Then test the combined system and record failure categories. Synthetic questions can exercise document coverage but often mirror source wording too closely, so retain native user tasks as an independent gate. After launch, sample ordinary sessions and high-severity incidents under privacy controls, adjudicate disagreements, and update a development set while preserving a holdout. Calibrate any LLM judge against human review and report uncertainty. No labels means part of the deployment work is building evidence about quality, not replacing evaluation with user enthusiasm.
