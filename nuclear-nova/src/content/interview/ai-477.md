## Question

Your agent model outputs an edited version of a 500-line file. Applying it verbatim is slow and error-prone. How do you make “apply” fast and reliable?

## Brief answer

Turn the generated full file into a minimal diff against its base version, validate that diff, and apply it transactionally to the current buffer. Use exact anchors and three-way reconciliation when the user has edited concurrently. Do not ask another model to blindly “apply” text when deterministic diffing can preserve unchanged regions.

## Detailed answer

**Suggested approach.** Normalize only agreed representations, such as line endings, without rewriting unrelated whitespace. Compute line-level diff and refine changed regions at token or character granularity. Reject truncated outputs, missing required sections, or an implausibly large deletion unless the task warrants it. Parse the resulting file and run targeted checks before claiming success.

Associate edits with expected old text and buffer version; fail safely on ambiguous matches. Group accepted edits into one undo transaction. Benchmark application time, unchanged-line preservation, conflict rate, and semantic correctness on real edit patterns. For a 500-line file, inference and validation may dominate deterministic diff time, so profile before introducing a second model or complex patch language. The optimization goal is reliable edits, not merely fewer transmitted bytes.

### Preserve evidence about what changed

Suppose only lines 240–245 need alteration. Diffing the returned file against its exact base should produce one local hunk; unrelated spacing and line endings should remain byte-for-byte stable wherever possible. Applying a whole replacement creates noisy review, disrupts cursor positions, and can overwrite changes made while generation was running. The hunk carries expected old text so application can reject a stale target.

Some valid tasks intentionally change most of a file, so a large-diff threshold should request scrutiny rather than automatically declaring corruption. Detect more concrete truncation evidence: incomplete syntax, missing trailing declarations, or a generated closing fence included as source text. Parsing catches syntax errors but not incorrect behavior, so run tests tied to the requested edit as well.

Line-level diff is usually adequate for a 500-line file; refine only changed spans when preserving cursor anchors or minimizing edits matters. A minimal textual diff is not always the clearest semantic diff, especially after moving a function. Keep the review presentation and the safe application mechanism separate, and measure end-to-end task time before optimizing microseconds in the diff algorithm.
