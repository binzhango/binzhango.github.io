## Question

Design a Text-to-SQL system over a warehouse with thousands of tables.

## Brief answer

Retrieve a small relevant schema and business glossary, generate a constrained read-only query, validate it, and execute under the user’s database permissions and resource limits. Thousands of tables make schema selection and semantic definitions central problems.

## Detailed answer

Use curated joins, metric definitions and example queries with versioned provenance. Parse SQL into an AST to reject writes, unsafe functions or disallowed relations; add timeouts and cost limits through the engine. Clarify ambiguous time ranges and metrics before execution. Return the query, relevant assumptions and an explanation of results. Evaluate execution correctness on held-out databases and adversarial prompts; syntactically valid SQL can still answer the wrong business question.

Create a searchable catalog containing table descriptions, column meanings, join keys, ownership, freshness and business metrics. Retrieve a small schema neighborhood for the question rather than presenting thousands of tables. A semantic layer for definitions such as “active customer” or “net revenue” prevents the model from inventing a different metric each time.

Clarify ambiguity before generating SQL: time zone, date range, currency, aggregation grain and inclusion rules can change the answer. Generate a read-only query under the user's database identity, parse its AST, and reject disallowed operations or relations. Use the database's own permissions, row/column policies, timeouts and scan-cost limits. A read-only query can still leak restricted data or exhaust resources if those controls are absent.

Validate on synthetic or controlled databases with known answers, including joins that duplicate rows, nulls, slowly changing dimensions and time-boundary cases. Execution success is weaker than semantic correctness. Show the executed query and important assumptions with the result, and attach the data freshness time. If the result is implausible, use bounded correction based on engine errors and schema evidence rather than unrestricted query retries. Monitor incorrect joins and definition errors separately from syntax failures so improvements target the real source of wrong answers.
