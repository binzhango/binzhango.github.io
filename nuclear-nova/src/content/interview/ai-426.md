## Question

A customer wants to migrate from a proprietary frontier-model API to an open model. How do you run that engagement?

## Brief answer

Suggested approach: Run a task-focused migration evaluation rather than comparing leaderboard ranks. Establish current quality, latency, cost, privacy, and tool behavior, then test candidate open models under the customer's actual prompts and workflows. Open weights shift operational responsibility to the customer or host; they do not automatically reduce total cost or preserve frontier-model capability.

## Detailed answer

Inventory dependencies on context length, multimodality, structured outputs, safety behavior, caching, and provider-specific APIs. Build a heldout suite from representative and severe-error cases, protecting customer data. Compare prompt adaptation, retrieval improvements, quantization, and fine-tuning only when needed, with matched inference budgets.

Estimate serving hardware, utilization, reliability, licensing obligations, updates, and engineering effort. Run shadow tests and a limited canary behind a model abstraction that supports rollback. Keep the proprietary model for tasks where alternatives fail if policy permits. Deliver a measured recommendation, including cases where migration is unattractive, rather than treating full replacement as the predetermined outcome.

### Start with an acceptance contract

Define the supported tasks, severe failure classes, latency target, context lengths, and privacy/deployment requirements before selecting an open model. Reproduce current behavior on a heldout task set so migration is judged against actual needs rather than a public benchmark. Include tool use, structured outputs, refusals, multilingual inputs, and long-running agent recovery when those are part of the product.

Evaluate candidate models with their correct templates and appropriate prompts, then measure the intended quantized or serving configuration rather than an unrelated full-precision checkpoint. Estimate full ownership cost: hardware utilization, redundancy, upgrades, monitoring, licensing review, and engineering time. A hybrid rollout can retain the proprietary API for unsupported tasks while moving predictable workloads. Use shadow traffic and canaries with a versioned routing policy and rollback. If the open model requires many more tokens or human corrections, cheaper nominal inference may not produce cheaper successful tasks. Recommend partial migration or no migration when evidence supports it.
