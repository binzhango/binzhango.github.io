## Question

How do you evaluate a code-editing model before shipping it? Design the offline and online eval story for tab or agent edits.

## Brief answer

Evaluate code-editing models on task correctness, scope discipline, compatibility, and user effort. Offline tests provide controlled evidence; online experiments reveal whether suggestions help real workflows. Acceptance rate alone can reward plausible edits that are later reverted or introduce subtle bugs.

## Detailed answer

For tab completion, replay realistic edit traces with future context hidden and score useful accepted text, cursor relevance, latency, and invalid syntax. For agents, use issue-like tasks with hidden tests, build checks, and manual review of unintended changes. Split by repository and time to reduce leakage, and compare at equal tool and token budgets.

In a staged rollout, measure accepted edits that survive, undo/revert rate, time to task completion, test regressions, and user-reported harm. Segment by language, repository size, and task type. Use privacy-preserving telemetry and opt-in reviewed examples. Gate releases on severe regressions even when the aggregate improves. Keep failed cases as versioned regression tasks, and inspect whether apparent gains come from broader edits, more compute, or genuine model improvement.

### Define the unit of success

For tab completion, the unit is a suggestion at a particular buffer version and cursor location. Offline replay must reveal only information available at that moment; including later edits leaks the intended answer. For an agent, the unit is a task completed within a fixed budget, with the final patch evaluated against behavior and scope constraints. Combining these into one acceptance percentage obscures their different failure modes.

An online user may accept a suggestion to inspect it, then undo it seconds later. Track survival over an appropriate horizon and whether the edit is followed by corrections, test failures, or abandonment. That signal still needs context: a later rewrite can be legitimate exploration rather than model failure. Pair telemetry with sampled task review instead of assigning automatic meaning to every event.

Use randomized rollout where practical and compare matched task classes. Hold severe failures, such as unwanted credential changes or silent deletion of user work, outside average-quality aggregation. Report the compute and human-review budget alongside success so a model that solves more tasks only by spending much longer is assessed as a real tradeoff.
