## Question

Kimi K2 targets agentic and coding tasks. How would you evaluate whether an agentic model is actually good, beyond a single benchmark number?

## Brief answer

Evaluate completed tasks under realistic budgets, repeated trials, and explicit permission boundaries. Report success, correctness, cost, latency, unsafe actions, and recovery from failure—not just benchmark score. Separate the model from the surrounding tools, prompts, and orchestration so improvements are attributable and comparisons fair.

## Detailed answer

Build suites for repository edits, debugging, terminal use, research, and multi-step workflows. Start each run from a reproducible snapshot and judge the final environment state using hidden tests or independently verified requirements. Include ambiguous requests, tool timeouts, stale documentation, malicious files, and tasks where the correct response is to ask for missing information.

Measure pass rate at a fixed token/tool/time budget and success across repeated runs. Log tool arguments, policy violations, unnecessary changes, and human interventions. Coding success requires more than existing tests passing: check security, maintainability, and requirement coverage. Keep a private, time-separated holdout and periodically refresh it. Kimi K2's reported benchmark results are a starting point for evaluation design, not evidence for every deployment.

### A concrete coding-agent trial

Give the agent a repository snapshot and a request to add pagination while preserving existing API behavior. Allow a fixed wall-clock and tool budget. Judge the resulting patch with hidden boundary tests, review unrelated changes, inspect whether dependencies or credentials were exposed, and measure how often a reviewer must intervene. “All tests passed” is insufficient if the agent deleted tests or never handled an empty page.

Repeat runs because sampling and tool timing affect outcomes. Report single-run task success, success across repeated trials, cost per successful task, and unsafe-action rate separately. A model with a higher best-of-ten score may be worse for a product that permits only one attempt. Classify failures into planning, tool selection, argument construction, environment recovery, and final verification so improvements target a mechanism. Keep the agent scaffold constant when comparing models, then evaluate the complete intended scaffold before release.
