## Question

p95 time-to-first-token regressed from 1.2 s to 3 s after a release. Walk me through finding and fixing it.

## Brief answer

Break time-to-first-token into client/network, queue, retrieval, prompt assembly, model prefill, and transport flush. Compare matched traffic cohorts before and after the release. A p95 increase from 1.2 to 3 seconds can reflect changed prompt lengths, cache misses, batching, or saturation even when average model compute is unchanged.

## Detailed answer

Inspect distributed traces and histograms conditioned on model, region, tenant, input tokens, cache hit, and concurrency. Verify that the timing endpoint really measures the first user-visible token; proxy buffering can delay display after inference already began. Replay representative requests on old and new releases at equal load, then bisect configuration and code changes.

If queueing dominates, examine admission control, worker readiness, and batch scheduling; if prefill dominates, inspect prompt growth, lost prefix reuse, or changed kernels. Roll back a harmful release while preserving traces. Validate the fix at realistic burst load and report p50/p95/p99, throughput, and output quality together. Reducing maximum batch size may improve one user's latency while lowering capacity enough to worsen the fleet's tail latency.

### Distinguish a service regression from a traffic change

Plot TTFT against input length and queue depth for both releases. If the new release receives twice as many long prompts, an unstratified comparison can look like a kernel regression. Conversely, unchanged per-request prefill time can coexist with much worse tails if a small utilization increase causes requests to wait behind large batches. Replaying a fixed request corpus at several offered-load levels distinguishes these cases.

An illustrative trace might show 100 ms at ingress, 1,900 ms waiting for a worker, 400 ms retrieving, 450 ms prefill, and 150 ms before the first visible event. Optimizing retrieval by 100 ms would barely address the dominant queue. Investigate a reduced warm pool, a model-loading bottleneck, or altered admission policy first. Do not add stage p95s and call the sum the end-to-end p95; measure the combined request distribution because stages and slow requests are correlated.

Use a canary with the same model, prompt distribution, cache conditions, and concurrent load to validate the fix. Retain a quality check and total-capacity guardrail so shorter prompts or smaller batches do not trade the visible latency regression for missing evidence or overload elsewhere.
