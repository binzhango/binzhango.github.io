## Question

Explain speculative decoding. When does it help, when does it hurt, and why adapt the speculator to live traffic?

## Brief answer

Speculative decoding uses a cheap draft mechanism to propose tokens and a target model to verify several at once. A correct acceptance/correction algorithm preserves the target sampling distribution; simply accepting matching-looking text does not. It helps when accepted tokens amortize verification and draft cost, and can hurt when acceptance is low or the target is already efficiently batched.

## Detailed answer

Measure expected accepted tokens per verification round, draft latency, target verification cost, and cache overhead. Prompt style, language, code versus prose, temperature, and model changes affect acceptance. Longer drafts can waste work when early tokens are rejected; short drafts may fail to amortize overhead.

Adapt draft length or model selection using recent acceptance and latency, with guardrails against oscillation and unfair resource use. Evaluate at realistic concurrency: a method improving single-stream latency may reduce total throughput under load. Keep a non-speculative fallback and compare output distributions or exact greedy behavior in correctness tests.

### Verification preserves the target distribution

Let q propose a token and p be the target model's probability for it at the same prefix. An exact speculative method accepts that sampled token with probability $\min(1,p/q)$, and on rejection samples from the appropriately normalized positive residual of p−q. The target can evaluate several drafted positions together, but accepting every draft unconditionally would instead sample from the draft model.

For greedy decoding, compare each proposed token with the target's greedy choice and stop at the first mismatch; tie handling must agree. Speed depends on how many tokens survive each verification pass relative to draft and verification cost. A draft specialized for code may perform poorly on another language, lowering acceptance. Adapt length or model choice from observed acceptance under the current traffic, with a non-speculative fallback. At high batch concurrency the target may already be well utilized, so extra draft work can hurt aggregate throughput even when single-request latency improves.
