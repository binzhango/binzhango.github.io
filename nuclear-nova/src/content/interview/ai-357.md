## Question

Design the routing layer that decides whether a user request is handled on-device, by a first-party server model, or by a third-party model.

## Brief answer

Suggested approach: route with an explicit policy combining task capability, privacy permissions, connectivity, latency, cost, and current device state. Local execution is attractive for private or offline tasks; server models may handle harder requests. A third-party route requires its own authorization and data minimization rather than being treated as an interchangeable fallback.

## Detailed answer

First classify the operation and required context without sending private content off-device. Check whether the local model supports the language, modality, tool schema, and complexity within memory and thermal limits. If not, determine whether the request may leave the device and whether a trusted server can satisfy the deadline.

Use calibrated routing signals and fallback conditions; raw model confidence is not sufficient. Preserve consistent tool permissions and response contracts across destinations. Record route decisions with minimal metadata and evaluate misroutes, quality, latency, and cost. Handle network loss or denied consent with a local limited response or a clear unsupported result. Do not automatically resend content to another provider after an ambiguous failure.

### Apply hard constraints before quality routing

A policy layer first determines whether data may leave the device and which providers are permitted. These are hard constraints. Among allowed destinations, a router estimates task suitability, latency, network availability, and cost. A local classifier can select a route without uploading the full private prompt merely to decide whether uploading is allowed.

For a simple rewrite while offline, the local path may be sufficient. A complex document analysis could use a first-party server if consent and policy allow it. A third-party path may require a separate permission and data-minimization step. Preserve the same tool-authorization boundary regardless of model quality. If a remote request times out, do not resend it to another provider automatically when doing so changes the approved disclosure. Measure false-local routes that produce poor answers and unnecessary-remote routes that increase cost or exposure. Use versioned policies and canary routing changes, since model upgrades can alter which tasks each destination handles well.
