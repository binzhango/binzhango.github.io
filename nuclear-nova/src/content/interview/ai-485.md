## Question

You are training an agent model with end-to-end RL in your own harness. Walk through the environment and reward design.

## Brief answer

Train in a sandbox that exposes the same tools, state transitions, and constraints as the deployed harness. Reward verified task completion and penalize unsafe or wasteful behavior without letting easy proxy rewards dominate. Hidden tests and trusted environment state should determine success, not the agent's final explanation.

## Detailed answer

**Suggested approach.** Sample repository snapshots and tasks with reproducible dependencies; the observation includes tool results and bounded working memory. Actions are typed edits and tool invocations. Terminal reward combines hidden functional checks, scope constraints, and explicit security invariants. Use modest cost penalties and intermediate rewards only when they correlate with progress and cannot be farmed by repetition.

Prevent access to hidden tests, grader code, and reward files. Include interrupted commands, flaky tests, dependency failures, and tasks requiring abstention. Separate training repositories and time periods from evaluation. Monitor reward versus independent human review to detect test overfitting, deletion of failing tests, or broad hard-coded fixes. Compare against the starting policy at equal budgets. A harness mismatch can erase training gains, so version tools and environment images with the model.

### Keep the reward outside the editable world

A coding task's terminal grader should execute hidden checks against a clean copy of the submitted patch. The agent may edit project tests as part of a legitimate task, but deleting a failing visible test cannot erase a hidden requirement. Likewise, a message claiming “all tests passed” earns no completion reward unless the trusted runner recorded the corresponding result.

An illustrative reward hierarchy first rejects forbidden actions or scope violations, then scores functional completion, and finally applies a modest efficiency preference among valid solutions. If saving a few tool calls can outweigh a correctness failure, the policy may learn to stop early. If rewards are issued for every successful test invocation, repeatedly running one trivial test can become a shortcut.

Train on varied environment conditions: missing dependencies, flaky checks, ambiguous tasks, and operations requiring a human decision. Evaluate whether the policy learns appropriate diagnosis and escalation, rather than treating every failure as a reason to rewrite more code. Version the model, tools, sandbox image, and grader together so a reward increase can be traced to a real policy improvement rather than an easier environment.
