## Question

An enterprise customer reports that responses from your deployed system have gotten slow. Walk me through the diagnosis.

## Brief answer

Trace latency across the entire request path and compare it with a known healthy period. Separate queueing, retrieval, reranking, prompt construction, model prefill, token generation and downstream tool time. “Responses are slow” may mean delayed first token, slow streaming or long answers; those have different causes and fixes.

## Detailed answer

Start with request IDs and percentiles by tenant, model, region, prompt length and output length. Check recent changes to documents, prompts, model versions, traffic and dependencies. Compare client-observed latency with server traces to identify network or buffering issues.

If queue time grew, inspect concurrency, admission and GPU capacity. If prefill grew, inspect prompt expansion and cache hit rate. If inter-token time grew, inspect batching, KV pressure and resource contention. If only tool-assisted requests slowed, isolate the external dependency and its retry policy.

Contain the issue with a measured intervention: rollback a prompt change, cap retrieved context, reduce unnecessary retries or add capacity. Verify quality alongside latency because blindly truncating context can create a second incident. Report the critical path and before/after evidence, not a list of speculative optimizations.

Ask which user-visible interval changed. Delayed first text suggests queueing, retrieval, tokenization or prefill; normal first text followed by long gaps suggests decode scheduling or transport buffering; a longer total response can simply reflect more generated tokens. Measure these separately before applying a broad “speed optimization.”

Compare matched requests across healthy and degraded periods, controlling for prompt length, output length, model tier and region. A larger retrieved-context default can double prefill work without any model change. Retry storms can make an external dependency appear slow while the real problem is multiplied load. Proxy buffering can hide tokens that the model already produced.

Choose one intervention tied to the observed bottleneck and verify both latency and task quality. Adding GPUs will not fix a serial slow API call; truncating context may reduce latency while making answers wrong. Preserve a replay workload and alert on the causal segment, with customer-observed p95/p99 latency as the final check that the improvement reaches users.
