## Question

Is vocabulary expansion necessary? Why?

## Brief answer

Vocabulary expansion is optional; consider it only when the existing tokenizer fragments important domain text inefficiently and the benefit justifies compatibility costs.

## Detailed answer

Measure token counts and task quality first. New tokens require resizing and training embedding rows and, where applicable, output-head rows; tied weights must remain consistent. The tokenizer must be deployed with every dependent model and adapter. Existing subword or byte fallback can often represent the text already, so poor terminology handling is not automatically a vocabulary problem. Expansion can invalidate caches and complicate serving.

Measure fragmentation rather than guessing from unfamiliar-looking tokens. Compare token counts for representative domain documents, especially identifiers, notation, and repeated technical terms. If a common domain unit becomes many tokens, adding it may reduce sequence length and improve efficiency, but the model still needs training to learn the new embedding and output behavior.

Suppose one frequently used term currently takes six tokens and becomes one. Each occurrence saves five input or output positions, but the benefit depends on how often it occurs and whether surrounding language remains unchanged. New randomly initialized rows have no learned meaning merely because the tokenizer can emit them. Initialization and continued training must connect them to the existing representation space.

Vocabulary changes affect both input embeddings and output logits, including tied-weight configurations. Adapters, quantized artifacts, token caches, and serving systems must use the matching tokenizer and vocabulary size. Evaluate whether the saved tokens justify those compatibility costs. If the actual failure is missing domain knowledge or poor task supervision, vocabulary expansion may consume effort without addressing the cause.
