## Question

Design the serverless inference layer: any of thousands of Hub models can receive a request at any moment.

## Brief answer

Use a model-aware scheduler with warm capacity for popular models and queued cold starts for the long tail. Resolve every request to an immutable model revision and validated runtime, then admit it only when memory, execution compatibility, and deadline constraints can be met. “Any model” cannot imply identical latency or unrestricted code execution.

## Detailed answer

**Suggested approach.** Maintain a registry of artifact size, accelerator requirements, tokenizer, supported tasks, and validated serving image. Route hot models to shared batching pools; stage cold weights from regional storage into host caches before GPU loading. Predict warmth from traffic and give paying latency tiers reserved capacity. Return an explicit cold-start estimate or asynchronous job handle when a synchronous deadline is unrealistic.

Separate model download, initialization, prefill, and decode queues so loading a huge model cannot starve active requests. Sandbox user code, disable arbitrary network access, and reject incompatible artifacts. Cap per-tenant concurrency and token reservations before scheduling. Record cold-start percentiles by model size, cache-hit rates, GPU utilization, deadline misses, and cost per successful completion. Test bursts across many distinct models, corrupt weights, out-of-memory loading, and cancellation during startup.

### Scheduling a cold model

Suppose a model requires 24 GB of weights and its admitted workload needs another 12 GB for caches and runtime buffers. A scheduler must reserve the combined footprint and loading headroom, not simply notice that a GPU has more than 24 GB free. Concurrent requests for the same absent revision join one loading operation. Without this single-flight rule, a burst can start dozens of identical downloads and exhaust host memory before inference begins.

Model instances move through downloading, loading, healthy, draining, and evicted states. Requests enter the serving queue only after a health check succeeds. On eviction, stop new admissions, finish or explicitly cancel active work, and retain useful host-cached weights when space permits. Rank warm candidates using predicted demand and reload cost; pure least-recently-used eviction can thrash between large models.

Hot pools improve latency but consume idle accelerator time. Long-tail queues lower idle cost but expose startup delays. Make that tradeoff part of the service contract, with bounded queue time and a clear rejection or asynchronous path when the requested model cannot meet its deadline.
