## Question

Why do we need text chunking?

## Brief answer

Chunking creates retrievable units that fit embedding and generation budgets while preserving enough context to interpret the evidence.

## Detailed answer

Whole documents can dilute relevant information or exceed model limits; tiny chunks can lose definitions and exceptions. Choose boundaries from document structure and expected questions. Preserve parent IDs, headings, and offsets so a small matched chunk can be expanded later. Overlap reduces boundary loss but increases storage and duplicates. Tune chunking with retrieval and answer-quality tests rather than applying a universal token count.

A retriever searches units, so chunk boundaries determine what can be selected together. If a policy rule is in one chunk and its exception in the next, returning only the rule can cause a wrong answer even though retrieval found the right topic. If the entire manual is one chunk, its embedding can dilute the local answer and exceed the generator's context budget.

Use document structure as the first boundary signal: sections, paragraphs, lists, code blocks, and tables. Add token limits to keep units within model constraints, and preserve headings or parent identifiers so a small matched unit can be expanded. Overlap can bridge boundaries, but increases index size and can fill the final context with repeated text.

Tune against actual questions. Short fact lookup may benefit from small chunks plus parent expansion; multi-step explanations may need larger coherent sections. Measure answer-bearing recall, packed-context completeness, and final answer quality, not just nearest-neighbor similarity. Record source offsets and versions so citations and document updates remain correct. There is no universal chunk size because the best unit depends on source structure, embedding limits, and the information needed to answer.
