## Question

Your p99 latency doubled after a deploy with no model change. Walk through the diagnosis.

## Brief answer

Split the regression into queueing, prefill, decoding, network and client rendering before changing model settings. An unchanged model can still experience scheduler, cache, dependency, traffic or infrastructure regressions.

## Detailed answer

Compare canary and control with the same prompt/output-length distributions. Inspect tokens admitted, cache hits, batch occupancy, kernel versions, CPU tokenization, GPU clocks, memory pressure and retries. Check whether a new timeout or retry policy amplified load. Replay representative traces against the previous build and bisect configuration changes. Roll back when the service objective is violated, then preserve traces and add a regression workload that reproduces the tail behavior.

Begin by comparing time segments for matched requests. If queue wait rose from 20 ms to 400 ms while GPU step time stayed constant, investigate arrivals, admission limits and available replicas. If only prefill slowed, compare prompt length, prefix hits, tokenization and prefill kernels. If inter-token gaps grew, inspect decode batch sizes, cache pressure and long-prefill interference. If server timing is unchanged, investigate proxy buffering and client rendering.

“No model change” does not imply identical work. A prompt-template change can multiply input length; a new default can increase output limits; a cache-key change can turn warm traffic cold. A deployment can also alter GPU placement, collective topology, graph capture or a quantized kernel fallback. Check these before blaming random variance.

Preserve request IDs and configuration versions, then replay a representative trace against both releases on comparable hardware. Use open-loop arrivals to expose queue instability; sequential requests will miss it. Roll back the smallest causal change once the regression is established, and compare p50, p95 and p99 rather than chasing one unstable outlier. Add a regression case that reproduces the responsible workload and include cancellation, retry amplification and resource saturation in the resulting alert criteria.
