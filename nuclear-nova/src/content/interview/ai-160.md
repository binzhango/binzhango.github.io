## Question

Implement a UI from a mockup with provided CSS and API.

## Brief answer

Translate the mockup into semantic structure and responsive constraints before adding interaction. Reuse the provided CSS, define loading/error/empty states and isolate the API adapter from rendering. The original mockup and API contract are absent, so a faithful reproduction cannot be specified; the example below demonstrates a scoped list interface with an explicit assumed response shape.

## Detailed answer

Assume `GET /api/items` returns an array of `{id, title}` objects. This runnable HTML uses text nodes to prevent API content from becoming executable markup.

```html
<section aria-labelledby="items-title">
  <h2 id="items-title">Items</h2>
  <button id="reload" type="button">Reload</button>
  <p id="status" role="status"></p>
  <ul id="items"></ul>
</section>
<script type="module">
const button = document.querySelector('#reload');
const status = document.querySelector('#status');
const list = document.querySelector('#items');
let controller;
async function load() {
  controller?.abort(); controller = new AbortController();
  const signal = controller.signal;
  button.disabled = true; status.textContent = 'Loading…';
  try {
    const response = await fetch('/api/items', {signal});
    if (!response.ok) throw new Error('Request failed');
    const items = await response.json();
    if (!Array.isArray(items) || items.some(x => !x || typeof x.title !== 'string'))
      throw new Error('Invalid response');
    list.replaceChildren(...items.map(item => {
      const li = document.createElement('li'); li.textContent = item.title; return li;
    }));
    status.textContent = items.length ? `${items.length} items` : 'No items yet.';
  } catch (error) {
    if (!signal.aborted) status.textContent = 'Could not load items. Try again.';
  } finally { if (!signal.aborted) button.disabled = false; }
}
button.addEventListener('click', load); load();
</script>
```

Verify keyboard operation, focus visibility, narrow viewports and all API states against the actual mockup once supplied. Use screenshot comparison for layout and interaction tests for behavior; passing a snapshot alone does not establish usable loading or failure states.

Start by inventorying the mockup's actual states and constraints: content hierarchy, spacing, maximum width, breakpoints, focus behavior and overflow. The provided CSS should be reused before introducing competing styles. An API contract needs more than the happy-path shape: specify errors, empty results, authentication expiry and whether a reload should preserve old data while loading.

The example uses `textContent` so API titles remain text. `AbortController` cancels obsolete requests, and the captured signal prevents an aborted older request from resetting the button state of a newer one. In a larger app, also guard stale responses when an adapter cannot truly cancel underlying work.

Verify keyboard access and status announcements, then inspect narrow and wide screenshots against the real reference. Test slow, failed, empty and malformed responses with deterministic fixtures. Because the original mockup is absent, the sample demonstrates safe rendering and state management rather than a fabricated claim of visual fidelity. A faithful implementation requires comparing the actual artifact, not merely reproducing a generic list.
