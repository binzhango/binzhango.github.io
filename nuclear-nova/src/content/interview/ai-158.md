## Question

Create a database ORM, step by step.

## Brief answer

Start with a small data mapper: map a known table to a typed object, bind values with SQL parameters, and keep transaction control explicit. Add relationship loading, schema migrations and query composition only after the basic identity and persistence contracts are clear. An ORM must not confuse object construction with a committed database write.

## Detailed answer

This scoped SQLite example supports saving and fetching users. The table and column names are fixed; only values are parameterized.

```python
import sqlite3
from dataclasses import dataclass

@dataclass
class User:
    id: int
    name: str

class Users:
    def __init__(self, connection): self.db = connection
    def save(self, user):
        self.db.execute('''INSERT INTO users(id,name) VALUES(?,?)
            ON CONFLICT(id) DO UPDATE SET name=excluded.name''', (user.id, user.name))
    def get(self, user_id):
        row = self.db.execute('SELECT id,name FROM users WHERE id=?', (user_id,)).fetchone()
        return None if row is None else User(*row)

connection = sqlite3.connect(':memory:')
connection.execute('CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT NOT NULL)')
repo = Users(connection)
with connection: repo.save(User(1, "O'Reilly"))
assert repo.get(1) == User(1, "O'Reilly")
assert repo.get(2) is None
```

Next define dirty tracking or explicit updates, optimistic version checks and eager versus lazy relationship loading. Test rollback, duplicate identity and SQL-injection-shaped values. Avoid building SQL identifiers from unchecked user input; parameters bind values, not identifiers.

This is a data mapper rather than a complete ORM: the `User` object contains data, and `Users` translates between objects and fixed SQL. Parameter binding keeps a name such as `O'Reilly` a value rather than SQL syntax. The connection context manages the transaction boundary; constructing or modifying a Python object alone does not persist it.

The upsert defines identity by primary key. Decide whether saving a missing ID inserts and saving an existing ID overwrites, or whether separate create/update methods are preferable. For concurrent edits, add a version column and update only when the expected version matches, otherwise one user can silently overwrite another.

Relationship loading introduces the N+1 query problem: fetching each user's related records lazily can generate one extra query per object. Offer explicit eager loading or batched lookup and test query counts. Keep schema migrations outside ad hoc object construction, and avoid a generic query builder until the supported operations require it. An ORM is valuable when it makes persistence contracts clearer, not when it hides transactions and database costs from callers.
