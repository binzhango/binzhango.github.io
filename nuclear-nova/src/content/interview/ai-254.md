## Question

Design a token-based rate limiter for a multi-tenant LLM API. Implement the core, then tell me what changes when it's distributed.

## Brief answer

Reserve a bounded token charge in an atomic per-tenant bucket before starting work, then settle once using actual usage. The core must handle duplicate requests, unused reservations and time-based refill without allowing repeated refunds or over-admission.

## Detailed answer

This single-process Python core uses a lock, an injected monotonic clock and a hard maximum charge. The caller must enforce that generation cannot exceed the reservation. Request IDs cannot be reused during their retention lifetime; completed IDs remain in the ledger to reject duplicate settlements.

```python
from threading import Lock

class TokenLimiter:
    def __init__(self, capacity, rate, clock):
        if capacity <= 0 or rate <= 0:
            raise ValueError('positive capacity and refill rate required')
        self.capacity, self.rate, self.clock = capacity, rate, clock
        self.buckets, self.reservations = {}, {}
        self.lock = Lock()

    def _refill(self, tenant):
        now = self.clock()
        tokens, last = self.buckets.get(tenant, (self.capacity, now))
        tokens = min(self.capacity, tokens + max(0, now-last)*self.rate)
        self.buckets[tenant] = (tokens, now)
        return tokens, now

    def reserve(self, tenant, request_id, maximum):
        if not 0 < maximum <= self.capacity:
            raise ValueError('invalid reservation')
        with self.lock:
            key = (tenant, request_id)
            if key in self.reservations:
                raise ValueError('duplicate request ID')
            tokens, now = self._refill(tenant)
            if tokens < maximum:
                return False
            self.buckets[tenant] = (tokens-maximum, now)
            self.reservations[key] = maximum
            return True

    def settle(self, tenant, request_id, actual):
        with self.lock:
            key = (tenant, request_id)
            reserved = self.reservations.get(key)
            if reserved is None:
                raise ValueError('unknown or already settled request')
            if not 0 <= actual <= reserved:
                raise ValueError('usage exceeds enforced reservation')
            tokens, now = self._refill(tenant)
            self.buckets[tenant] = (min(self.capacity, tokens+reserved-actual), now)
            self.reservations[key] = None

now = [0.0]
limiter = TokenLimiter(100, 10, lambda: now[0])
assert limiter.reserve('a', 'one', 80)
assert not limiter.reserve('a', 'two', 30)
limiter.settle('a', 'one', 50)
assert limiter.reserve('a', 'two', 30)
assert limiter.reserve('b', 'one', 100)  # tenant isolation
now[0] = 10
assert limiter.reserve('a', 'three', 100)
```

Operations are expected O(1) with hash maps; ledger space grows with retained request IDs. Production needs bounded retention, crash-safe reservations and a recovery policy for unfinished requests. Across servers, move debit/settlement to a transactional shared authority or lease quotas with bounded overshoot. Never implement distributed admission as an unlocked read-then-write. Define whether the product limits admission tokens or billed tokens, since refunds and long-running requests affect the interpretation.

### Admission and billing are related but distinct

In the test, tenant A reserves 80 from a 100-token bucket, leaving 20. A second request needing 30 is rejected. Settling the first request at 50 returns 30 unused credits, allowing the second request. Tenant B has an independent bucket. Time-based refill permits later bursts up to the capacity, while the lock makes each decision atomic within this process.

The caller must actually stop generation at the reserved maximum; otherwise the limiter's accounting invariant is false. Completed request IDs remain as tombstones to reject a second refund, so retention must outlast valid retries and be bounded in production. A process crash needs durable reservation state and reconciliation of actual provider usage. Across gateways, use a transactional authority or leased quotas whose total overshoot is explicitly bounded. Separate concurrent outstanding work from rate credits: a long request can occupy cache after its admission charge has refilled. Test duplicate settlement, cancellation, expiration, tenant isolation, and concurrent admission at the capacity boundary.
