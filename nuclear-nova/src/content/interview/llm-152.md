## Question

How can knowledge-graph retrieval improve on standalone vector similarity search?

## Brief answer

Graph-based retrieval can follow explicit relationships and constraints to find evidence that a standalone similarity search misses.

## Detailed answer

For example, first identify which team owns a service, then retrieve that team's current escalation policy. This depends on accurate entity resolution, edge typing, and temporal validity. Combine graph candidates with text retrieval and reranking, and pass supporting passages to the generator. Graph construction can lose information or introduce unsupported links, so it is not a universal replacement for vector or lexical search.

A graph can enforce relational structure that a similarity score does not express. For “Which active services depend on library L and are owned by team T?”, traverse dependency and ownership edges and apply the active-status condition. Vector retrieval may find many documents about L or T without establishing that all conditions hold for the same service.

The benefit depends on graph quality. Resolve entity aliases, preserve direction and relation type, and attach temporal validity. Ownership can change while an old document remains semantically relevant. Each returned path should carry source evidence for its edges; a generated relationship without support should not become a definitive answer simply because it is stored in a graph.

Combine graph selection with passage retrieval. The graph identifies candidate services, while source text explains operational details and exceptions. Bound traversal to avoid generic high-degree nodes overwhelming the context. Compare against structured database queries where authoritative tables already exist; extracting a graph from prose is unnecessary when the required relationships are available directly. Use graph retrieval when explicit connections improve the targeted questions enough to justify construction and maintenance.
