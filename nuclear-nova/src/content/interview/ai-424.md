## Question

A customer's distributed training job on your GPU cluster gets 55% scaling efficiency at 64 nodes. Debug it.

## Brief answer

First define scaling efficiency: for strong scaling, compare fixed-workload speedup against the increase in node count; for weak scaling, keep work per node fixed. At 55%, profile exposed communication, pipeline bubbles, input stalls, imbalance, and hardware health. A single percentage cannot identify whether the network, parallelism layout, or workload size is responsible.

## Detailed answer

Compare step-time breakdowns at one, several, and 64 nodes with the same numerical configuration. Inspect collective latency, all-to-all traffic for MoE, gradient bucket sizes, compute/communication overlap, and synchronization stragglers. Check topology placement, NIC utilization, failed links, CPU pinning, and data-loader throughput.

If local batches became too small, matrix efficiency and communication amortization may collapse. If global batch increased, ensure the comparison accounts for convergence and not just tokens/sec. Tune parallelism and accumulation based on the bottleneck, then test quality-equivalent time to solution. Preserve traces and a synthetic communication baseline so cluster faults can be distinguished from model-code regressions. Avoid increasing node count until the critical path is understood.

### Define the scaling baseline first

For strong scaling, global work stays fixed: ideal time at 64 nodes is one-node time divided by 64. Efficiency of 55% means speedup is 35.2× relative to that baseline, assuming the single-node run is itself comparable and feasible. For weak scaling, work per node stays fixed and the interpretation differs. State which experiment produced the number.

Break step time into data loading, forward/backward kernels, exposed collectives, pipeline bubbles, and optimizer work. Compare rank-level traces to find whether every node waits on communication or one straggler delays all others. A collective microbenchmark can identify topology/NIC faults; a compute-only benchmark can expose undersized local batches. Gradient accumulation may amortize communication but changes update cadence and potentially convergence. Judge fixes by quality-equivalent time to solution and total cost. Adding nodes can improve raw tokens per second while worsening efficiency and economics, so locate the knee in the measured scaling curve.
