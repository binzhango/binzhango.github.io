## Question

Design the scheduler for a continuous-batching inference engine.

## Brief answer

Suggested approach: schedule at iteration boundaries, removing finished requests and admitting new work according to token, KV-memory, and latency budgets. Mix decode steps with bounded prefill chunks so long prompts do not stall active streams. Continuous batching improves utilization, but needs fairness and admission control to avoid starvation and out-of-memory failures.

## Detailed answer

Track each request's prompt progress, generated length, cache blocks, deadline, priority, and cancellation state. Reserve enough cache for the next scheduled work and maintain a pool-wide safety margin. Prefer urgent decode work while allowing prefill to make progress through bounded chunks; tune this policy using measured SLO trade-offs.

Reclaim blocks only after device work completes, and handle preemption by a supported swap or recomputation policy. Use per-tenant quotas and aging so short or high-priority traffic cannot starve others indefinitely. Measure throughput under first-token and inter-token constraints, not unconstrained tokens/sec. Test bursty arrivals, long outputs, cache exhaustion, canceled clients, and worker failure.

### Schedule by resources, not request count

A request with a 20,000-token prompt consumes very different prefill work and cache from a short chat. At each iteration, select a token/work budget whose weights, live KV blocks, and temporary tensors fit. Advance existing decodes, admit bounded prefill chunks, and incorporate newly arrived or completed requests without waiting for a fixed batch to finish.

Pure decode priority can starve new prompts; pure prefill priority can stall existing streams. Use deadlines, quotas, and aging to balance first-token and inter-token SLOs. Estimate future cache growth conservatively and define preemption when memory is tight: recomputation, swap, or rejection have different costs. Canceled requests stop consuming scheduling slots, but physical blocks can be reused only after device work referencing them completes. Test bursty long prompts and long generated outputs separately. Optimize SLO-compliant throughput and tenant fairness; a benchmark that maximizes tokens per second while allowing arbitrarily long waits is not a useful interactive scheduling result.
