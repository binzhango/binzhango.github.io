## Question

A Spark job joining a 2 TB fact table to a 50 GB dimension table has one straggler task running 100x longer than the rest. Diagnose and fix it.

## Brief answer

Suggested approach: Inspect the straggler's input, shuffle, spill, CPU, garbage collection, and executor health. A single huge join partition often indicates key skew, but a slow disk, lost executor, or pathological user function can look similar. Fix the measured cause; increasing the cluster size does little when one hot key still maps to one task.

## Detailed answer

Use the Spark UI and task metrics to compare partition sizes and duration distributions. Count heavy join keys, including null/default values, and inspect the physical plan. A 50 GB dimension is not automatically safe to broadcast: compressed storage size differs from in-memory serialized and hashed size.

Project and filter early, update statistics, and evaluate adaptive skew-join handling. For persistent hot keys, isolate them or salt the fact key while replicating only the corresponding dimension rows, preserving join semantics. Tune shuffle partitions for normal data but recognize that repartitioning by the same hot key alone does not split it. Verify row counts and multiplicity after changes. Spark SQL performance tuning documents adaptive query execution and skew handling.

### Distinguish skew from a sick executor

If one task reads hundreds of times more shuffle bytes than others, a heavy join key is likely. If similar-sized tasks are slow only on one executor, inspect disk, network, garbage collection, and hardware health instead. A null or default key can concentrate a large fraction of a 2 TB fact table into one partition even with many shuffle partitions.

For key skew, isolate the heavy key or split it using a salt. Replicate only its matching dimension rows across the salt values, then join on key plus salt so each fact row still matches exactly the intended dimension records. Handle null and outer-join semantics deliberately. Adaptive execution may split skewed shuffle partitions when the deployed version and query support it. Do not broadcast the whole 50 GB dimension merely because it is smaller than the fact table; its in-memory representation may overwhelm every executor. Verify row multiplicity and result checksums after optimizing, since an apparently faster join that drops matches is incorrect.
