## Question

You need to run an LLM call over 50,000 documents. The API allows ~100 concurrent requests and occasionally returns 429s and timeouts. Write the Python.

## Brief answer

Stream documents into a bounded worker pool, cap in-flight requests below the provider's concurrency ceiling, and add token/request-rate admission separately. Persist each document's result by stable ID and retry only transient errors. Timeouts can leave an unknown server outcome, so use idempotency or reconcile before repeating costly side effects.

## Detailed answer

This Python 3.11+ core uses 90 workers as illustrative headroom below a roughly 100-request ceiling. The injected `call` adapter should translate HTTP 429/5xx into retryable errors and honor `Retry-After`.

```python
import asyncio, random

class Retryable(Exception): pass

async def run_documents(documents, call, save, workers=90):
    if workers < 1: raise ValueError('positive worker count required')
    queue = asyncio.Queue(maxsize=2*workers)
    async def worker():
        while True:
            item = await queue.get()
            try:
                if item is None: return
                doc_id, text = item
                for attempt in range(5):
                    try:
                        answer = await asyncio.wait_for(call(doc_id, text), 60)
                    except (Retryable, TimeoutError) as error:
                        if attempt == 4:
                            await save(doc_id, {'status':'failed', 'error':type(error).__name__})
                        else: await asyncio.sleep(random.uniform(0, min(30, 2**attempt)))
                    except Exception as error:
                        await save(doc_id, {'status':'failed', 'error':type(error).__name__}); break
                    else:
                        await save(doc_id, {'status':'ok', 'answer':answer}); break
            finally: queue.task_done()
    async with asyncio.TaskGroup() as group:
        for _ in range(workers): group.create_task(worker())
        for document in documents: await queue.put(document)
        for _ in range(workers): await queue.put(None)
```

A persistence failure should stop the run so completed work is not silently lost; writes must be idempotent and durable. Resume by selecting unfinished IDs, track retry counts and p95 latency, and reduce concurrency after sustained throttling. Fifty thousand pending tasks are unnecessary: the queue bounds scheduling memory independently of corpus size. Test with fake calls that time out, fail permanently and return out of order.

The queue bounds pending scheduling work to a small multiple of worker count, while each worker owns one document through its retries. Persisting by stable document ID allows completion out of order and safe restart. A resume query should select only unfinished or explicitly retryable IDs rather than resubmitting every document and hoping duplicates are harmless.

Ninety simultaneous calls do not guarantee compliance with a provider's token-per-minute limit. Estimate prompt/output budgets and use a separate rate controller; reduce offered load after sustained 429s instead of merely adding retries. The adapter should honor server retry timing and distinguish authentication or validation failures from transient overload. The shown retry exception is intentionally minimal and would need to carry that metadata.

Test result-store failure separately from provider failure: if an answer was produced but could not be saved, the job must not claim completion. For expensive calls, an idempotency contract or durable provider request ID can help reconcile uncertainty after timeout. Track completed, failed, retried and abandoned documents, with a final count that reconciles to the input set. This avoids a batch that reports success while silently losing a small fraction of records.
