## Question

How do you evaluate an LLM workflow before and after giving it access to production operations?

## Brief answer

Before writes, evaluate reasoning and tool plans in a stateful sandbox with production-like permissions and failure cases. After enabling operations, evaluate actual outcomes, unauthorized effects, recovery, and human workload under a staged rollout. Access to production changes the consequence of errors, so release gates must become stricter than answer-quality checks alone.

## Detailed answer

**Suggested approach.** Start with replay and shadow mode, compare proposed actions against expert decisions, and test deterministic invariants such as spending limits and allowed resource scopes. Then allow drafts or reversible low-risk actions with approval, logging authoritative receipts and reconciliation states. Expand only after predefined thresholds and incident-response readiness are met.

Track duplicate writes, wrong-target actions, policy violations, false success claims, time to recovery, and business benefit. Sample successful-looking runs for hidden errors. Test adversarial instructions, stale data, revoked permissions, and network failures after commit. Maintain a kill switch and model/prompt version rollback. A high offline score cannot compensate for an execution service that lacks idempotency or authorization.

### Production writes add new failure classes

Before writes, a sandbox should reproduce identities, object states, permissions, and tool error behavior. Score the proposed final state, not whether the agent used the expected words. A work-order task passes only if the correct asset, fields, and status are produced without changing unrelated records. Inject stale versions, duplicate messages, and timeout-after-commit cases.

Progress from shadow proposals to drafts, then to a narrow reversible action set under the appropriate approvals. Record authoritative receipts and compare a sampled set with human review. After production access, monitor wrong-target writes, duplicates, unauthorized effects, and unresolved transactions separately from answer quality and latency. A false “done” message can conceal a failed external operation, so reconcile task and system state. Keep a kill switch at the executor boundary to stop new actions while preserving read access for diagnosis. Promotion decisions should combine useful business outcomes with explicit severe-error gates and tested recovery, rather than treating high offline accuracy as sufficient authorization to expand operations.
