## Question

You're handed a small unfamiliar agent codebase. Users report it sometimes confirms an order that was never actually placed. How do you debug it?

## Brief answer

Trace one false confirmation from the conversation through tool invocation, backend response, and persisted order state. The likely architectural defect is allowing generated language to claim success without authoritative transaction evidence, but verify the actual failure before changing prompts. Contain the issue by blocking unsupported confirmations immediately.

## Detailed answer

Reproduce with a sandbox order and correlation ID. Inspect timeouts after commit, exceptions swallowed as empty results, optimistic UI state, mock responses, duplicate retries, and ambiguous status mapping. Query the order system directly to distinguish “not placed” from “placed but acknowledgment lost.” Preserve logs without exposing customer payment data.

Represent order execution as explicit states such as proposed, authorized, submitted, confirmed, failed, and unknown. Only a validated backend receipt permits the confirmed state; unknown outcomes trigger reconciliation, not a blind retry or reassuring message. Add regression tests for network interruption before and after commit, malformed responses, and duplicate requests. Evaluate both backend correctness and the wording presented to the customer, since a real failure can still be compounded by a misleading explanation.

### Reconcile uncertain outcomes

Consider a payment request that reaches the order backend, commits, and then loses its response. Retrying with a new identifier may create a duplicate; telling the user it failed may also be false. Persist an operation ID before submission and query status by that ID after a timeout. The conversation should say the result is being checked until the backend resolves the uncertainty.

At the tool boundary, return a typed result such as `{status, operation_id, order_id, error_code}`. A nonempty string or HTTP 200 from a proxy is not enough to enter the confirmed state. Validate that the response belongs to the expected customer and operation, and distinguish an accepted asynchronous request from a completed order.

Add a test that deliberately disconnects after commit and checks both the backend ledger and the customer message. Add another where the backend rejects the order but an empty error object reaches the agent. These reproduce the causal boundaries that matter. Prompt changes may improve wording, but the durable fix ties success language to authoritative state and prevents unsupported transitions.
