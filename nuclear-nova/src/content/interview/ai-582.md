## Question

Find and fix a double-counting bug in a function that tallies values in a HashMap.

## Brief answer

First define whether the tally counts rows, distinct events, or entities, then reproduce the smallest double-counting case. Fix the actual duplication boundary rather than subtracting an arbitrary amount. If retries produce duplicate events, deduplicate by a stable event ID and detect conflicting payloads under the same ID.

## Detailed answer

This example tallies unique immutable events `(event_id, key, amount)`. Repeated identical events are ignored; a reused ID with changed data is rejected rather than silently accepting inconsistent totals.

```python
from collections import defaultdict

def tally(events):
    totals, seen = defaultdict(int), {}
    for event_id, key, amount in events:
        payload = (key, amount)
        if event_id in seen:
            if seen[event_id] != payload:
                raise ValueError('conflicting event id')
            continue
        seen[event_id] = payload
        totals[key] += amount
    return dict(totals)

assert tally([('e1', 'a', 2), ('e1', 'a', 2), ('e2', 'a', 3)]) == {'a': 5}
assert tally([('e1', 'a', 2), ('e2', 'a', 2)]) == {'a': 4}
assert tally([]) == {}
```

Expected time is O(n), with O(unique events + keys) memory. For a distributed persistent tally, event deduplication and aggregate updates must commit atomically. If the original bug instead increments on both initialization and update, fix that branch and preserve legitimate repeated rows. The event-ID policy is a stated example contract, not a universal solution for every HashMap bug.

### Reproduce the duplication mechanism

For a branch bug, a minimal input containing one new key may reveal that initialization sets its first amount and a following unconditional update adds the same amount again. Fix the branch so each input contributes once. For retry duplication, one logical event arriving twice requires event identity rather than a branch change; two distinct events with equal values must both count.

The sample stores each event's payload before adding its amount. A repeated ID with the same payload is ignored, while a conflicting payload raises because its meaning is ambiguous. It intentionally retains all seen IDs, so an unbounded stream requires retention rules or durable deduplication storage. In a database-backed tally, inserting the event ID and updating the aggregate must be atomic; otherwise a crash between them can lose or duplicate a contribution. Test duplicate replay before and after other events, negative adjustments under the business contract, conflicting IDs, and empty input. Do not deduplicate by key alone, which would erase legitimate repeated activity.
