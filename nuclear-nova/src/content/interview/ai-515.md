## Question

Walk me through the latency budget of a query: query understanding → retrieval → rerank → LLM answer. Where do you spend and where do you cut?

## Brief answer

Budget the critical path from measured stage distributions and preserve slack for tail behavior. Query understanding should be cheap unless it measurably improves retrieval; search branches can run in parallel; expensive reranking should see a bounded set; generation cost depends strongly on prompt and output length. Optimize supported task completion under the latency target.

## Detailed answer

An illustrative two-second first-answer budget might allocate 100 ms to routing, 350 ms to retrieval, 200 ms to reranking, 350 ms to prefill, 700 ms to a short answer, and 300 ms to transport/slack. These are allocations to test, not measured timings. Parallel operations contribute their critical-path maximum, while queues and retries can add substantial tail latency.

Cut redundant model calls, oversized context, and unproductive retrieval branches before sacrificing necessary evidence. Apply per-stage deadlines and an explicit degraded mode when a branch times out. Trace p50/p95/p99 by query type, cache state, and load; summing independent p95 values is not a valid estimate of total p95. Compare quality at equal latency and cost to avoid shipping a fast but unsupported answer.

### Spend latency where it changes the answer

For an exact identifier lookup, a separate query-rewriting model may add hundreds of milliseconds while making the identifier less precise. Route directly to lexical search and spend the saved budget on validating the returned record. For a comparison requiring several sources, parallel retrieval branches and bounded reranking may be worth the additional time because missing a facet changes the conclusion.

Carry an absolute request deadline through the workflow and reserve output time before deciding how long retrieval may continue. If one branch times out, determine whether the remaining evidence is adequate; a degraded response must expose the limitation when it affects the answer. Returning fast with silently missing essential evidence is not a successful latency optimization.

Instrument timestamps at queue entry, execution start, evidence cutoff, generation start, first visible output, and completion. These boundaries reveal queueing and buffering that isolated model benchmarks omit. Compare before and after at the same traffic mix and load, and distinguish time to first visible content from time to a complete useful answer. Optimizing one can worsen the other.
