## Question

Write a service that proxies streaming TTS to a browser and cancels cleanly when the user navigates away.

## Brief answer

Propagate browser disconnects and deadlines to the upstream TTS request, stream with backpressure, and release both reader and connection resources on every exit path. Do not buffer the entire audio response or keep synthesizing after the listener leaves. The proxy must also enforce authentication, input size, provider policy, and media type.

## Detailed answer

This Node.js example is a small HTTP proxy skeleton using built-in `fetch` and stream bridging. Supply an approved upstream URL and token through environment configuration; add deployment-specific authentication before exposing it publicly.

```javascript
import http from 'node:http';
import { Readable } from 'node:stream';
import { pipeline } from 'node:stream/promises';

export function createTtsServer(upstream, token) {
  return http.createServer(async (req, res) => {
    if (req.method !== 'POST' || req.url !== '/tts') {
      res.writeHead(404).end(); return;
    }
    const controller = new AbortController();
    const timer = setTimeout(() => { controller.abort(); res.destroy(); }, 30000);
    res.on('close', () => { if (!res.writableFinished) controller.abort(); });
    req.on('aborted', () => controller.abort());
    try {
      let size = 0;
      const parts = [];
      for await (const chunk of req) {
        size += chunk.length;
        if (size > 16384) { res.writeHead(413).end(); return; }
        parts.push(chunk);
      }
      const response = await fetch(upstream, {
        method: 'POST', signal: controller.signal,
        headers: { authorization: `Bearer ${token}`, 'content-type': 'application/json' },
        body: Buffer.concat(parts),
      });
      if (!response.ok || !response.body) throw new Error('upstream failed');
      const type = response.headers.get('content-type') || '';
      if (!type.startsWith('audio/')) throw new Error('unexpected media type');
      res.writeHead(200, { 'content-type': type, 'cache-control': 'no-store' });
      await pipeline(Readable.fromWeb(response.body), res, { signal: controller.signal });
    } catch {
      controller.abort();
      if (!res.headersSent && !res.destroyed) res.writeHead(502).end();
      else res.destroy();
    } finally {
      clearTimeout(timer);
      controller.abort();
    }
  });
}
```

The browser should pass an `AbortController.signal` to its fetch and abort on navigation; the server still detects disconnects independently. Test cancellation before headers and midstream, slow readers, upstream errors, oversized input, and normal completion. Provider payload validation and audio playback buffering are separate concerns.


### Follow the stream through completion and cancellation

The browser sends a bounded text request. `fetch` opens the upstream response, `Readable.fromWeb` adapts its stream, and `pipeline` forwards chunks while respecting the downstream socket's ability to accept bytes. If the browser reads slowly, backpressure limits how much the bridge pulls into memory. This avoids accumulating an entire recording in the proxy, although the provider may still synthesize ahead internally.

Cancellation is distinct from successful completion. A response `close` event can occur after normal delivery, so `writableFinished` prevents treating every close as abandonment. A premature close aborts the provider request. The `finally` block clears the deadline and releases any remaining upstream work on both success and failure. Before response headers are sent, an upstream failure can become a 502; after audio has started, the server must terminate the stream because it cannot replace the already-sent status.

For production, validate the JSON schema and text length before contacting the provider, reject unsupported media encodings, and attach a request ID across both connections. Test with a mock upstream that emits small delayed chunks: verify that the first chunk arrives before the last is generated, then disconnect the client and assert that upstream generation stops. A status-code-only test would miss both buffering and cancellation bugs.
