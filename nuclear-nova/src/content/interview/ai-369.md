## Question

What does TensorRT / TensorRT-LLM actually do to a model to make it faster, and when will it not help?

## Brief answer

TensorRT optimizes supported inference graphs and selects efficient implementations; TensorRT-LLM adds LLM-specific kernels and serving techniques such as paged KV caches, in-flight batching, and quantized execution. Gains come from reducing launch and memory overhead and matching computation to the GPU. Unsupported operators, poor shape coverage, or non-GPU bottlenecks can limit the benefit.

## Detailed answer

Compare graph fusion, precision choice, kernel selection, and memory planning against the baseline. For LLMs, scheduler behavior and cache allocation can matter as much as an individual matrix kernel. Pin the model, runtime version, hardware, and build configuration, because supported features change.

Benchmark the complete request path with realistic shapes and concurrency. Compilation/startup expense may not pay off for infrequent or frequently changing models. An optimized engine cannot fix slow retrieval, an overloaded gateway, network stalls, or poor model quality. Verify outputs under the chosen precision and ensure fallbacks do not silently move expensive work to a slower path. Report quality and SLO-constrained throughput, not only a best-case kernel speedup.

### Explain a fusion benefit concretely

A baseline may write a matrix multiplication's output to memory, launch a separate bias kernel, then launch an activation kernel. A fused implementation can keep intermediate values close to compute and reduce launches and memory traffic. Precision-specific kernels, optimized attention, and planned tensor layouts can add further gains when the model and hardware support them.

Shape specialization helps select efficient implementations, but highly variable or unsupported operations may trigger slower paths. LLM serving also requires efficient KV storage, batching, and cancellation, so compare full runtime configurations rather than attributing all gains to compilation. An application spending two seconds on retrieval and 200 ms on model execution can save at most that model portion without other changes. Validate output differences after precision changes and record engine-build cost and warmup. Use the exact supported model and runtime version; “TensorRT” is a toolchain family, not a universal acceleration percentage.
