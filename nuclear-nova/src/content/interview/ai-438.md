## Question

Build the task-lifecycle core of an annotation platform. Start simple; I'll add consensus of k annotators, then priority re-review, then annotator cooldowns.

## Brief answer

Model tasks and assignments separately. Atomically lease an eligible task to an annotator, accept one submission per assignment, and complete a task only after its current review round has enough distinct eligible annotators. Re-review creates a new round; cooldown changes eligibility, not the identity or validity of historical votes.

## Detailed answer

**Suggested approach.** A task stores priority, round, required consensus count, and state. An assignment stores task, round, annotator, lease expiry, and submitted result, with a unique key on that triple. Claiming work runs in a transaction: select an eligible task, reserve one available slot, and create the lease. Submission checks the lease and round and is idempotent by assignment ID. Expired leases release slots without counting a vote.

Consensus is a reducer over distinct accepted submissions, with an explicit tie/adjudication state rather than arbitrary majority acceptance. Priority re-review increments the round and invalidates outstanding old-round writes, while retaining the audit history. Annotator cooldown is enforced using a server timestamp inside claim eligibility. Test simultaneous claims for the last slot, duplicate submission, late responses after re-review, conflicting votes, and cooldown expiry. Avoid using an in-memory queue as the authority for task state.


The following single-process reference core makes round, priority, consensus, lease, and cooldown semantics executable. Methods must be serialized by the caller; a real service replaces this in-memory state with the transactions described above. Labels are assumed to be from a validated finite vocabulary. A round completes when all k votes agree; disagreement goes to adjudication.

```python
class AnnotationQueue:
    def __init__(self, cooldown=0, lease=30):
        if cooldown < 0 or lease <= 0: raise ValueError('invalid timing')
        self.tasks, self.last, self.history = {}, {}, []
        self.cooldown, self.lease = cooldown, lease
        self.serial = 0

    def add(self, task_id, k=1, priority=0):
        if task_id in self.tasks or type(k) is not int or k < 1:
            raise ValueError('task must be new and k a positive integer')
        self.tasks[task_id] = dict(k=k, priority=priority, round=0, votes={},
                                   leases={}, state='open', result=None)

    def claim(self, user, now):
        if now < self.last.get(user, float('-inf')) + self.cooldown:
            return None
        for task_id, task in sorted(self.tasks.items(), key=lambda x: (-x[1]['priority'], x[0])):
            task['leases'] = {u: entry for u, entry in task['leases'].items() if entry[1] > now}
            if task['state'] != 'open' or user in task['votes'] or user in task['leases']:
                continue
            if len(task['votes']) + len(task['leases']) >= task['k']:
                continue
            self.serial += 1
            token = (task_id, task['round'], user, self.serial)
            task['leases'][user] = (token, now + self.lease)
            return token
        return None

    def submit(self, token, label, now):
        task_id, round_id, user, _ = token
        task = self.tasks[task_id]
        if task['round'] != round_id: raise ValueError('stale round')
        if user in task['votes']:
            old_token, old_label = task['votes'][user]
            if (old_token, old_label) != (token, label): raise ValueError('conflicting submission')
            return task['state']
        entry = task['leases'].get(user)
        if not entry or entry[0] != token or entry[1] <= now:
            raise ValueError('expired or invalid lease')
        del task['leases'][user]
        task['votes'][user] = (token, label)
        self.last[user] = now
        if len(task['votes']) == task['k']:
            labels = {value[1] for value in task['votes'].values()}
            task['state'] = 'complete' if len(labels) == 1 else 'adjudication'
            task['result'] = next(iter(labels)) if len(labels) == 1 else None
        return task['state']

    def rereview(self, task_id, priority):
        task = self.tasks[task_id]
        self.history.append((task_id, task['round'], dict(task['votes']), task['state']))
        task.update(round=task['round'] + 1, priority=priority, votes={}, leases={},
                    state='open', result=None)

q = AnnotationQueue(cooldown=10)
q.add('t', k=2)
a, b = q.claim('alice', 0), q.claim('bob', 0)
assert q.claim('carol', 0) is None
assert q.submit(a, 'yes', 1) == 'open'
assert q.submit(b, 'yes', 2) == 'complete'
assert q.submit(b, 'yes', 3) == 'complete'
q.rereview('t', priority=10)
assert q.claim('alice', 3) is None
assert q.claim('alice', 12) is not None
```

Cooldown here means time since the annotator's last accepted submission across tasks; it does not prevent concurrent leases on different tasks. If the product permits only one active assignment per annotator, add that global invariant. Re-review may use the same annotators after cooldown; independence requirements can instead exclude prior-round participants.

### Why the state transitions matter

Consider a two-vote task with Alice and Bob holding leases. Alice submits “yes”; Bob's lease expires before his response arrives. Carol may claim the freed slot, but Bob's late write must be rejected rather than counted as a third vote. The lease token identifies the exact assignment, not merely the annotator. After a re-review increments the round, even a previously valid token belongs to historical state and cannot complete the new round.

The reference implementation scans and sorts tasks on each claim, costing O(T log T) for T tasks before lease cleanup. That is acceptable for demonstrating correctness, not for a large production queue. A database implementation needs an eligibility index or queue of candidate task IDs, followed by a transaction that rechecks remaining slots. The queue is a scheduling hint; the transactional task and assignment records decide whether a claim succeeds.

Consensus also needs a product definition. Unanimity, majority, weighted experts, and a minimum confidence threshold produce different completion conditions. Changing the reducer should not change assignment uniqueness, lease expiry, or round isolation. Those are independent invariants that remain testable under every consensus policy.
