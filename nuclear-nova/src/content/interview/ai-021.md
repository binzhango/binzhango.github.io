## Question

Explain prefix caching / prompt caching. When should you use it, and what invalidates a cached prefix?

## Brief answer

Prefix caching reuses KV state for an identical token prefix under compatible model execution settings. It is useful when many requests share system instructions, tool definitions or document prefixes.

## Detailed answer

Key cache entries by model revision, tokenizer/template, adapter, position treatment and exact token prefix, plus tenant or authorization scope where needed. A changed token invalidates reuse after that position. Retrieval evidence changes frequently, so put stable material first when the prompt format permits. Cache-hit rate alone is insufficient: measure saved prefill tokens and avoid leaking cross-tenant information through reuse or timing. Prefix caching saves computation, but does not make decoding the remaining response free.

Consider a 4,000-token system-and-tool prefix followed by a 100-token user question. If many requests reuse the first 4,000 tokens exactly, a cache hit can skip most prompt computation. It still needs to compute the new suffix and all generated tokens. If a date or tenant identifier changes near the start, the reusable prefix ends there even when the rest of the prompt text looks similar.

The cache represents model activations, not a stored answer. Two requests with the same prefix can sample different continuations while safely reusing identical deterministic prefix states. Reuse requires matching the effective execution context: weights, active adapter, token IDs, position rules and any relevant multimodal inputs. Application authorization can impose a stricter sharing boundary than mathematical equivalence alone.

Operationally, retain high-value prefixes based on saved work and frequency, evict cold blocks, and avoid allowing one tenant to monopolize cache capacity. An exact text match can still fail if tokenization or chat-template revisions differ. Track hit coverage in tokens rather than only requests: a hit on ten tokens is not equivalent to a hit on ten thousand. Evaluate warm and cold traffic separately so capacity planning does not assume every request receives an unrealistically favorable cache state.
