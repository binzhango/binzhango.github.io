## Question

Estimate the KV-cache memory for a 3B on-device model at 4k context, and name the levers that shrink it.

## Brief answer

Parameter count alone cannot determine KV-cache memory; layer count, KV heads, head dimension, precision, context, and batch size are required. For ordinary GQA/MHA, bytes are approximately $2BLTn_{kv}d_hb$. The factor two represents keys and values. Quantized weights do not imply a quantized cache.

## Detailed answer

Illustrative 3B-like configuration: batch $B=1$, $L=28$ layers, $T=4096$, $n_{kv}=8$, $d_h=128$, and $b=2$ bytes. Cache size is $2\times28\times4096\times8\times128\times2=469{,}762{,}048$ bytes, or 448 MiB. These are assumed dimensions, not a claim about every 3B model.

Reduce memory through fewer KV heads, lower cache precision with calibration, shorter contexts, sliding-window attention where the architecture permits it, or architectural cache sharing. Paged allocation reduces fragmentation rather than the mathematical size of live KV values. Prefix sharing helps multiple requests, while a single on-device conversation benefits mainly from avoiding recomputation. Include allocator padding, temporary buffers, and peak application memory before declaring the model fits.

### Derive the cache formula

Each layer stores one key and one value per past token for every KV head. With batch B, context T, layers L, KV heads $n_{kv}$, head width $d_h$, and b bytes per element, memory is $M=2BTLn_{kv}d_hb$. Query-head count does not enter directly when several query heads share each KV head. Parameter count alone therefore cannot determine cache size.

In the stated example, doubling context to 8,192 doubles 448 MiB to 896 MiB. Reducing eight KV heads to two would yield 112 MiB at 4K, but that is an architecture change, not an arbitrary serving flag. One-byte KV elements would nominally halve value storage while adding scale metadata and possible quality costs. Sliding windows limit historical state only if the model's attention semantics support it. Include live concurrent requests: even a small per-request cache becomes substantial when multiple features or sessions run together.
