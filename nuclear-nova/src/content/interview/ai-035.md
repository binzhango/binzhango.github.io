## Question

How would you evaluate the quality of a RAG pipeline: retrieval and generation separately?

## Brief answer

Evaluate whether retrieval finds sufficient evidence separately from whether generation uses it correctly. An end-to-end score alone cannot distinguish a missing document from an unsupported answer.

## Detailed answer

For retrieval, use judged relevant passages, recall@k, ranking metrics and permission/version correctness. For generation, supply known-good context and assess factual support, completeness, citation accuracy and abstention. Then run the real combined pipeline on the same cases. Include unanswerable queries and corrupted or conflicting sources. Slice by document type, language and query complexity; use paired comparisons and uncertainty estimates when deciding whether a change is an improvement.

Build a small judged set with the user question, acceptable answer criteria, relevant document versions and the specific evidence spans needed. For multi-hop questions, mark all required pieces: retrieving one of two documents is partial success. Include questions that the corpus cannot answer so the system is evaluated for appropriate abstention as well as recall.

Run three experiments. First, evaluate retrieval alone: does the top-k contain the necessary evidence, and how highly is it ranked? Second, feed gold evidence to generation to isolate reasoning, citation and instruction-following failures. Third, run the actual retrieved context through the generator. The gap between the second and third experiments estimates how much retrieval/context assembly limits end-to-end quality.

For example, a correct policy document might be retrieved but its effective date omitted during chunking. The failure is neither a missing source nor pure hallucination; provenance and context assembly need inspection. Score factual correctness, supported-claim precision, completeness and citation coverage separately. Use blind human review for a representative subset and calibrate automated judges against it. Compare paired results on the same queries, report uncertainty and critical-error counts, and avoid choosing a release from one aggregate score that conceals permission or language-specific failures.
