## Question

Why use adapter-tuning?

## Brief answer

Bottleneck adapter tuning adds small trainable modules to a frozen backbone, allowing multiple tasks to reuse the same pretrained model.

## Detailed answer

Each task stores its own adapter parameters instead of a full copy of all model weights. This can reduce training-state memory and simplify task switching, especially when data is limited. Extra modules still require computation and can add latency. Choose adapter placement and width using held-out task quality and serving constraints.

Suppose many teams share one large pretrained model but each needs a different document format or specialized classifier. Saving a full model copy per team is expensive. A frozen backbone plus small task-specific bottleneck adapters allows those tasks to share the large weights while storing smaller separate updates. Training also avoids optimizer moments and gradients for frozen weights.

The adapter learns how to transform intermediate features for its task. Because the base remains fixed, it provides a stable starting representation, while the adapter's width and placement limit the adaptation capacity. A narrow module may suffice for modest behavior changes but can underfit a task requiring a larger transformation. More adapter capacity increases parameters and runtime work.

Deployment must load the correct adapter with the matching base model and preprocessing. Extra nonlinear modules add sequential computation and may complicate batching requests using different adapters. Compare latency, memory, task accuracy, and retained capabilities with LoRA or full tuning under the actual serving workload. Adapter tuning is attractive for modularity and resource savings; it is not automatically the fastest inference method or the strongest choice for every domain shift.
