## Question

How to build a domain evaluation set?

## Brief answer

Build a domain evaluation set from independently held-out sources and realistic tasks, with trustworthy references and clear scoring rules.

## Detailed answer

Split by document, entity, customer, or time where needed to avoid overlap. Include common requests, difficult reasoning, ambiguous inputs, unanswerable cases, and required refusals. Use executable or exact checks where possible and expert rubrics where judgment is necessary. Report uncertainty, slice results, latency, and cost. Keep development and final test sets separate, and version the dataset as domain requirements change.

Define the deployment task before collecting questions. A domain assistant may need factual lookup, interpretation of supplied documents, multi-step calculations, and appropriate abstention. Build separate labels or rubrics for those capabilities. For a numerical task, store the expected result, units, tolerance, and required source fields. For an explanatory task, identify the claims and qualifications a correct answer must contain.

Hold out source documents, cases, or time periods so training cannot contain near copies. Keep a development set for prompt and model selection and a final test set for reporting. Include questions whose correct answer changes across document versions, and record the source snapshot used to label them.

Score correctness, support, and behavior separately. An answer can quote the document faithfully yet fail the requested calculation, or give a correct number without adequate source support. For judgment-based scoring, calibrate reviewers on examples and resolve disagreements. Report uncertainty and important slices alongside latency and cost. Evaluation is a maintained product asset: version it when requirements change and preserve older regression cases instead of silently replacing difficult examples.
