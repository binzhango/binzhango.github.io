## Question

How does function calling actually work with an LLM, and how do you make it reliable enough for production agents?

## Brief answer

The model emits a structured proposal naming a tool and its arguments; the application validates and authorizes it, executes the tool, and returns a structured result for the next model step. Generating a valid call does not mean the action occurred or was permitted.

## Detailed answer

Use narrow schemas with explicit units and resource identifiers, and validate business rules beyond JSON types. Separate reads from writes, enforce caller permissions and require appropriately scoped approval for consequential changes. Bound the loop's steps and cost. For uncertain write outcomes, use idempotency keys and status reconciliation rather than retrying blindly. Return distinct success, retryable failure and permanent failure states. Test wrong-tool selection, invalid arguments, malicious tool output and repeated callbacks. Evaluate final environment state alongside the assistant's narrative, since it can incorrectly announce success after a failed execution.

### A tool call is a proposal in a state machine

For a calendar request, the model emits a tool name and arguments such as date, duration, attendees, and calendar ID. The host parses and validates those fields, resolves identities, checks permission and any required confirmation, then invokes a configured calendar API. The authoritative event ID becomes the tool result, which the model can use to explain the outcome.

Schema-conforming JSON does not establish that the intended attendee was selected or that a write is authorized. Those checks belong in the trusted executor. Distinguish invalid arguments, denied calls, transient failures, and unknown outcomes after timeouts so the next step can repair or reconcile appropriately. Store request IDs for side-effecting operations to prevent duplicate execution. Limit steps, tokens, and wall time, and stop on repeated ineffective calls. Treat tool descriptions and returned text as untrusted data. Evaluate final state—for example, exactly one correct event exists—rather than rewarding a confident “created” message after the API failed.
